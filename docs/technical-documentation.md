# ChanceMachine — Technical documentation

## Overview

ChanceMachine is an Angular PWA (Progressive Web App) that computes, via exact enumeration (no Monte Carlo), the hit/destroy probabilities against a target in Warmachine/Hordes, for a sequence of attacks (several attackers, several attacks each) chained against a single shared target.

- **Stack**: Angular 21 (standalone components, signals), TypeScript, Vitest.
- **No runtime dependency beyond Angular**: the calculation engine (`src/app/engine/`) is pure TypeScript with no Angular dependency, testable in isolation.
- **PWA**: `@angular/service-worker`, installable on mobile (Android/iOS via "Add to Home Screen"), works offline (the calculation engine itself makes no network calls - Feedback and the analytics script are the only things that do, and both are best-effort, never required for the app to function).

## The calculation engine (`src/app/engine/`)

### General principle: exact enumeration, no simulation

Dice rolls in Warmachine/Hordes involve small d6 pools (2 to ~8 dice with boosts). The outcome space (6^n) therefore stays tiny (6^8 ≈ 1.68 million cases, well under a second of computation). The engine therefore enumerates **every** possible outcome and aggregates their exact probabilities, rather than doing random draws (Monte Carlo). This gives deterministic, instant results, with no flicker in the display.

### `dice-pool.ts` — the base building block

- `rollDicePool({ diceCount, discard?, treatOnesAsSixes?, extraCritDice? })`: enumerates every roll of `diceCount` d6 (plus, if configured, `extraCritDice` extra dice), applies `treatOnesAsSixes` first (Jump the Shark — every 1 becomes a 6 before anything else), then any discard (keep the highest/lowest), then computes the sum and returns the aggregated distribution `{ sum, hasDouble, probability }[]`.
  - `discard?: { highest?: number; lowest?: number }`: the two counts are independent and **can be active at the same time** on the same roll (e.g. `{ highest: 1, lowest: 1 }` on 4 dice keeps the two middle dice). `applyDiscard(dice, highestCount, lowestCount)` sorts the dice then slices `sorted.slice(lowestCount, Math.max(lowestCount, sorted.length - highestCount))` — the `Math.max` avoids a `slice` whose end bound is below its start bound if the sum of the two exceeds the number of available dice (in which case the result is simply an empty list, summing to 0, rather than an error).
  - `treatOnesAsSixes` (Jump the Shark): turns every die showing 1 into a 6 before discard/sum/double detection — implemented at the lowest level (on each individual face) so that discard and double detection already see the transformed faces.
  - `extraCritDice` (Sanguine Fate): `N` extra dice rolled alongside the pool, which count toward `hasDouble` detection (a double with an "extra" die does trigger a critical hit) but are **never** included in `sum` — implemented by iterating over `diceCount + extraCritDice` dice in total, of which only the first `diceCount` feed the discard/sum.
- `hasDouble`: true if at least two rolled dice (before discard, counting Sanguine Fate dice) show the same face — that's the critical (double) trigger in WM/H.
- `rerollPoolOnceIf(outcomes, isBad)`: models a single, optional reroll of outcomes flagged `isBad`, correctly preserving the `(sum, hasDouble)` correlation: each kept outcome keeps its own `hasDouble`, and the rerolled probability mass is redistributed across **the entire** original distribution (including its `hasDouble` values) rather than overwriting `hasDouble` to `false`. This is the fixed version of an earlier bug (see below): the old implementation set `hasDouble: false` on every rerolled roll, which silently killed any chance of a critical hit on an attack with reroll active.
- `rerollPoolOnceIfBelow(outcomes, threshold)`: convenience wrapper around `rerollPoolOnceIf` for the "reroll if the sum is below a threshold" case (a below-average damage roll).
- `probabilityAtLeast`, `probabilityOfDouble`: aggregation utilities.
- Safety guard: throws an error beyond 8 dice total (`diceCount + extraCritDice`), well above anything the game produces.

**Bug fixed: `hasDouble` overwritten by a reroll.** The first implementation of reroll (`rerollPoolOnceIfBelow`) forced `hasDouble: false` on *every* roll after a reroll, including rolls that were kept without being rerolled — a naturally critical roll could therefore lose its critical status simply because reroll was enabled on that attack. Fixed by generalizing to `rerollPoolOnceIf(outcomes, isBad)`, which only touches `hasDouble` via the correct redistribution described above.

### `attack-model.ts` — a single attack

The calculation is split into two steps for performance reasons (see `sequence/`):

1. **`buildAttackProfile(attack, damage, target, effects, autoHit)` → `AttackProfile`**
   Builds an attack's full probabilistic profile — independent of the target's remaining box count:
   - `missChance`, `hitNonCritChance`, `hitCritChance`
   - `nonCritDamage` / `critDamage`: `damage → probability` distributions, conditional on a non-critical / critical hit.
   - If `autoHit` is true (a Stationary/Knocked Down target facing a melee attack, or an explicit `forceAutoHit`), no to-hit roll is made: `hitChance = 1`, `critChance = 0` (no to-hit dice rolled, so no double possible).
   - If **Brutal Damage** (`effects.brutalDamageDice`) is active, the critical damage distribution uses a larger dice pool (extra dice) than the non-critical distribution.
   - **Armor Piercing** (`effects.armorPiercing: EffectTrigger`): the ARM used for the damage roll (non-critical and/or critical, depending on `appliesOnNonCritHit`/`appliesOnCritHit`) is replaced by `Math.ceil(target.baseArm / 2) + (target.arm - target.baseArm)` — only the printed base is halved; every buff/debuff/penalty currently in play still applies on top, via `target.arm - target.baseArm` (the net modifier total, since `target.arm` is already the fully-resolved ARM). `baseArm` is the ARM **before** any buff/debuff/penalty (see `sequence/`), deliberately distinct from `target.arm` (the effective ARM, everything folded in) precisely so this delta can be recovered.
   - **Decapitation** (`effects.decapitation: EffectTrigger`): the relevant damage distribution is doubled afterward via `doubleDamageValues` (each `(damage, p)` becomes `(damage × 2, p)`).
   - **Trash** / **Shatter** (`effects.trash` / `effects.shatter`, booleans): an extra damage die is added if `target.knockedDown` / `target.stationary` is true **at the time of this attack** — these two flags are plain booleans passed in by `sequence/`, which alone is responsible for knowing whether the target is currently in that state.
   - This is the expensive part of the calculation (dice enumeration): it's only done **once per attack** (per distinct DEF/ARM/status context, see `sequence/`).

2. **`applyProfile(profile)` → `AppliedOutcome[]`**
   Flattens a profile into a plain list `{ probability, isHit, isCrit, damageDealt }` (cheap, just iterates over the distribution maps' entries).

3. **`computeAttackOdds(input)` → `AttackOdds`**
   High-level function for a single, isolated attack (used by tests and, conceptually, by any component that only needs a single attack): builds the profile, applies it, aggregates into `hitChance`, `missChance`, `critOnHitChance`, `damageDistribution`, `expectedDamage`, `destroyChance` (accounting for Tough), `chanceOfAtLeast(n)`.

**Roll modifiers (`RollModifiers`)**, applied independently to the to-hit roll and/or the damage roll (each has its own `modifiers`/`damageModifiers`):
- `boostDice`: extra dice added to the base pool (2d6).
- `discard`: `{ highest?: number; lowest?: number }` discard before summing — both can be set at once (see `dice-pool.ts` above).
- `reroll`: a single, optional reroll — see `applyRerollIfConfigured` below.
- `treatOnesAsSixes` (Jump the Shark), `extraCritDice` (Sanguine Fate): passed through as-is to `rollDicePool` (see `dice-pool.ts`).

**Reroll (`applyRerollIfConfigured` + `isBadDamageRoll`)**: when `modifiers.reroll` is active, the pool is rerolled via `rerollPoolOnceIf` with a "bad roll" criterion that differs by context:
- To-hit roll: "bad" = `!isHitOutcome(...)` (the roll would genuinely miss — not a simple `sum < neededDiceSum` comparison, see below for why).
- Damage roll: "bad" = `isBadDamageRoll`, i.e. a sum strictly below average (`sum < 3.5 × diceCount`) — rerolling a below-average roll strictly maximizes expected damage, so no configurable threshold is needed on the UI side.

**Supported effects (`AttackEffects`, formerly `CriticalEffects`)** — a deliberately short, precise list rather than a vague, generic system, though it has grown since its first version (which only contained Knockdown and Brutal Damage — Knockdown has since been moved into `sequence/`'s generic `StatEffect` system, see below):
```ts
type EffectTrigger = 'hit' | 'crit'; // 'hit' fires on any hit (crits included); 'crit' only on a critical hit

interface AttackEffects {
  brutalDamageDice?: number;      // crit only, no configurable trigger
  armorPiercing?: EffectTrigger;
  decapitation?: EffectTrigger;
  trash?: boolean;
  shatter?: boolean;
}
```
`appliesOnNonCritHit(trigger)` (`=== 'hit'`) and `appliesOnCritHit(trigger)` (`=== 'hit' || === 'crit'`) centralize this triggering logic — an effect with `trigger: 'hit'` therefore also applies on a critical hit (a crit is a special case of a hit), whereas `trigger: 'crit'` only applies on a critical hit.

**Attack type (`AttackType`)**: `'melee' | 'ranged' | 'arcane'`. Currently used to condition auto-hit against a Knocked Down/Stationary target (only melee automatically hits an immobilized target; ranged and magic roll normally against a DEF capped at 5 in that case, see `sequence/`).

**Extreme rolls (`isHitOutcome`).** Outside the `autoHit` case, the to-hit roll applies an extra rule before the classic sum-vs-DEF comparison: every **kept** die (after any discard) showing 1 is always a miss, and every one showing 6 is always a hit (unless only one die is kept). Since a die's face is always ≥ 1, the sum of N dice can only equal exactly N if every one shows 1, and can only equal 6N if every one shows 6 — `isHitOutcome` therefore detects both cases purely from `outcome.sum` and the number of kept dice (`keptDiceCount`), with no need to inspect each face individually or surface extra information from `dice-pool.ts`. A hit forced by "all 6s" with 2+ dice is necessarily also a double, and therefore a critical hit (`hasDouble` is true as soon as ≥2 dice show the same face) — no special handling is needed for `hitCritChance` to count it correctly.

### `sequence/` — chaining several attacks

`computeSequenceOdds(attacks: SequencedAttack[], target: SequenceTarget) → SequenceResult`

Computes the probability of destroying a target over the course of an attack sequence **ordered by the user** (no automatic ordering optimization — a product decision: see the functional documentation).

**Calculation model — a state distribution, not a combinatorial tree:**

Rather than branching a probability tree per attack (combinatorial explosion), the engine maintains a probability distribution over a **target state**, whose "persistent penalties" part is grouped into `DebuffState`:

```ts
interface DebuffState {
  knockedDown: boolean;
  stationary: boolean;   // Ice Cage at 2+ stacks also makes the target Stationary, see isStationary
  iceCageStacks: number; // the only penalty explicitly stackable besides armPenalty
  shadowbind: boolean;
  blind: boolean;
  paralyzed: boolean;
  flare: boolean;
  weaken: boolean;
  armPenalty: number;    // generic "-X ARM", cumulative
  dispelled: boolean;    // once true, every currently-Dispellable spell bonus/rule is gone - see "Target capabilities" below
  grievouslyWounded: boolean; // once true, no Tough/Tough Steady and no Rapid Healing - see "Rapid Healing" below
}
```

... combined with `boxes` (boxes remaining), `focusLeft`/`furyLeft` (remaining resource points) and `destroyed` (absorbing state) in the rest of the calculation. For each attack in the sequence, its profile is "folded" into the current state distribution:
- For each living state, the effective DEF/ARM are computed (`effectiveDef`/`baseArm - debuffState.armPenalty`) and whether the attack should auto-hit (melee + `isKnockedDownOrStationary`, or an explicit `forceAutoHit`), the right precomputed profile is chosen, and each outcome's probability is distributed across the new states (reduced boxes and/or new penalties, or destroyed) — after applying, if applicable, the target's **optimal** spend of a Focus/Fury point (see below).
- A Tough roll is retried every time damage (after any Focus/Fury mitigation) would be lethal (no "once per turn" limit in this model — a documented simplification in the code) - **unless the target is currently Knocked Down/Stationary**, in which case plain Tough can't be attempted at all (the real tabletop rule) and the target is simply destroyed; **Tough Steady** (`SequenceTarget.toughSteady`) is immune to that negation - see `damageBranches`. **Grievous Wounds** (`DebuffState.grievouslyWounded`) removes both outright, on top of (and regardless of) that negation - it's the one condition Tough Steady isn't immune to.
- If Tough (or Tough Steady) succeeds, the target is simplified to 1 box remaining and Knocked Down (standard Tough rule behavior), with no fine-grained re-modeling of a partial damage grid — this rule is what couples the "persistent penalties" sub-problem to the "boxes/resources" sub-problem (see below).

**Persistent effects (`StatEffect` / `StatEffectType`)**: each attack carries an optional `statEffects: StatEffect[]` list, each `{ type, trigger, amount? }` (`amount` only for `'armPenalty'`). `applyStatEffectsForOutcome(state, statEffects, isHit, isCrit)` applies, for a given outcome, every effect whose trigger matches (`'hit'` fires on any hit including a critical one; `'crit'` only on a critical hit) via `applyStatEffect` - a miss (`isHit: false`) applies nothing, regardless of any effect's own trigger. **Bug fixed**: `isHit` used to be missing from this function entirely, and the check was just `isCrit` - since a miss and a plain non-crit hit both have `isCrit === false`, an "on hit" effect (Knockdown, Stationary, ...) was wrongly applied on a MISS too, in both the backward-scoring pass and the forward replay (both funnel through the single `resolveOneOutcome` call site) - e.g. an arcane attack with ~0% real hit chance could still show a 100% chance to destroy, because its Knockdown was applied unconditionally and a later melee attack then auto-hit the (never actually) Knocked Down target.
- Every boolean flag (`knockedDown`, `stationary`, `shadowbind`, `blind`, `paralyzed`, `flare`, `weaken`, `dispelled`, `grievouslyWounded`) is **idempotent** — re-triggering it has no further effect, in line with the "an effect only applies once unless stated otherwise" rule. `dispelled`/`grievouslyWounded` are the odd ones out semantically (they strip bonuses/capabilities rather than adding a penalty) but mechanically they're just two more sticky flags, same `applyStatEffect` switch cases as the others.
- `iceCageStacks` is incremented on every trigger (the only flag explicitly stackable among the booleans), `armPenalty` is added to on every trigger (as specified for the generic "-X ARM").
- `isStationary(s)` = `s.stationary || s.iceCageStacks >= 2`; `isKnockedDownOrStationary(s)` = `s.knockedDown || isStationary(s)` — it's this last function that determines auto-hit in melee and the DEF cap of 5, exactly the same logic for Knockdown and Stationary (they're only distinguished because Trash/Shatter need to be able to tell them apart).
- `effectiveDef(baseDef, s)`: first caps DEF at `DEF_FLOOR = 5` if `s.paralyzed || isKnockedDownOrStationary(s)`, then subtracts the cumulative flat penalty (`iceCageStacks × 2 + shadowbind×3 + blind×4 + flare×2 + weaken×2`) — reproduces the "additive, with Paralysis/Knockdown/Stationary as a floor" rule validated with the user.

**Avoiding the combinatorial explosion of a dense 11-dimension penalty table (`getValueTableAt`, lazily-built `Map<string, ValueTable>`):**

Naively adding `DebuffState`'s 11 dimensions (9 penalty fields plus `dispelled`/`grievouslyWounded`) to the dense value table `number[boxes][focus][fury]` (already used for Focus/Fury, see below) would turn it into a ~14-dimension table, whose size would explode combinatorially even for a handful of configured effects. The fix: don't build a table for every THEORETICALLY possible `DebuffState` (or, once Puppet Master/Knowledge of the Damned added their own resource dimensions on top - see below - every possible mask/charge-count combination either) - build one **lazily, on first request, memoized** for whichever combinations a real branch of the computation actually produces:

- `getValueTableAt[k]` (built per step `k`, from `n` down to `0` in the backward pass) is a closure over its own `Map<string, ValueTable>` cache: called with `(debuffState, pmMask, kotdOffLeft, kotdDefLeft)`, it looks up `tableKey(...)` in that cache and returns the stored table if present, or builds one on the spot (via `shotsValue`, which resolves attack `k` against whatever LATER step's own `getValueTableAt[k+1]` calls it needs) and caches it before returning. Nothing precomputes "every state that could occur" up front the way an earlier version of this engine did (`computeReachableDebuffStates`, since removed) - a state that's never actually asked for during either the backward pass's own recursive construction or the forward replay simply never gets a table built for it at all, and the cost stays proportional to what's genuinely reachable, not to any dimension's full combinatorial range.
- The base case (`k === n`, no attacks left) is even simpler than "lazy": since every state trivially "survives" with value `1` regardless of boxes/debuffState/masks, `getValueTableAt[n]` just returns ONE shared table (`baseValueTable`, built exactly once) for every input, rather than a cache keyed by state at all.
- **Tough ↔ Knockdown coupling needs no special handling anymore.** The rule "surviving a Tough roll also knocks the target down" makes a `DebuffState` change depend on a dice roll that belongs to the resource sub-problem - `damageBranches` (see below) computes this directly, producing a `{...debuffState, knockedDown: true}` branch at the moment Tough succeeds. Under the OLD eager-precomputation design this required `computeReachableDebuffStates` to separately anticipate and widen for that exact transition (documented at length in an earlier version of this file); under the CURRENT lazy design there's nothing to anticipate - `getValueTableAt` builds a table for whatever state `damageBranches` actually hands it, on the spot, the same as any other state.
- **Attack profile cache (`profileCache` / `profileFor`)**: since an attack's effective DEF/ARM/status now depend on the current `DebuffState` (which can vary within a single step `k` if several penalty states are reachable at that point), the profile is no longer cached solely by attack index `k` but by the full key `` `${k}|${usesAutoHit}|${def}|${arm}|${knockedDown}|${isStationary(debuffState)}` `` — the number of distinct contexts actually encountered stays low in practice (bounded by the effects configured on the sequence), so the dice enumeration (the expensive part) is never redone for a context already seen. `def`/`arm` here are already the FULLY resolved numbers (printed stat, persistent debuffs, and the target's static buffs all folded in - see "Target capabilities" below), so the cache key correctly distinguishes contexts that only differ by, say, Unyielding applying to a melee attack but not a ranged one.

**Target capabilities - static, sequence-wide buffs on top of the printed stats, some spell-granted and therefore removable by Dispel:**

Unlike `DebuffState` (attack-triggered, evolves as the sequence plays out), the target's capability fields on `SequenceTarget` are fixed **inputs** for the whole sequence - they model target capabilities (Shield, spell bonuses, Unyielding, Carapace, Tough/Tough Steady) set once before the calculation runs, not something an attack can inflict. What CAN vary mid-sequence is which of these are still *active*, since Dispel (a `StatEffectType`, see above) strips every currently-Dispellable one - so most of these fields come in a **pre-Dispel/post-Dispel pair**, and `profileFor`/`damageBranches` pick whichever half matches `debuffState.dispelled`:

| Capability             | Pre-Dispel field    | Post-Dispel field           |
|------------------------|---------------------|------------------------------|
| Shield's ARM bonus     | `shieldArmBonus`    | *(none - see below)*         |
| Spell ARM bonus        | `spellArmBonus`     | `spellArmBonusPostDispel`    |
| Spell DEF bonus        | `defBonus`          | `defBonusPostDispel`         |
| Non-spell ARM bonus    | `nonSpellArmBonus`  | `nonSpellArmBonusPostDispel` |
| Non-spell DEF bonus    | `nonSpellDefBonus`  | `nonSpellDefBonusPostDispel` |
| Unyielding             | `unyielding`        | `unyieldingPostDispel`       |
| Carapace               | `carapace`          | `carapacePostDispel`         |
| Tough                  | `tough`              | `toughPostDispel`            |
| Tough Steady           | `toughSteady`        | `toughSteadyPostDispel`      |

**The non-spell ARM/DEF bonus pair is currently always 0** - `target-panel.model.ts` has no non-spell (feat/aura) source left in its model at all (see `TargetState`'s "Upkeep spells / Animi"/"Spells" fields below), so `OddsCalculator`'s `sequenceTarget` computed simply omits `nonSpellArmBonus`/`nonSpellArmBonusPostDispel`/`nonSpellDefBonus`/`nonSpellDefBonusPostDispel` from the object literal it builds (all four are optional on `SequenceTarget`, defaulting to `?? 0` inside `sequence/` - see below). The fields themselves, and every line of `sequence/` logic that reads them, are left fully intact - a UI-unreachable engine capability, not a deleted one, the same "keep the capability, prune only the now-dead UI path" treatment `SPELL_RULE_OPTIONS`/`grantsRule` got earlier in this file's history.

The UI layer (`odds-calculator.ts`) fills the pre-Dispel half with the "effective" value (permanent toggle OR dispellable grant - `effectiveUnyielding`/`effectiveCarapace`/`effectiveToughKind`/`spellArmBonus`/`spellDefBonus` in `target-panel.model.ts`) and the post-Dispel half with the **raw permanent signal alone** (`target.unyielding()`, `target.toughKind() === 'tough'`, etc.) or `spellArmBonusPostDispel`/`spellDefBonusPostDispel`. This is a deliberate simplification that falls out of a real invariant in the model: `dispellableUnyielding`/`dispellableTough` (see `TargetState` below) are, by definition, always what Dispel removes - "post-Dispel" for Unyielding/Tough/Tough Steady never needs to filter anything, it's simply "ignore the dispellable grant, keep only the permanent toggle." The spell ARM/DEF bonus pair works the same way now: `TargetState.spellArmAmount`/`spellDefAmount` ("Spells") are permanent and always survive Dispel, `upkeepSpellArmAmount`/`upkeepSpellDefAmount` ("Upkeep spells / Animi") never do - see `spellArmBonus`'s doc comment below.

**Shield has no post-Dispel field at all**, and `shieldArmBonus` is read by `profileFor` unconditionally (never gated by `debuffState.dispelled`) - there's no dispellable-Shield concept in the UI at all (unlike Unyielding/Tough, which each have one - see `TargetState.dispellableUnyielding`/`dispellableTough`), so `shieldArmBonus` is always just the innate capability's bonus (`target.shieldAmount()`), which Dispel can never touch. If the UI ever exposes a dispellable Shield, this field would need to split into an innate/dispellable pair exactly like the others.

**Two per-attack toggles narrow this further, independent of Dispel**: `SequencedAttack.blessed` makes a specific attack ignore every Stat-type bonus flagged **Spell** (DEF and ARM) - the non-spell counterpart (`nonSpellArmBonus`/`nonSpellDefBonus`, a feat or non-spell aura, currently always 0 from the UI - see above) is never Blessed-ignorable - and `SequencedAttack.chainWeapon` makes it ignore Shield's ARM bonus specifically. Neither is a `DebuffState` flag (they don't persist or get triggered), just a plain boolean read straight off the attack being resolved. `profileFor`'s `contextFor` combines both axes, folding the non-spell bonus in WITHOUT gating on `atk.blessed`:
```ts
const activeStatArmBonus =
  (atk.blessed ? 0 : debuffState.dispelled ? spellArmBonusPostDispel : spellArmBonus) +
  (debuffState.dispelled ? nonSpellArmBonusPostDispel : nonSpellArmBonus);
const activeShieldArm = atk.chainWeapon ? 0 : shieldArmBonus;
```
(`activeStatDefBonus` mirrors this for DEF.)
- `def = effectiveDef(baseDef, debuffState) + activeStatDefBonus` - the (Blessed/Dispel-filtered) stat DEF bonus is added *after* the debuff floor/penalty logic, so it still helps even on a floored (Knocked Down/Paralysis) DEF.
- `arm = baseArm - debuffState.armPenalty + activeShieldArm + activeStatArmBonus + conditionalArmBonus`, where `conditionalArmBonus` is resolved fresh for every attack (`activeUnyielding && atk.type === 'melee' ? 2 : 0` `+` `activeCarapace && atk.type === 'ranged' ? 4 : 0`) since it depends on that specific attack's type - Unyielding/Carapace can't be pre-summed the way Shield/stat bonuses can. `activeUnyielding`/`activeCarapace` are the Dispel-gated pair lookup (`debuffState.dispelled ? unyieldingPostDispel : unyielding`), same pattern as the ARM/DEF bonuses above.
- Critically, **`baseArm`/`baseDef` themselves are never touched by any of this** - they stay the target's raw printed stats. Armor Piercing needs that untouched value to know exactly what to halve (`Math.ceil(baseArm / 2)`), then re-applies every buff/debuff/penalty on top via `arm - baseArm` (see `attack-model.ts`'s `buildAttackProfile`) - it changes *what gets halved*, not whether modifiers apply at all. This is why every one of these bonuses is resolved as a separate addition in `profileFor` rather than folded into `target.arm` before it ever reaches the engine: `attack-model.ts` needs both the fully-resolved `arm` and the untouched `baseArm` side by side to compute that delta.

**Tough/Tough Steady are resolved OUTSIDE `profileFor` entirely** (in the resource-branching logic - `damageBranches`/`bestAction`, see below), so they need the same pre/post-Dispel selection done there instead. Rather than threading five separate parameters (two tough flags × two Dispel variants, plus the shared fail chance) through every call, they're bundled into one `ToughRules` object built once in `computeSequenceOdds` and passed down:
```ts
interface ToughRules {
  hasTough: boolean;
  hasToughSteady: boolean;
  hasToughPostDispel: boolean;
  hasToughSteadyPostDispel: boolean;
  failChance: number; // same threshold either way - Dispel doesn't change the Tough roll's target number, only whether it applies at all
}
```
`damageBranches` picks `debuffState.dispelled ? tough.hasToughPostDispel : tough.hasTough` (and the Tough Steady equivalent), then ANDs in `!debuffState.grievouslyWounded`, before applying the existing Knocked Down/Stationary negation rule - Dispel, Grievous Wounds, and the Knockdown-negation rule are three independent conditions that all have to allow a Tough attempt for it to actually happen (Grievous Wounds is the only one of the three that also blocks Tough Steady - see the module doc comment). `hasAnyTough` (gating whether `toughRules.failChance` is even computed, rather than left at its default `0`) stays `hasTough || hasToughSteady` without needing the post-Dispel variants folded in: by construction, `hasToughPostDispel`/`hasToughSteadyPostDispel` can only be true if the corresponding pre-Dispel flag is already true (post-Dispel is strictly the innate-only subset of pre-Dispel, per the invariant above), so checking the pre-Dispel pair alone already covers every case the post-Dispel one could add.

**Rapid Healing - a third sub-problem, folded into `damageBranches`'s output rather than tracked as its own dimension:**

`SequenceTarget.rapidHealing` (a plain boolean, unlike Tough/Unyielding/etc. it has no pre/post-Dispel pair - see its doc comment for why) and `HealingRules` (`{ hasRapidHealing, initialBoxes }`, the `boxes`-dimension counterpart to `ToughRules`, built once in `computeSequenceOdds`) drive `healBranches`:
```ts
function healBranches(boxes, rawDamageDealt, debuffState, focusLeft, furyLeft, healing): ResourceBranch[] {
  if (!healing.hasRapidHealing || rawDamageDealt <= 0 || debuffState.grievouslyWounded) {
    return [{ probability: 1, boxes, debuffState, focusLeft, furyLeft, destroyed: false }];
  }
  return [1, 2, 3].map((healAmount) => ({
    probability: 1 / 3,
    boxes: Math.min(healing.initialBoxes, boxes + healAmount),
    debuffState, focusLeft, furyLeft, destroyed: false,
  }));
}
```
`damageBranches` calls this at both of its exit points - the plain non-lethal case, and the Tough-survival case (from 1 box) - so a target that gets knocked down to 1 box by a lethal hit but saves it via Tough can still heal back up afterward if it's also eligible. `Math.min(healing.initialBoxes, ...)` caps the result at the target's starting box count, which isn't just thematic - it's also *necessary*, since `ValueTable` is indexed `0..initialBoxes` and a heal that overshot that range would be an out-of-bounds write.

**`rawDamageDealt` vs `damageDealt` - the eligibility check is deliberately based on the attack's damage BEFORE Focus/Fury, not the amount that actually reached `boxes`.** A model that spends a resource point to blunt or fully negate a hit was still hit - the point softens the consequence, it doesn't undo the fact that the attack landed - so Rapid Healing still triggers off the original wound. Only a genuine miss, or a hit ARM already reduces to 0 before Focus/Fury is even a factor, skips healing. This means `damageBranches` and `bestAction` have to carry two damage values side by side rather than one:
```ts
function damageBranches(boxes, damageDealt, rawDamageDealt, debuffState, focusLeft, furyLeft, tough, healing): ResourceBranch[]
```
`damageDealt` is whatever a given candidate action actually subtracts from `boxes` (the lethal check, and the non-Tough non-lethal case, both use this one); `rawDamageDealt` only ever reaches `healBranches`, unchanged by whichever mitigation was chosen. `bestAction` receives a single `damageDealt` parameter (the attack's true raw damage, straight from `outcome.damageDealt`) and passes it through as `rawDamageDealt` to all three of its candidate `damageBranches` calls - the no-mitigation one (where it's also the literal `damageDealt`), the Focus one (`max(0, damageDealt - 5)` as `damageDealt`, but still the original as `rawDamageDealt`), and the Fury one (`0` as `damageDealt`, still the original as `rawDamageDealt`). A worked example lives in `engine.spec.ts`'s "Rapid Healing still triggers on a Fury-negated hit" test: a target forced (by an otherwise-certain-destruction lethal hit) to spend its one Fury point still heals afterward, because that hit's raw damage was nonzero even though the mitigated damage that hit `boxes` was 0.

No special handling is needed for any of this: healing only ever changes `boxes` (a dimension the value-table machinery already handles per-step), never `DebuffState` - Grievous Wounds is the one thing that gates it, and that's already a `DebuffState` flag tracked for the Tough interaction above.

**Same-attack ordering, established already by Knockdown/Tough and reused here as-is.** Both `bestAction` call sites compute `newDebuffState = applyStatEffectsForOutcome(oldState, atk.statEffects, isCrit)` *before* calling `damageBranches`/`healBranches` - so if a single attack inflicts Grievous Wounds `'on hit'` and also deals the damage that would otherwise trigger Rapid Healing (or a Tough save), the wound is already in effect for that same hit's resolution, not just for later attacks. This isn't special-cased for Grievous Wounds/Rapid Healing - it falls directly out of the existing evaluation order, the same one a Knockdown-and-lethal-damage-in-one-attack scenario already relies on. (A test exercising exactly this - `engine.spec.ts`'s "Grievous Wounds also disables Rapid Healing, including on the very hit that inflicts it" - has to be careful the attack's own damage doesn't also trigger a *self-referential* Tough check the same way; see the Tough-vs-Knockdown tests earlier in the same file for the `boxes: 50` workaround that isolates one attack's effect from corrupting another's.)

**Why it's fast even at ~10 attacks:**

An attack's profile (`buildAttackProfile`, the part that enumerates dice — expensive) does **not** depend on the target's remaining box count. It's therefore cached per distinct context (see `profileCache` above, in practice a small handful per sequence), then reapplied cheaply against every state encountered. A performance test (`engine.spec.ts`) verifies that a sequence of 10 attacks (with or without resource points, with or without persistent effects) runs in under 2 seconds (in practice near-instant).

**Optimal Focus/Fury spending — backward induction (`valueTables`):**

The target may spend, once per attack and after the damage roll, a Focus point (reduces damage by 5) or a Fury point (fully negates damage), never both at once. It's assumed to play **optimally**, meaning: maximizing its probability of surviving the **rest of the sequence**, not just reacting to the current hit. Since the decision is made before knowing future dice rolls, but with a known attack sequence ahead of time, this problem is solved via **backward induction** (dynamic programming) rather than pure forward simulation:

1. **Backward pass**: for each attack `k` (from the last to the first) and for each penalty state actually reached, a table `getValueTableAt[k](debuffState, ...)[boxes][focusLeft][furyLeft]` is built (lazily - see "Avoiding the combinatorial explosion" above) = probability of surviving attacks `k..n-1` while playing optimally **given that we're in this penalty state**, computed from `getValueTableAt[k+1]` (built on demand, recursively, the first time IT'S asked for a given state) and attack `k`'s profile for that context. The base case is `1` everywhere (no attacks left = already survived).
2. For each state and each outcome of attack `k`, `bestAction` (in `sequence/`) compares the 3 possible choices (spend nothing / spend Focus / spend Fury) and keeps the one that maximizes this future survival value.
3. **Forward pass**: the exact same policy is replayed (via the same already-warm `getValueTableAt` caches) to produce the actual state distribution and the displayed statistics (`hitChance`, `destroyChanceAtThisStep`, etc.).

**Tie-breaking.** Comparing only "probability of surviving the rest of the sequence" can produce strict ties (e.g. the target is doomed either way, or no future attack depends on the exact remaining box count anymore). A naive comparison (strict `>`) would then systematically resolve these ties toward "spend nothing", which reads as counter-intuitive behavior (the target refuses to defend itself on the current hit even though doing so would cost it nothing). `bestAction` therefore uses a **3-level lexicographic score** (see `outcomeScore`/`isBetterScore`): (1) probability of surviving the rest of the sequence — the real objective; (2) as a tiebreaker, probability of surviving **this specific hit**; (3) as a further tiebreaker, number of boxes preserved. Only when all 3 levels are fully tied does the point go unspent (default behavior: keep the resource).

**Shield Guards and Scapegoats (`SequenceTarget.shieldGuards`/`scapegoats`) — two more `bestAction` candidates, architecturally alongside Focus/Fury rather than a new profile-level stage:**

Unlike Puppet Master/Knowledge of the Damned (which reroll dice, so they have to act BEFORE outcomes are enumerated - see below), a Shield Guard/Scapegoat block only needs the outcome that already happened (hit + damage + would-be effects), the exact same timing Focus/Fury already use. So they're added as two more `bestAction` candidates and two more DENSE `ValueTable` axes (`number[boxes][focusLeft][furyLeft][shieldGuardsLeft][scapegoatsLeft]`), not folded into `tableKey` the way `pmMask`/`kotdOffLeft`/`kotdDefLeft` are - `ResourceBranch`/`ValueLookup` both gained `shieldGuardsLeft`/`scapegoatsLeft` fields accordingly, threaded everywhere `focusLeft`/`furyLeft` already are.

A block is a TRUE block, not mitigation like Focus/Fury, which creates two twists Focus/Fury never needed:

- **Reverting `DebuffState`, not just damage.** By the time `bestAction` used to run, `newDebuffState = applyStatEffectsForOutcome(oldState, atk.statEffects, isCrit)` had already been computed and was the ONLY debuff state `bestAction` ever saw - the pre-hit state was simply discarded once `resolveOneOutcome` moved past it. `bestAction` now takes BOTH `oldDebuffState` and `newDebuffState`: every existing candidate (nothing/Focus/Fury) still resolves against `newDebuffState` exactly as before, but a block candidate calls `damageBranches(boxes, 0, 0, oldDebuffState, ...)` - reverting to the state as it was before this hit's `statEffects` ever applied.
- **Never triggering Rapid Healing.** Calling `damageBranches` with BOTH `damageDealt` and `rawDamageDealt` at 0 is sufficient on its own - no new helper needed. `healBranches`'s existing gate (`rawDamageDealt <= 0` skips healing) already treats this exactly like a miss, and pairing it with `oldDebuffState` means Grievous Wounds/other `statEffects` from this hit were never applied either. This is the one place a block's semantics genuinely diverge from Fury's own `damageBranches(boxes, 0, damageDealt, ...)` call (which deliberately keeps the ORIGINAL `damageDealt` as `rawDamageDealt`, so Rapid Healing still triggers off a Fury-negated hit - see the Rapid Healing section above): a block passes 0 for BOTH.

**Suppressing Critical Shred on a block, without touching Hit%/Crit% — the one place `bestAction` needed a second `valueAt`.** A blocked crit must not chain into another Shred instance (a TRUE block - the hit never really landed), but it must still count toward the displayed Hit%/Crit% for that attack (those are tallied upstream in `resolveAttackChainForward`, straight from `outcome.isHit`/`isCrit`, before `resolveOneOutcome` is even called - completely unaffected by anything `bestAction` decides, exactly as they already are for Focus/Fury). Since `continuesChain` (whether a crit chains) is baked into the SAME `valueAt` every candidate used to share, `bestAction` now takes two lookups instead of one:

```ts
function bestAction(..., valueAt: ValueLookup, blockValueAt: ValueLookup): { branches: ResourceBranch[]; valueAt: ValueLookup }
```
`valueAt` (possibly a Shred-recursing closure) scores the nothing/Focus/Fury candidates; `blockValueAt` (always "attacks k+1 onward", never Shred) scores the two block candidates. `bestAction` returns whichever of the two matches the candidate it actually picked, so the caller (`resolveOneOutcome`) always scores/routes the winning branches with the lookup consistent with how they were chosen - `resolveOneOutcome` forwards this as `continuationValueAt` (used for scoring) and also derives an explicit `continuesChain: boolean` from it (`rawContinuesChain && valueAt !== blockValueAt`) for `resolveAttackChainForward`'s own forward-pass routing, which can't compare closures the way the backward pass implicitly does. When a hit doesn't crit-and-chain in the first place, `valueAt` and `blockValueAt` are literally the same function reference, so this split costs nothing in the common case.

**`MAX_SCAPEGOATS = 4`, deliberately separate from `MAX_RESOURCE_POINTS = 10`.** Scapegoats are mechanically capped at 4 by the feature's own spec - a genuinely smaller limit, not a tightened version of the shared Focus/Fury/Shield-Guard cap, so it gets its own constant and its own validation branch in `computeSequenceOdds`, rather than reusing `MAX_RESOURCE_POINTS`.

**Performance: a different KIND of cost than Knowledge of the Damned's, not a restatement of it.** `pmMask`/`kotdOffLeft`/`kotdDefLeft` are folded into `tableKey`, so they multiply how many DISTINCT `ValueTable`s might get built - and `getValueTableAt`'s laziness means most combinations, for a short sequence, are simply never built at all. `shieldGuardsLeft`/`scapegoatsLeft` are dense array axes INSIDE `ValueTable` itself instead, so they multiply the SIZE of every table that IS built, unconditionally - there's no laziness benefit inside a plain array. Every table built now costs up to `(maxShieldGuards+1) × (maxScapegoats+1)` (≤ 11×5 = 55×) more than before, on top of the `(maxFocus+1)×(maxFury+1)` factor already there. At realistic UI ranges (boxes ≤ 99) this stays bounded, but it's worth flagging explicitly as a distinct cost rather than something the Knowledge of the Damned-era performance note already covers.

**Critical Shred (`SequencedAttack.criticalShred`) — a bounded self-referential value problem, wrapping `bestAction` rather than replacing it:**

Every other effect changes DEF/ARM/boxes/`DebuffState` for a FIXED, known-in-advance sequence of attacks. Shred is the odd one out: a crit makes the SAME attack fire again immediately, and that instance can itself crit and fire again - so the number of dice rolls "at position `k`" becomes a random variable, not a constant. Rather than dynamically growing the sequence (which would make `attacks.length` itself probabilistic, breaking the per-step `getValueTableAt`/attack indexing everywhere else), this is modeled as a small recursive value problem local to position `k`, bounded by a constant `MAX_SHRED_DEPTH = 10`:

```ts
function attackChainValue(k, atk, debuffState, boxes, focusLeft, furyLeft, depthRemaining, outerValueAt, cache): number
```

Resolves ONE instance of attack `k`, and - on a crit with `atk.criticalShred` set and `depthRemaining > 0` - recurses into ANOTHER call to itself (`depthRemaining - 1`) instead of falling through to `outerValueAt` (attacks `k+1` onward); every other outcome (miss, non-crit hit, or a non-shredding attack) takes the `outerValueAt` branch as before. This means `attackChainValue` **replaces** the old inline `bestAction`+`branchesValue` call at every use site in the backward pass, shred or not - for an attack without Critical Shred, `continuesChain` is always false, so it degenerates to exactly the pre-Shred single-instance computation (verified by the full pre-existing test suite passing unchanged after the refactor). Memoized per `` `${depthRemaining}|${debuffKey}|${boxes}|${focusLeft}|${furyLeft}` `` in a `cache` shared across the whole `buildValueTable` grid for a given `k` - the same `(boxes, damage-so-far)` combination is reachable via many different orderings of chained crit damage, and this cache is what keeps that from being recomputed each time.

**Truncation, not a rules limit.** There's no tabletop cap on how many times a Shred chain can continue - only the dice decide. `MAX_SHRED_DEPTH = 10` caps the calculation anyway: each further instance requires another crit, so the untruncated tail's probability is `critChance^depth` - for any realistic crit chance this is astronomically small well before depth 10 (`0.3^10 ≈ 6e-6`), the same "exact enough" tradeoff already used for Tough's "no once-per-turn limit" and the app's existing 0.0005 display cutoff. `engine.spec.ts`'s "extends average damage into a geometric series" test measures this directly: an untruncated infinite series would give exactly `245/31`, and the actual (depth-10-truncated) result differs from that by ~3e-9 - small enough that the test needs `toBeCloseTo(..., 8)` rather than the `9` used everywhere else in that file, specifically to keep this real (if minuscule) truncation gap from failing on floating-point-level precision.

**No precomputed widening needed for a shredding attack's crit-only `statEffects` (Ice Cage, generic "-X ARM" - anything explicitly stackable) firing once per instance in the chain.** An earlier version of this engine (before value tables were built lazily) had to widen its up-front reachable-state exploration to anticipate up to `MAX_SHRED_DEPTH + 1` repeated crit-effect applications for a shredding attack, specifically so a stacking effect couldn't reach a `DebuffState` during real chain resolution that never got a value table built for it in advance. Under the current lazy `getValueTableAt` design (see "Avoiding the combinatorial explosion" above) there's nothing to anticipate: however many times the chain actually stacks Ice Cage/"-X ARM" before it terminates, that exact resulting `DebuffState` gets its own table built on first request, same as any other state.

**Forward simulation (`resolveAttackChainForward`) needs the SAME non-exponential shape as `attackChainValue`, achieved differently.** The natural way to write this counterpart - recurse into itself per branch, exactly mirroring `attackChainValue`'s structure - looks correct and IS correct, but is a performance trap: `attackChainValue` avoids blowing up because it's memoized *by value* (a repeated `(depth, state)` key returns instantly), but a forward simulation has no single "value" to memoize - it's accumulating probability *mass* into `stats`/`next` by mutation as it goes, so a naive per-branch recursion re-walks its ~11-way branch at every depth independently, reaching up to `11^MAX_SHRED_DEPTH` calls in the worst case even though the number of *distinct* states involved stays tiny (this was caught empirically during development: a target with `boxes: 1000` - large enough that a Shred chain rarely dies out early - made the calculation hang, while `boxes: 20` finished in under 100ms, because small `boxes` prunes most of the tree via early "destroyed" termination and large `boxes` doesn't). The fix applies the exact same trick the OUTER forward-simulation loop already uses for `dist`/`next` between separate attacks: resolve the chain **one depth level at a time**, merging every state reached at that depth into a single `Map` (keyed by `fwdKey`) before resolving the next instance against it, rather than recursing per branch:

```ts
let current = new Map([[fwdKey(initialState), { state: initialState, probability }]]);
let depthRemaining = MAX_SHRED_DEPTH;
while (current.size > 0) {
  const continuing = new Map();
  for (const { state, probability } of current.values()) {
    // resolve one instance from `state`; route each surviving branch into either
    // `continuing` (if it crit-shredded) or `next` (attack k+1 onward), merging
    // probability into an existing entry by `fwdKey` rather than adding a new one
  }
  current = continuing;
  depthRemaining--;
}
```

Two different paths through the chain landing on the same `(boxes, debuffState, focusLeft, furyLeft)` are now resolved together instead of separately, so the cost stays proportional to the number of *distinct* states per depth level (small, same reasoning as `attackChainValue`'s cache) rather than the number of *paths* to reach them (exponential). `stats.hitMass`/`critMass` only accumulate at `depthRemaining === MAX_SHRED_DEPTH` (the very first level) - "Hit"/"Crit" chance are the ORIGINAL roll's own, a single well-defined probability, unlike "Avg damage" (`stats.damageMass`) which stays meaningful summed across however many instances actually fired at every level. In the **Step by step** breakdown (see the functional documentation), this is exactly what surfaces: **Avg damage** for a Critical Shred attack is the whole chain's expected total, but **Hit**/**Crit** stay the first roll's own.

**Rate of Fire (`SequencedAttack.rof`, `AttackRow.rof`) plus `SequencedAttack.attackCount`/`AttackRow.attackCount` ("# Atks") — a KNOWN shot count, not a per-shot coin flip.** Every attack fires `attackCount` shots as a fixed, guaranteed base (1-10, defaults to 1, every attack type) - `rofOutcomes(atk)` starts from `const base = atk.attackCount ?? 1`. On top of that, a RANGED attack with `rof: 'd3' | '2d3'` fires 1-3 (or 2-6) EXTRA independent shots against the target, additively (total shots = `attackCount + extra`, not `attackCount * extra`), the extra count decided by a die roll BEFORE any of this attack's own dice are thrown - `rofOutcomes(atk)` returns that total count's probability distribution (`'d3'`: `base+1`/`base+2`/`base+3` each 1/3; `'2d3'`: `base +` sum of two independent d3 rolls, weighted 1/9, 2/9, 3/9, 2/9, 1/9). `RofValue`'s sentinel "no extra shots" value is `'-'` (renamed from `'1'` once `attackCount` took over owning the guaranteed base - `'1'` no longer described anything once a weapon's own guaranteed count could be anything from 1 to 10). This `attackCount` base requires no changes anywhere else in `sequence/`, or in `odds-calculator.ts`'s `sequencedAttacks` computed (still exactly one `toSequencedAttack(row, ...)` call per row) - `attackCount` flows straight through as one more field on the SAME `SequencedAttack` entry, reusing the multi-shot machinery below entirely unchanged. The key design decision behind that machinery, and the reason it ISN'T built the same way as Critical Shred's per-outcome conditional continuation: because the shot count is rolled **before any dice**, the target already knows the full count K by the time it's deciding whether to spend Focus/Fury on shot *i* - the correct lookahead value for that decision is "K−i more shots of THIS attack, then attacks k+1 onward", conditioned on the ACTUAL (already-known) K, not a blended average over an unresolved future. A memoryless "continue with some fixed probability after each shot" reformulation would give the same MARGINAL destroy chance/expected damage, but would silently make the target's Focus/Fury policy suboptimal (it would hedge against an unknown future that, in reality, was never uncertain in the first place) - so the implementation keeps K's branches genuinely discrete:

- **Backward pass (`buildShotsValue`)**: returns a `shotsValue(shotsRemaining, debuffState, boxes, focusLeft, furyLeft, ...)` function, one memoized cache PER remaining-shot-count level (`cachesByShotsRemaining[shotsRemaining]`, shared across the whole grid/every debuffState for that level - same reasoning as `attackChainValue`'s own per-attack `shredCache`). `shotsValue(0, ...)` is exactly `getNextTable` (attacks k+1 onward - the lazy `getValueTableAt[k+1]` accessor, what `valueAt` used to be inline before laziness); `shotsValue(s, ...)` for `s > 0` is `attackChainValue(..., outerValueAt: (b,d,f,fu,...) => shotsValue(s-1,d,b,f,fu,...), ...)` - i.e. "resolve one more shot (itself already Shred-aware), then whatever `s-1` more shots plus the rest of the sequence is worth". `getValueTableAt[k]`'s own build step (see "Avoiding the combinatorial explosion" above) constructs a table by averaging `shotsValue(count, ...)` over `rofOutcomes(atk)`. For a non-ROF attack (`rofOutcomes` returns a single `{count:1, probability:1}`), this collapses to EXACTLY the pre-ROF computation (`shotsValue(1,...)` calling `attackChainValue` with `shotsValue(0,...)` as its continuation, which IS the old inline `valueAt`) - verified by the full pre-existing test suite passing unchanged.
- **Forward simulation (`resolveRofAttackForward`)**: for each possible count K (weighted by `rofOutcomes`), splits the incoming probability mass by that weight, then resolves K sequential `resolveAttackChainForward` calls WITHIN that K-branch - shot *i*'s survivors become shot *i+1*'s starting distribution, and shot *i*'s `outerValueAt` is `shotsValue(K-i, ...)`, reusing the EXACT SAME functions (and their already-warm caches) the backward pass built, so the replayed policy matches what was actually optimized for. A target already destroyed partway through a volley never reaches its later shots (`resolveAttackChainForward` already excludes destroyed mass from what it hands to the next shot), so a later shot's own stats correctly reflect "however many shots actually got to fire".
- **Per-shot reporting (`SequenceStepResult.shots: SequenceShotResult[]`)**: rather than collapsing a whole volley into one row-level `hitChance`/`critChance`/`averageDamage` (the FIRST shot's own chance, plus every shot's damage summed), `resolveRofAttackForward` accumulates a SEPARATE `ShotStats` object (`{ hitMass, critMass, damageMass, occursMass }`) per shot INDEX, shared across every K-branch that reaches that far - at the top of each `shotIndex` iteration, the incoming `current` map's probability is summed into that index's own `occursMass` (the mass that actually attempts the shot) BEFORE `resolveAttackChainForward` adds its `hitMass`/`critMass` (topLevel-only, i.e. the shot's own roll, not a Shred-recursion's) and `damageMass` (every depth, so a Shred chain triggered BY this shot counts as part of its own damage). `resolveAttackChainForward`'s old `trackHitCrit` parameter is gone entirely - every shot now gets its OWN tracked hit/crit (previously only shot 1 did, everything else folded into the row). `computeSequenceOdds`'s main loop then derives each `SequenceShotResult`: `occursChance = occursMass / aliveMass` (aliveMass = mass entering the WEAPON, i.e. the same denominator the old row-level fields used), `hitChance = hitMass / occursMass`, `critChance = critMass / occursMass`, `averageDamage = damageMass / occursMass` - all conditioned on the shot actually firing, not just on the target being alive when the weapon's turn comes up. `odds-calculator.ts`'s `shotRows` computed (mirroring the existing `damageDistributionPoints`/`maxDamageProbability` pattern - derived computeds live in the orchestrator, `DetailsDialog` stays a dumb renderer) flattens every row's `shots[]` into one continuously-numbered list for the Details pop-up, restoring the pre-grouping "one row per attack" numbering. Each `ShotRow` carries `isNewWeapon` (true for that weapon's own first shot) and `isNewAttacker` (a strict subset of `isNewWeapon` - only true when `attackerIndex` also differs from the PREVIOUS weapon's, not `attackerName`, for the same "two unnamed attackers can share a display name" reason `SequencedAttack` itself avoids comparing by name), plus `attackerName`/`typeEmoji` (from `TYPE_EMOJI`, keyed by `step.attack.type`); the template (`details-dialog.html`) renders a group header before every `isNewWeapon` row - the attacker's name only when `isNewAttacker` is also true, the weapon's type icon always - so consecutive weapons owned by the same attacker share one header instead of repeating its name. `.steps__row` itself (`details-dialog.css`) is a CSS Grid (`grid-template-columns: auto repeat(4, 1fr)`) rather than a flex row, with each `.steps__metric` stacked label-above-value (`flex-direction: column`, matching the app's pre-existing `.mini-field` convention) instead of side-by-side - columns shrink together as the viewport narrows, so the row never needs horizontal scrolling to show all four metrics.
- **No precomputed widening needed for a ROF attack independently triggering its `statEffects` once per shot** (up to `maxShots` times), for the same reason Shred needs none (see above) - whatever `DebuffState` a given shot's outcome actually produces, `getValueTableAt` builds a table for it on first request, regardless of how many shots' worth of stacking it took to get there.
- **Composes with Critical Shred for free**: since each ROF shot is resolved via the SAME `attackChainValue`/`resolveAttackChainForward` that already handles a single attack's own Shred chain internally, a ranged attack with both `rof` and `criticalShred` set needs no special-casing - every shot in the volley can independently crit and shred. This is also the combination's main performance risk: `maxShots` (up to 6, for `'2d3'`) multiplies directly against `MAX_SHRED_DEPTH`'s own cost, so `engine.spec.ts`'s composition test deliberately uses a realistic `boxes: 50` (the UI's own 1-99 range) rather than the pure-math ROF tests' `boxes: 1000`, which would otherwise take several seconds for no benefit the test needs.

**Sustained Attack (`SequencedAttack.sustainedAttack: 'hit' | 'crit'`, a hit/crit-pair effect like Armor Piercing/Decapitation - see `HIT_CRIT_PAIR_KEYS`) — a new `sustained: boolean` state dimension threaded through the SAME per-row shot loop ROF/Shred already use, but reset every row instead of persisting.** Once a shot in THIS row's own volley hits (`'hit'`) or specifically crits (`'crit'`), every LATER shot of that same volley auto-hits - never reaching a different weapon row, even one representing the same physical weapon (a deliberately scoped-down version of the tabletop rule, confirmed with the product owner rather than tracking cross-row weapon identity). Mechanically, `sustained` rides the exact same threading `pmMask`/`kotdOffLeft`/`kotdDefLeft` already use - appended to `ExtendedValueLookup`'s signature, `FwdState`'s fields, and every function between `attackChainValue`'s entry and `bestAction` that already threads `k, atk, debuffState` together (`contextFor`, `profileFor`, `damageRerollPopulations`, `resolvePmSplit`, `resolveKotdOffSplit`, `rerollDamageIfAboveAverage`, `resolveOneOutcome`, `profileScore`, `resolveKotdDefChoice`) - but with one deliberate asymmetry from those three: it's **never** added to `ValueTable`/`tableKey`/`getValueTableAt`, which represent "attacks k+1 onward" (a DIFFERENT row) - `sustained` would be actively WRONG to persist there. `contextFor` just ORs it into the SAME `usesAutoHit` boolean `forceAutoHit` already sets (`usesAutoHit = !!atk.forceAutoHit || sustained || ...`), so every existing "auto-hit never crits" / Puppet Master reroll / Knowledge of the Damned reserve-rule behavior applies to a sustained-forced hit for free, with zero new branching anywhere else - the entire feature's real logic lives in ONE line, in `resolveOneOutcome`:
  ```ts
  const outcomeSustained =
    sustained || (atk.sustainedAttack === 'hit' && outcome.isHit) || (atk.sustainedAttack === 'crit' && outcome.isCrit);
  ```
  `outcomeSustained` (not the incoming `sustained`) is what gets passed to BOTH the Critical Shred recursion (so a Shred-triggered follow-up attack inherits a just-turned-on flag too) and `outerValueAt` (the next shot in the volley, or - via `buildShotsValue`'s base case dropping `sustained` entirely when calling `getNextTable` - the next row, always entering fresh). `resolveOneOutcome` now also RETURNS `outcomeSustained`, purely for the forward pass: `resolveAttackChainForward` builds explicit `FwdState` objects (not closures) and sets `sustained: outcomeSustained` on each one, exactly parallel to how it already sets `pmMask: resultingMask`. The other reset point, `resolveRofAttackForward`, explicitly zeroes `sustained: false` on every state it copies from `initialDist` (the PREVIOUS row's own ending distribution) before starting the new row's shot loop - the one place a stale value could otherwise leak forward. `attackChainValue`'s cache key gains one more `|${sustained}` segment - a single boolean at most doubles cache entries, nowhere near Knowledge of the Damned's 11x11 addition. Modeling it as ONE `EffectTrigger`-valued field (not two separate booleans) means the UI gets mutual exclusivity between "triggers on any hit" and "triggers only on a crit" for free, via the same shared-`TriggerEffectRow` mechanism Armor Piercing/Decapitation already use (see `AttackEditDialog` below) - `toSequencedAttack` reads it with `triggerOf(row, 'sustainedAttack')`, not `isEffectOn`. Deliberately left OUT of `rowIsAutoHitGuaranteed`/`isAutoHitGuaranteedForRest`/`remainingMissableRollCount` (Puppet Master's/Offensive Knowledge of the Damned's own "is everything left guaranteed to hit" lookahead): `sustainedAttack` is CONDITIONAL on an earlier shot in the SAME row already qualifying, not a static per-row guarantee the way `forceAutoHit` is, so folding it in would need shot-position-aware reasoning these functions don't have - leaving it out keeps these checks conservatively correct, at the cost of a rare missed optimization, consistent with `remainingMissableRollCount`'s own existing "safe upper bound, not exact" precedent for `maxShots`.

**Multiple targets (`computeMultiTargetSequenceOdds`, `SequenceOptions`, `RowInjection`, `SequencedAttack.eligibleTargetIndices`) — one target's own survival is answerable by running the EXISTING single-target engine unmodified, chained via a "mass enters the fight partway through" mechanism, rather than modeling every target's state jointly (which would blow up the state space combinatorially).** Attacks go against the first target until it's destroyed, then spill onto the next; each target keeps its own fully independent DEF/ARM/boxes/debuffs/Focus/Fury/Knowledge of the Damned/Shield Guards/Scapegoats, since none of that state is ever threaded across targets - a genuinely separate `computeSequenceOdds` call per target, closure and all.

- **`computeSequenceOdds` gained an optional 4th parameter, `options?: SequenceOptions`**: `{ rowActive?: boolean[]; injection?: RowInjection[] }`. `rowActive[k] === false` makes row `k` a pure no-op for THIS call - the forward pass pushes an empty step and leaves `dist` untouched, and the backward induction aliases `getValueTableAt[k] = getValueTableAt[k + 1]` directly rather than building a table nobody needs. `injection` replaces the implicit "100% of the mass starts fresh before row 0" every earlier version of this function had baked in - `dist` now starts genuinely EMPTY, and ALL of a run's mass enters exclusively through `injection`, defaulting to `[{ row: 0, shotsRemaining: 0, probability: 1 }]` when omitted (today's exact single-target behavior). Every existing call site (all of `engine.spec.ts`) omits the 4th argument entirely and is unaffected - verified by the full pre-existing suite passing unchanged before anything new was added on top.
- **`RowInjection` (`{ row, shotsRemaining, probability }`)**: `shotsRemaining === 0` means "enter row `row` completely fresh" - this mass folds into `enteringDist` (merged with whatever survived from earlier rows) BEFORE the row's normal `rofOutcomes` split, so it gets its own freshly-rolled ROF count exactly like row 0 always has. `shotsRemaining > 0` means "resume row `row`'s own weapon with exactly this many shots still unfired" - a FIXED count, deliberately NOT re-rolled: the weapon's total shot count for that volley was already decided (per the Rate of Fire section above, before any of its own dice were thrown), before the target now facing it ever came under fire. Each such entry becomes its own synthetic branch inside `resolveRofAttackForward`, structurally identical to a normal `rofOutcomes` branch except its `current` map starts as a single fresh state (`initialState`) rather than being split off `initialDist`.
- **Shot-level (not just weapon-level) handoff is what this buys**: if shot 2 of a 5-shot ROF weapon destroys the current target, shots 3-5 of that SAME weapon redirect to the next target, matching the tabletop rule precisely - chosen deliberately over the cheaper row-boundary-only alternative (see the functional documentation's "Product choices"). This works with NO change to the backward induction, because `buildShotsValue`'s `shotsValue(s, ...)` already answers "value of `s` more shots of this row's weapon, then rows k+1 onward" for every possible `s` - exactly the value function a resumed volley needs, already built and memoized per row by the Rate of Fire machinery above.
- **`resolveRofAttackForward` now tracks destroyed mass per `shotsRemainingAfter` (`destroyedByShotsRemaining: { mass: number }[]`, sized to the row's own max shot count), not one shared row-level accumulator.** `shotsRemainingAfter = count - shotIndex` is K-INVARIANT (unlike absolute shot position, which different ROF branches reach at different indices for the same remaining count) - exactly the coordinate the next target's own injection needs. `SequenceStepResult.destroyChanceAtThisStep` is now the sum of this array; the array itself is exposed as `SequenceStepResult.destroyChanceByShotsRemaining` for `computeMultiTargetSequenceOdds` to consume directly.
- **Reporting a resumed volley's own shots (`shotStats`, absolute-position-indexed) has no single true absolute position** - a resumed branch's `shotsRemaining` doesn't determine which original ROF branch it came from. `resolveVolley`'s new `reportOffset` parameter (0 for a normal branch; `shotStats.length - shotsRemaining` for an injected one) is a deliberate REPORTING-ONLY approximation ("assume it resumes at the position that leaves exactly this many shots before the row's own maximum count ends") - it never touches `shotsRemainingAfter`/`shotsValue`/`destroyedByShotsRemaining`, which stay exact regardless; it only decides which `shots[]` row the Details pop-up shows a resumed shot's stats in.
- **`computeMultiTargetSequenceOdds(attacks, targets, onProgress?)`** runs each target sequentially: `rowActive[k] = !atk.eligibleTargetIndices || atk.eligibleTargetIndices.includes(targetIndex)` (weapon range, index-based like `attackerIndex` for the same collision-safety reason). A single evolving `available: RowInjection[]` schedule threads across the whole loop (starts as `[{ row: 0, shotsRemaining: 0, probability: 1 }]`, today's exact single-target starting condition). Each target splits it into `ownInjection` (entries on rows it's eligible for - fed to its own `computeSequenceOdds` call) and `passthrough` (entries on rows it ISN'T eligible for - carried forward UNCHANGED into the next target's own `available`, rather than dropped: **a redirect landing on a weapon out of range for the current target now keeps searching further down the target list for one it CAN reach, instead of fizzling** - a real bug in an earlier version of this function, not a deliberate simplification). On top of that, `ownInjection` gets topped up to a full, unconditional 1 at this target's own FIRST eligible row if no earlier-ranked target is ALSO eligible there (`hasEarlierRivalAtFirstRow`) - `available` only ever holds entries something upstream explicitly produced, so a row nothing earlier ever touched (because nothing earlier could) has no entry to pass through at all; without this, a target scoped to a fully disjoint set of weapons from every earlier target would see 0% there instead of the guaranteed 100% it's actually entitled to (see the module doc comment's "Multiple targets" section for the full reasoning, including the narrower known limitation this leaves for a target with BOTH an unrivaled row AND a later row it genuinely shares with an earlier target). One off-by-one subtlety in building the next target's own `available`: `shotsRemaining === 0` (died on row `k`'s own LAST shot - that row's whole volley is already spent) injects the next target at row `k + 1`, not `k` again; `shotsRemaining > 0` (still owes shots) injects at row `k` itself (a genuine mid-volley resume). Returns `TargetSequenceResult[]` (`{ result: SequenceResult; engagementChance: number }[]`) - `engagementChance` is `ownInjection`'s own probability sum: 1 for the first target and for any later target with no earlier-ranked co-eligible target, less than 1 only when it genuinely depends on an earlier, shared-eligibility target's own fate. Cost is linear in target count: each target's own run is the same complexity class as today's single-target computation, since the backward induction (the expensive part) is completely unchanged - only the forward pass gets a constant-factor more bookkeeping (tracking two accumulator shapes instead of one, resolving the occasional extra synthetic branch).
- **`OddsCalculator`'s own damage-distribution/average-damage computeds correct for mass a target's `result` never accounted for at all** (an earlier target survived entirely, or - per the fizzle rule above - a redirect landed on an out-of-range weapon): `rawDamageDistributionByTarget` folds `1 - (finalDestroyChance + survivalDistribution's own sum)` into a "0 damage" bucket, since that mass took no damage and kept full boxes, rather than letting `expectedBoxesRemaining`'s naive `[...dist.values()].reduce(...)` silently omit it (an EMPTY `dist` sums to 0, not `boxesInitial`, which would otherwise make a barely-engaged target's own average damage read as unrealistically high - caught during manual browser verification of this feature, not by `engine.spec.ts`, since it's a presentation-layer correction over an internally-consistent engine result, not an engine bug).

**Puppet Master (`SequencedAttack.attackerIndex`/`hasPuppetMaster`) — a fixed forward rule, deliberately NOT optimized.** Every other attacker-side resource in this file (there isn't one, until this) would naturally invite the SAME "spend optimally" treatment Focus/Fury already gets - but doing that here would let the app claim a higher destroy chance than a real player could actually achieve, since an omniscient-optimal spend requires knowing in advance which future roll will turn out to be the best one to save the token for. So Puppet Master follows a fixed, mechanical, no-lookahead rule instead (`resolvePmSplit`, walking this attacker's own rolls in order): reroll the first missed attack roll; once every remaining attack of this attacker's is already guaranteed to auto-hit (or it's down to the very last attack), reroll a below-average damage roll instead; otherwise the token can go entirely unused. This makes it the SHAPE of a Focus/Fury-style resource (still needs to be threaded through the same backward/forward machinery, since a LATER roll's own profile depends on whether the token was already spent) without any of the optimization machinery - no `bestAction`-style candidate comparison, no argmin.

- **`pmMask`**: one bit per DISTINCT `attackerIndex` with `hasPuppetMaster` set (`pmBitOf`, `maxPmMask = 1 << pmAttackerIndices.length`) - a small, densely-enumerated resource dimension exactly like `focusLeft`/`furyLeft`, NOT a sparse reachability-pruned one like `DebuffState`. Folded into the SAME `Map<string, ValueTable>` key `DebuffState` already uses (`tableKey`) rather than adding a 4th array axis to `ValueTable` itself - `ValueTable`/`buildValueTable`/`readValueTable`/`bestAction`/`ResourceBranch`/`ValueLookup` all stay completely unchanged; a new `ExtendedValueLookup` type (see "Knowledge of the Damned" below) is used only ABOVE that level (`attackChainValue`/`resolveAttackChainForward`/`buildShotsValue`), since `pmMask` only ever changes once, atomically, before a roll's own outcomes are even enumerated. With no attacker running Puppet Master, `maxPmMask === 1` (only mask 0 ever exists) and every new code path below degenerates to exactly the pre-existing behavior - verified directly by a regression test comparing against a run with the fields omitted entirely.
- **`resolvePmSplit(k, atk, debuffState, pmMask, trueOriginal)`** returns every sub-population that GENUINELY happens when resolving attack `k` (never a competing choice, unlike `bestAction`) - e.g. "hit normally, mask unchanged" (mass = `trueOriginal.hitChance`) plus "missed, mask now spent" (mass = `trueOriginal.missChance`), each already pre-scaled to its own share and handed straight to `attackChainValue`/`resolveAttackChainForward`'s existing per-outcome loop (now nested one level deeper: for each population, for each of ITS outcomes). A "reroll" is mathematically just an i.i.d. redraw from the SAME pool the original roll came from, so the "now spent" population's own outcome distribution is simply `trueOriginal` again (scaled down to `missChance`'s share) - `resolvePmSplit` never needs to build a genuinely new "rerolled" profile for the miss case. `trueOriginal` (`profileFor(k, atk, debuffState)`) is computed ONCE by the caller and shared with every later stage - see "Knowledge of the Damned" below for why this needs to be an explicit parameter now rather than computed internally, as it originally was.
- **Below-average damage checks** (`damageRerollPopulations`, shared with Offensive Knowledge of the Damned below - was `damageCheckPopulations`, Puppet-Master-only, before that generalization) need real access to the raw dice-pool split (not just `AttackProfile`'s already-collapsed final-damage maps, which can merge multiple different raw dice sums - some below average, some not - into the same final-damage bucket after the `max(0, sum+pow-arm)` floor). `attack-model.ts` gained `damagePoolFor` (refactored out of `buildAttackProfile`'s old private `buildDamagePool` closure, now shared) and `splitAttackDamageByAverage(damage, effects, target, variant, direction)` (renamed/generalized from the Puppet-Master-only `splitAttackDamageForPuppetMaster` once Defensive Knowledge of the Damned needed the OPPOSITE direction too - see below), returning `{ kept: Map<number,number>; rerollMass: number }` for either the non-crit or crit damage roll - mirroring `buildAttackProfile`'s own ARM/Brutal-Damage/Decapitation resolution exactly (via a shared `resolveArm` helper), just reporting the split instead of blending it into one map. No changes needed to `dice-pool.ts` - both functions are built entirely from primitives already imported there.
- **`isAutoHitGuaranteedForRest(k, atk, debuffState)`/`isLastAttackOfAttacker(k, atk)`** are the "has nothing left to wait for" gate on the damage-roll fallback. Both are pure, no-lookahead functions: `isLastAttackOfAttacker` is static (precomputed once, `pmAttackIndicesByAttacker`); `isAutoHitGuaranteedForRest` only needs the debuff state AS OF ENTERING `k` (already a fixed, known value at every point this is called from) plus each remaining attack's own static `type`/`forceAutoHit` (via the shared `rowIsAutoHitGuaranteed(atk, debuffState)`, also reused by Offensive Knowledge of the Damned's own reserve-count helper below) - correct without ever inspecting how a later roll actually turns out, because Knocked Down/Stationary never clears once inflicted (see `DebuffState`), so if the target is immobilized now, it stays immobilized for every later attack too.
- **Composes with Critical Shred and Rate of Fire for free, the same way both already compose with each other.** The Shred self-recursion inside `resolvePmSplit`'s callers passes each population's OWN `resultingMask` forward (not the incoming `pmMask`), and `buildShotsValue`/`shotsValue` thread `pmMask` through their own per-shot recursion into `attackChainValue` - so the token is independently re-evaluated at every Shred instance and every ROF shot, not just an attack's first roll, without any extra code beyond adding the `pmMask` parameter everywhere Shred's `depthRemaining`/ROF's `shotsRemaining` already thread through.

**Knowledge of the Damned (`SequenceTarget.offensiveKnowledgeOfTheDamned`/`defensiveKnowledgeOfTheDamned`) - two more reroll pools, both living on the TARGET and shared across every attacker (unlike Puppet Master's per-attacker token).** Offensive Knowledge of the Damned is Puppet Master generalized from "1 token" to "N pooled charges" (`kotdOffLeft`); Defensive Knowledge of the Damned is the genuinely new piece architecturally - the TARGET's own optimal choice (full sequence lookahead, like Focus/Fury) of whether to force a reroll (`kotdDefLeft`).

- **The "two profiles" principle**, the key generalization this whole feature needed: `resolvePmSplit`'s `trueOriginal` parameter exists because, once Offensive/Defensive Knowledge of the Damned sit downstream of Puppet Master, "how much mass is currently in front of this stage, and which portion is eligible for ITS OWN reroll" (`inputProfile`) and "what a fresh reroll actually draws from" (`trueOriginal = profileFor(k, atk, debuffState)`, computed ONCE per roll and shared by every stage) stop being the same thing - true only for Puppet Master, the first stage in the pipeline. Every function below Puppet Master's own level takes both explicitly.
- **`resolveKotdOffSplit(k, atk, debuffState, kotdOffLeft, shotsRemainingThisRow, inputProfile, trueOriginal)`** mirrors `resolvePmSplit`'s own structure (unconditional miss-portion reroll; a damage-roll check via the shared `damageRerollPopulations`), but the damage-roll check's eligibility gate is the "reserve rule" (`damageRerollEligibleForOffKotd`) instead of Puppet Master's own per-attacker `isAutoHitGuaranteedForRest`/`isLastAttackOfAttacker`: eligible only when the charges that would remain AFTERWARD are enough to cover `remainingMissableRollCount` - every remaining roll, system-wide across every attacker, that could still miss. This collapses EXACTLY onto Puppet Master's own rule when `kotdOffLeft` is 1 (the only way `charges - 1 >= remainingCount` can hold with 1 charge is `remainingCount === 0` - Puppet Master's own condition, verified directly by a test asserting the two produce identical results). `remainingMissableRollCount` counts a Rate of Fire row's OWN remaining shots exactly (`shotsRemainingThisRow`, already known once inside that row's own volley - see the Rate of Fire section above, threaded into `attackChainValue`'s signature from `buildShotsValue`'s own `shotsRemaining` parameter) - but a LATER row's own ROF shot count isn't decided yet at evaluation time `k`, so its worst case (`Math.max(...rofOutcomes(row).map(o => o.count))`) is used as a safe upper bound rather than an exact count. A Critical-Shred-active row is deliberately NOT expanded into multiple units, matching `isAutoHitGuaranteedForRest`'s own row-level treatment exactly (both iterate `attacks`, never a chain's own instance count).
- **`normalizeMap`** fixes a subtlety the original Puppet-Master-only code got away without: `splitAttackDamageByAverage`'s own `kept` map deliberately sums to `1 - rerollMass` (a filtered SUBSET of the full dice pool, each entry keeping its own original probability) rather than 1 - safe to pair with an UNREDUCED `hitNonCritChance`/`hitCritChance` scalar ONLY as long as the resulting population is consumed directly by `applyProfile` (which just multiplies scalar × map-entry and doesn't care whether the map itself sums to 1) and never treated as a properly-normalized `AttackProfile` by anything downstream. Defensive Knowledge of the Damned's `rerollDamageIfAboveAverage` (below) does exactly that - via `mergeWeighted`, which assumes its OWN input map sums to 1 - so `damageRerollPopulations`'s "kept" population now runs its map through `normalizeMap` (dividing every entry by `1 - rerollMass`) with `hitNonCritChance`/`hitCritChance` correspondingly REDUCED to the true absolute mass, keeping every profile in the pipeline honoring the normal `AttackProfile` contract (scalar × 1-summing map = absolute mass) throughout, not just in the cases Puppet Master alone ever exercised. The per-value absolute masses `applyProfile` computes are bit-identical before and after this change - a representation fix, not a behavior change (Puppet Master's own existing tests confirm this).
- **`resolveKotdDefChoice(k, atk, debuffState, kotdDefLeft, inputProfile, trueOriginal, ...)`** is the architecturally new piece: a genuine 3-way comparison (don't spend / `rerollAttackRollIfHit` / `rerollDamageIfAboveAverage`) via `profileScore`, a new helper that aggregates `bestAction`'s own `outcomeScore`/`isBetterScore` lexicographic comparison ACROSS EVERY outcome a candidate profile can produce (reusing `resolveOneOutcome`, extracted from `attackChainValue`'s own per-outcome loop body specifically so Critical Shred's recursive continuation logic is never duplicated - the single biggest correctness risk in this feature) - unlike `bestAction`, which only ever scores a single already-REALIZED outcome, since Focus/Fury only ever transform a post-hoc damage NUMBER, never the underlying dice the way a reroll must. `rerollAttackRollIfHit`/`rerollDamageIfAboveAverage` are the mirror image of Puppet Master/Offensive Knowledge of the Damned's own reroll-if-bad-for-the-attacker math, flipped to reroll-if-GOOD-for-the-attacker (i.e. bad for the target) instead - `rerollAttackRollIfHit` is pure arithmetic on `AttackProfile`'s three chance scalars (hit/crit/miss are exact aggregates, not lossy post-ARM buckets, so no `attack-model.ts` helper is needed there the way the damage-roll candidate needs `splitAttackDamageByAverage(..., 'rerollAboveAverage')`).
- **Composition order, inside `attackChainValue`**: the row's own `reroll` toggle (baked in by `buildAttackProfile`/`profileFor` already) -> Puppet Master (`resolvePmSplit`, per-attacker, fixed, sums populations) -> Offensive Knowledge of the Damned (`resolveKotdOffSplit`, global, fixed, sums populations) -> Defensive Knowledge of the Damned (`resolveKotdDefChoice`, global, optimal, picks ONE candidate - run once per Puppet-Master-population × Offensive-Knowledge-of-the-Damned-population, since its optimal choice can legitimately differ per resulting resource combination). Each stage consumes the PREVIOUS stage's output profile as its own `inputProfile`, all three sharing the same `trueOriginal` - this strictly sequential composition is what makes "a roll can be rerolled once by each rule, but by both an attacker-side rule (the row's own Reroll, Puppet Master, or Offensive Knowledge of the Damned) AND the target's own Defensive Knowledge of the Damned" hold, without any special-casing anywhere.
- **`kotdOffLeft`/`kotdDefLeft`** thread through the exact same grid `pmMask` already occupies - `tableKey` (now 4-argument: `debuffState, pmMask, kotdOffLeft, kotdDefLeft`), the renamed `ExtendedValueLookup` type (was `MaskedValueLookup`, now 7-argument), `FwdState`/`fwdKey` - `bestAction`/`ValueTable`/`ValueLookup`/`ResourceBranch` stay entirely unaware either exists, for the same reason they stay unaware of `pmMask`.
- **Performance**: `focusLeft × furyLeft × pmMask × kotdOffLeft × kotdDefLeft` is a genuine multiplicative state-space cost once several of these are configured with large point totals at once - an early version of this feature built a full `ValueTable` for every combination of that whole grid, at every step, for every reachable debuff state, regardless of whether the computation could ever actually reach it (a 3-attack sequence with Puppet Master + Critical Shred + Rate of Fire + Focus/Fury(1/1) + BOTH Knowledge of the Damned counters at their full 10-charge cap took well over a minute that way). **Lazy value tables** (`getValueTableAt`, replacing the old eager `valueTables` array of fully-populated `Map`s) fixed most of that: each step's accessor is a memoized closure that builds a `ValueTable` for a given `(debuffState, pmMask, kotdOffLeft, kotdDefLeft)` tuple the FIRST time it's actually asked for, not upfront - a short sequence can never spend anywhere near 10 charges, so most of the configured range is simply never built. This also made the dedicated `computeReachableDebuffStates`/`attackTransitionCandidates` precomputation pass (which used to enumerate every reachable `DebuffState` up front, purely so the eager loop knew what to build tables for) entirely redundant - removed outright, since the lazy cache now only ever contains entries for states some real branch of the computation genuinely produced, which is automatically exactly the reachable set, without a separate exploration pass over-approximating it first. The same worst-case scenario above dropped from well over a minute to about 14 seconds - still a real cost at the full 10/10 cap on a busy sequence (unlike `pmMask`'s `MAX_PM_ATTACKERS` guard, the `MAX_RESOURCE_POINTS` cap of 10 is a direct, intentional part of this feature's own spec, not tightened further), but no longer paying for combinations that were never reachable in the first place. `engine.spec.ts`'s own mass-conservation test for this feature still deliberately uses modest (1 each) charge counts, favoring breadth of simultaneously-active mechanics over maximum point totals in what's meant to be a fast unit test.

**Attacker Focus (`Attacker.focusPoints`/`SequencedAttack.attackerFocus`) - the offensive mirror of the target's own Focus/Fury, spent optimally (full-sequence backward induction, like Focus/Fury/Defensive Knowledge of the Damned) rather than the fixed no-lookahead rule Puppet Master/Offensive Knowledge of the Damned use.** Unlike those two, a real player genuinely CAN see the whole board when deciding how to spend their own model's Focus (the same "not pretending to know more than a real player would" argument that put Defensive KotD on the optimal side of that split - see above), so this is deliberately the more expensive, higher-fidelity treatment. Per attacker, 0-10 points, spent over the WHOLE sequence (every target, not reset per target - see "Cross-target persistence" below) on any of three actions: boost an attack roll (+1 die), boost a damage roll (+1 die), or buy an extra melee attack fired after that attacker's own configured attacks.

- **`MAX_SEQUENCE_COMPLEXITY = 100000` (`constants.ts`) is now a purely ADVISORY threshold - `sequence.ts` itself never rejects a configuration for being "too complex" at all.** A user-reported bug: three attackers with Attacker Focus active (only 2 supported by the old flat `MAX_FOCUS_ATTACKERS` cap) silently broke the computation - the worker threw near-instantly, well under `SHOW_CALCULATING_DELAY_MS`, and `OddsEngine` only `console.error`'d it, leaving the UI looking frozen with the last successful result stuck on screen (fixed alongside this - see `OddsEngine.error` below). Investigating further, the user pointed out the cap's own SHAPE was wrong: attacker COUNT was the wrong proxy for cost - 3 attackers with 2 Focus each (`3^3 = 27` reachable combos) is cheaper than 2 attackers with 10 Focus each (`11^2 = 121`), yet the old cap forbade the first and allowed the second. A first fix replaced the flat count cap with a computed estimate over every dimension that actually drives cost (`estimateSequenceComplexity`, below) checked against a threshold - still a hard reject, just a smarter-shaped one. After more testing, the user pushed further: they didn't want a hard cap AT ALL, even a well-shaped one - their own device could handle configs well past what felt "safe" to guess at in advance, and no fixed number can know that ahead of time. **The final design has NO reject path for complexity, at any magnitude** - the computation always runs; `estimateSequenceComplexity`'s only remaining job is deciding whether to show a "this might take a long time" heads-up (`OddsEngine.slow`, below), leaving the actual judgment call (wait it out, Cancel, or change the inputs) to the player.
  - **`estimateSequenceComplexity(attacks, target)` (single-target.ts, re-exported from `sequence.ts`)** computes `(boxes+1) x (targetFocus+1) x (targetFury+1) x (shieldGuards+1) x (scapegoats+1) x (kotdOff+1) x (kotdDef+1) x 2^pmAttackerCount x` (per focus-enabled attacker) `(focus+1) x` (per finite-Reload weapon) `(reloadCap+1)` - every one of these dimensions is folded into the SAME `tableKey`/`ValueTable` Map key (or multiplies a table's own dense array size the way `boxes` does), so their product is a reasonable, monotonic proxy for how many value tables the lazy backward induction ends up building. Exported specifically so `OddsEngine` can call it on the MAIN thread, synchronously, before the Worker is even spun up - a cheap O(1) multiplication, unlike the computation it's estimating the cost of, so the "might take a long time" hint is available from the very first render of the "Calculating" overlay rather than needing to wait and see.
  - **Calibration history** (three rounds of real testing on the SAME scenario that prompted this - boxes=57, three attackers): threshold 5000 - Focus `[3,1,1]` (estimate 928) "slow but tolerable" (~86s), Focus `[3,6,6]` (estimate 11368) still hadn't finished after 2+ minutes; raised to 10000 - Focus `[3,6,5]` (estimate 9744) completed in ~4s (comfortably tolerable, not just "allowed"); raised further to 100000 once the user decided even 10000 was needlessly conservative, without a matching measured data point at THIS specific magnitude - by this point the number is a coarse "worth a heads-up" line, not a tuned boundary. **Explicitly NOT a wall-clock predictor even where it WAS calibrated**: a synthetic repro of the `[3,1,1]` scenario completed in under a second when built with default (2-dice) damage pools, but ~4.5 minutes once faithfully reproducing the original bug report's actual weapon (one 6-damage-dice attack) - a large dice pool (a per-table CONSTANT-factor cost this estimate doesn't model at all, and doesn't need to: it's already bounded by its own separate, unrelated cap in `dice-pool.ts`) can move the real runtime independently of the state-space product this estimate DOES track, by more than an order of magnitude (the repro's own measured time didn't match the user's reported ~86s either). This is exactly why `OddsEngine.cancel()`/Retry exist alongside `slow` rather than the estimate trying to be more precise: the number is a rough proxy for ONE cost dimension, not a promise about actual runtime.
- **`SequenceContext` gains `focusIndexOf: Map<number, number>`** (attacker index -> slot in an `attackerFocusLeft: number[]` vector, mirrors `pmBitOf`) and an **unconditional** `attackIndicesByAttacker: Map<number, number[]>` - every attacker's own row indices, NOT Puppet-Master-gated like `pmAttackIndicesByAttacker`, and critically **filtered by `rowActive`**: a row inactive for the CURRENT target (because it's scoped to a different target's own weapon via `eligibleTargetIndices`) must not be mistaken for this attacker's own last active row - omitting that filter was a real bug caught during development (see "Bugs found" below), not a hypothetical edge case.
- **Boost attack roll is the OUTERMOST decision, unlike every other stage in this file.** Every other per-roll choice (PM, both Knowledge of the Damned counters, Defensive's reroll) operates on `trueOriginal` AFTER it's already built - but boosting the attack roll changes what `trueOriginal` itself is, since a downstream reroll (PM/KotD) must redraw from the BOOSTED pool, not the unboosted one. So `chooseAttackerAttackBoost` builds BOTH the unboosted and boosted `trueOriginal` (`profileFor` gains an `attackBoosted: boolean` param - and the profile cache key gains an `attackBoosted` segment, the sharpest correctness trap in this feature: omitting it silently returns the wrong cached profile for the other boost state) and runs EACH all the way through the rest of the pipeline (PM split -> KotD-off split -> damage-boost split (below) -> KotD-def choice -> outcome resolution) via `pipelineScore` (the same full-pipeline body `attackChainValue`'s per-outcome loop already runs, extracted so it can be run twice for comparison instead of once), picking the better whole-pipeline outcome via `isBetterForAttacker` - the exact mirror of `bestAction`'s own `isBetterScore`, but every comparison direction flipped (the attacker wants the target's survival value LOWER, not higher). `attackChainValue` itself becomes a thin memoizing wrapper around this.
- **Boost damage roll is a MID-PIPELINE population split, like `resolvePmSplit`, not a whole-profile candidate.** By the time damage-roll boosting is decided, the attacker already knows crit-vs-non-crit (unlike attack-roll boosting, which must decide before the roll happens at all) - so `resolveAttackerDamageBoostChoice` splits the input profile into miss/non-crit-hit/crit-hit populations (mirroring `resolvePmSplit`'s own population-splitting shape) and lets EACH flavor independently choose boost-or-not via `profileScore`/`isBetterForAttacker` - a crit's damage roll and a near-certain non-crit hit's damage roll can rationally get different answers even within the same overall roll. `attack-model.ts` gained `boostedDamageMap(damage, effects, target, variant)`, mirroring `buildAttackProfile`'s own non-crit/crit damage derivation (ARM halving, Brutal Damage, Decapitation) with `+1 boostDice`, returning just the one damage map since the attack-roll chances are already fixed by this point in the pipeline. Sits between `resolveKotdOffSplit` and `resolveKotdDefChoice` in the existing composition order.
- **Buying an extra attack is a boundary-triggered VALUE LADDER, shaped exactly like `buildShotsValue`'s own ROF ladder, not a `bestAction`-style single-outcome candidate.** Offered only at the row where `isLastAttackOfAttackerForFocus(ctx, k, atk)` (built on the unconditional `attackIndicesByAttacker` above) - i.e. only after every one of this attacker's own configured attacks have already fired, per the feature's own spec. `buildBoughtAttacksValue(attackerIndex, getNextTable)` returns `{ valueAt, stopValueAt }`: `stopValueAt` is a plain read-through of the ORIGINAL, unwrapped `getNextTable` (attacks after this attacker's own last row); `valueAt` is the full recursive ladder - for each Focus level, compares `stopValueAt` (genuinely stop buying) against firing one more melee attack (via `attackChainValue`, full pipeline, target's own Tough/Rapid Healing/Focus-Fury/Shield Guard/Critical Shred/Sustained Attack all apply normally, since a bought attack is a genuine attack) for EVERY melee weapon this attacker owns, with `outerValueAt` wrapping `valueAt(focusLeft - 1)` so a bought attack can itself recurse into buying further attacks - picking the attacker-best (minimum survival value) via plain `<`, not `isBetterForAttacker`'s lexicographic triple (this compares whole downstream expected-values, already-scalar `attackChainValue` results, not single-outcome branches, so the triple's tie-break semantics don't apply). Hooked into the backward loop by wrapping `getValueTableAt[k+1]` with `buildBoughtAttacksValue(...).valueAt` before it reaches `buildShotsValue(k, atk, wrapped)` - every OTHER row's own lookahead still passes `getValueTableAt[k+1]` straight through unwrapped, so a buy decision stays invisible to a different attacker's rows and to this attacker's own non-last rows. `resolveBoughtAttacksForward` is the forward-pass mirror, replaying the exact weapon-choice policy the backward pass computed.
  - **The `stopValueAt`/`valueAt` split exists to fix a real bug, not preemptively.** An earlier version compared "stop" against `valueAt` itself (the WRAPPED, recursive ladder) rather than the unwrapped `getNextTable` - i.e. "stop" was being compared against an already-optimal-including-further-buying value, heavily biasing toward never buying and producing NON-MONOTONIC results at certain Focus levels (`f=3` scoring WORSE than `f=2` for the identical scenario). Caught via a monotonicity-sweep regression test in `engine.spec.ts`, which explicitly documents this exact failure mode as what it guards against.
  - **No separate "max bought attacks" cap needed**: buying is already bounded by `focusLeft` itself (≤ `MAX_RESOURCE_POINTS` = 10), so the ladder terminates naturally, the same reasoning `buildShotsValue`'s own ROF ladder already relies on.
  - **Scope cut, flagged deliberately**: a bought attack does NOT participate in this attacker's own Puppet Master reroll or either Knowledge of the Damned counter's "last chance" eligibility rule (`isAutoHitGuaranteedForRest`/`isLastAttackOfAttacker`/the Offensive reserve-count check) - those stay scoped to the attacker's originally-configured rows only, since they already mean "is this the attacker's last roll opportunity", which becomes circular once "how many more attacks will this attacker buy" is itself part of the SAME optimization being solved.
  - **UI/reporting gap, accepted**: `SequenceStepResult`/`SequenceShotResult` have no slot for a bought attack in the row-by-row Details breakdown (a bought attack isn't a configured `SequencedAttack` row) - the math is fully correct end-to-end, bought attacks just aren't individually visible in that one step-by-step view; the Focus strategy summary (below) is where the player learns about buying.
- **Cross-target persistence (`RowInjection.attackerFocusRemaining`, `DestroyedAccumulator`) - the single largest source of new complexity in this feature, and the reason it's threaded separately from Phases 2-3's single-target scope.** Per the feature's own spec, Focus is ONE shared pool for the whole sequence, not reset per target - structurally new, since `RowInjection` (`{row, shotsRemaining, probability}`, see "Multiple targets" above) previously carried mass between targets with no channel for attacker resource state at all.
  - `RowInjection` gains an optional `attackerFocusRemaining?: number[]`; every mass-carrying tuple threaded through `computeMultiTargetSequenceOdds` (`available`, `passthrough`, `ownInjection`, the `nextInjection` built forward) carries this tag now, not just row/shot position. Unset falls back to each attacker's own configured `attackerFocus` (today's default, unaffected - a 0-Focus attacker, or any run before this feature existed, is byte-identical).
  - **`DestroyedAccumulator` (`{ mass: number; byFocus: Map<string, { attackerFocusRemaining: number[]; mass: number }> }`) replaces every bare `{ mass: number }` destroy-mass accumulator** in `single-target.ts`, via `recordDestroyed`/`mergeDestroyed` helpers - needed so `computeMultiTargetSequenceOdds` can hand Focus forward broken down by exactly how much each attacker had left when the target died, not just a lump destroy probability. `SequenceStepResult.destroyMassByShotsRemainingAndFocus` exposes this breakdown (the Focus-aware sibling of the existing `destroyChanceByShotsRemaining`) for the multi-target orchestrator to consume directly.
  - **The "unrivaled row top-up" rescaling bug** (the second of two critical bugs this phase found - see "Bugs found" below): the pre-existing multi-target.ts logic that tops a later target's own first-eligible-row mass up to a full 1.0 (when no earlier target could ever "hold" that row - see "Multiple targets" above) used to REPLACE whatever partial, Focus-tagged mass existed there with one bare untagged `{probability: 1}` entry - silently resetting Focus to its full configured value at essentially every non-first target in the most common multi-target setup (dedicated weapon per target). Fixed to rescale the matching existing entries proportionally to sum to 1 (preserving each entry's own `attackerFocusRemaining`), falling back to the bare untagged entry only when genuinely nothing was tracked at that row at all.
  - **A third bug, found post-release (user-reported): leftover Focus couldn't buy attacks against a later target at all once an attacker had exhausted every configured row against an earlier one.** `RowInjection.row === attacks.length` (`n`, off the end of the shared `attacks` array - what a `shotsRemaining: 0` death on the LAST configured row hands forward) was silently dropped by BOTH sides: `computeSequenceOdds`'s own `injectionsByRow` lookup is only ever read for `k` in `[0, n-1]` (never `n`), and `computeMultiTargetSequenceOdds`'s `rowActive`-based split routed it to `passthrough` (`rowActive[n]` is always `undefined`), where it then perpetually failed `rowActive[inj.row]` for every later target too and was never consumed by anyone. Harmless for a plain (non-Focus) attacker - an exhausted weapon genuinely has nothing left to contribute to a later target regardless - but wrong the moment Focus is involved, since remaining Focus is still spendable via buying even with zero configured rows left. Fixed with two coordinated pieces:
    - `computeSequenceOdds` builds a SEPARATE `terminalBoughtLookups` ladder (one per focus-enabled attacker, chained in ascending attacker-index order, each rooted at the PREVIOUS attacker's own resulting table so two simultaneous focus attackers still compose correctly) rooted at `getValueTableAt[n]` - the true "nothing else happens" terminal, deliberately NOT reusing `boughtAttacksValueAtByAttacker` (rooted at each attacker's OWN last configured row, which can sit strictly before `n` when a later row belongs to a different, non-Focus attacker, and would therefore wrongly assume that row still needs to fire). Any `row: n` injection is converted to a fresh state per `RowInjection.attackerFocusRemaining` (via `freshStateWithFocus`, exactly like a row-0 fresh entry) and run through `resolveBoughtAttacksForward` per attacker after the main backward/forward passes finish; destroyed mass folds into `finalDestroyChance` via a new `SequenceResult.postSequenceBuyingDestroyMass` field (not tied to any `SequenceStepResult` - there's no configured row for it to belong to), survivors fold into `dist`/`survivalDistribution` as normal.
    - `computeMultiTargetSequenceOdds` special-cases `row === rowCount` (`attacks.length`) entries explicitly, since `rowActive` has nothing to say about a row index past its own bounds: routed to `ownInjection` (a real potential engagement, via buying) only when the entry actually carries spendable Focus (`attackerFocusRemaining.some(f => f > 0)`); a fragment with nothing left keeps flowing through `passthrough` untouched, preserving the existing (correct) no-Focus behavior exactly. `result.postSequenceBuyingDestroyMass` is read alongside every step's own `destroyMassByShotsRemainingAndFocus` when building `nextInjection`, feeding back in at the SAME `row: rowCount` marker so a THIRD target also gets a shot at whatever Focus is still left after the second.
- **Focus strategy summary (`FocusPolicyLog`/`FocusWeaponTally`/`FocusStrategyEntry`/`summarizeFocusStrategy`) - data-driven summarization of the policy actually computed, not a hand-authored heuristic, broken down by SITUATION, PHASE, WEAPON, and (at the UI layer) TARGET.** Recorded ONLY during the forward replay (never during backward scoring, which evaluates plenty of hypothetical states that never actually happen) at the three decision points above: after `chooseAttackerAttackBoost` (boost detected via `postBoostFocusLeft !== state.attackerFocusLeft` - both functions return the SAME array reference when NOT boosting and a NEW sliced array when boosting, a reference-equality trick that avoids a separate boolean return field), after `resolveAttackerDamageBoostChoice` per population (same reference-equality check, `populationMass = missChance + hitNonCritChance + hitCritChance` for that population), and in `resolveBoughtAttacksForward` right before firing the chosen weapon. Each recording is tagged with a `situation: 'healthy' | 'debuffed'` (`situationOf`), a `weaponLabel` (the row whose own roll is being decided for a boost, or the weapon `resolveBoughtAttacksForward` actually chose to fire for a buy - these can differ, since buying always triggers at the attacker's own LAST configured row but can fire ANY of that attacker's own melee weapons), and the probability mass reaching that decision, tallied per `(attackerIndex, situation, weaponLabel)` into `{ boostAttackMass, boostAttackMassBought, boostDamageMass, boostDamageMassBought, buyMass }`. The `Mass`/`MassBought` split (PHASE) is `resolveAttackChainForward`'s own `isBoughtAttack` param, threaded to `recordFocusPolicy` - `false` at its call site inside the main per-row forward loop, `true` at its call site inside `resolveBoughtAttacksForward` - since that same shared function resolves BOTH a configured row's attack chain and a bought weapon's own attack chain, and a boost decision on either one otherwise lands in the exact same tally with no way to tell them apart. `buyMass` itself needs no phase split - the decision to buy an attack at all is inherently a "bought" concept already.
  - `focusStrategy: FocusStrategyEntry[]` (one entry per attacker, `healthy`/`debuffed` each an ARRAY of `FocusWeaponTally`) is seeded from `focusIndexOf.keys()` (every Focus-enabled attacker), NOT from `focusPolicyLog`'s own entries directly - an attacker whose true-optimal policy legitimately never finds spending worthwhile (e.g. a certain-kill scenario nothing can improve on) would otherwise be silently ABSENT from the array, indistinguishable from "Focus not configured at all". A `SequenceResult.focusStrategy` entry is inherently scoped to the ONE target that `computeSequenceOdds` call is for - `OddsCalculator`'s own `focusStrategyBlocks` computed (see "The UI" below) uses this directly, one full walkthrough per (attacker, target) pair actually engaged, rather than merging every target's own tallies together the way an earlier version did.
  - `summarizeFocusStrategy(entry, targetLabel?)` returns `readonly FocusStrategyItem[]` (`{ kind: 'line'; text }` or `{ kind: 'branch'; condition; lines }`), not a flat string array - the CALLER (`OddsCalculator`'s `focusStrategyBlocks`) spreads the array into its own flat `items: FocusStrategyItem[]` rather than pushing one entry per (attacker, target) pair. Rather than a fixed situation-then-phase cross, `collectInitialAttackLines` walks each weapon's own "initial attack" advice in ROW order (the order `FocusWeaponTally[]` was recorded in) and decides per weapon whether to hoist it as an unconditioned line or defer it into a branch: a weapon ABSENT from one of `entry.healthy`/`entry.debuffed` entirely (not just insignificant there - e.g. an attacker's first weapon can never reach a "debuffed" decision point, since nothing could have knocked the target down before it fires) is always hoisted, since there's no real branch to speak of; a weapon present in both situations hoists only when its healthy and debuffed phrases are IDENTICAL, otherwise its healthy phrase goes into the healthy branch's own line list and its debuffed phrase into the debuffed branch's. The "buying" step stays a single joined phrase per situation (via `summarizePhase`, itself now a thin wrapper around `weaponPhrasesForPhase` - buying happens once, after every configured attack, so there's no per-weapon ordering to preserve the way there is for each weapon's own roll) and is hoisted-or-branched the same way, appended after any per-weapon branch lines already collected. `targetLabel` is a plain string the CALLER builds (e.g. `"Cyrenia"` for a multi-target sequence) folded in as a "vs Cyrenia: " prefix on every unconditioned line's `text` and once per branch's own `condition` (not repeated on every nested line) - the engine itself has no notion of attacker or target display names.
  - **`boostAttackMass`/`boostDamageMass`/`buyMass` (and their `*Bought` counterparts) are NOT a mutually-exclusive partition of one (situation, phase, weapon) bucket's mass, and DIFFERENT weapons' own tallies aren't mutually exclusive either - they're recorded independently at three SEPARATE decision points, and routinely overlap.** A user-reported bug (fixed post-release, part one): an earlier version picked a single "dominant" action per situation (whichever tally was largest, with no weapon dimension at all) and silently dropped the rest - with only a couple of Focus points and one hard-to-hit roll, the true-optimal policy often boosts BOTH the attack roll (to land the hit at all) AND the damage roll (on that same, now-more-likely hit) with its two points, and reporting only the larger of the two tallies described half the real strategy as if it were the whole thing. `weaponPhrasesForPhase` fixes this by computing `SIGNIFICANT_ACTION_RATIO` (0.5) against the strongest mass across EVERY weapon in that bucket (not per weapon - a weapon with only a sliver of genuinely-reachable mass shouldn't get flagged as "significant" purely for being the largest of its OWN small numbers), then returns every weapon's own phrase (via `phraseForWeapon`) once it clears that threshold, ordered the way the pipeline itself decides actions (attack-roll boost, outermost, first; damage-roll boost, mid-pipeline, second; buy, only after every configured attack, last) and the way weapons appear in `FocusWeaponTally[]` otherwise. `joinPhrases` (used by `summarizePhase` for the single-step "buying" phrase, and directly inside `phraseForWeapon` for one weapon's own multi-action phrase) renders one, two, or more simultaneous phrases into a single natural sentence (e.g. "boost Ranged's attack rolls, boost Melee1's attack and damage rolls, and buy extra attacks with Melee1"). `phraseForWeapon` puts the `buy` clause FIRST when combined with a boost clause (buying is the decision that triggers the roll being boosted) and, for `phase === 'initial'`, prefixes "initial " and drops to singular "roll" when only one of attack/damage is boosted (there's exactly one such roll - the weapon's own single configured attack); `'bought'` stays plural and never says "initial", since a bought weapon can fire more than once.
  - **`FocusPolicyLog.debuffCausesByAttacker: Map<number, Set<'knockedDown' | 'stationary'>>`** - a side-table alongside `byAttackerAndSituation`, populated inside `recordFocusPolicy` (via `debuffCausesOf(debuffState)`) whenever a recording lands in the `'debuffed'` bucket, tracking which of Knocked Down/Stationary ACTUALLY occurred for that attacker across every decision point, not just that "some" debuff did. Flows into `FocusStrategyEntry.debuffCauses` (set only when the debuffed bucket has real data) and `summarizeFocusStrategy`'s `debuffConditionLabel` reads it to label a branch "If Knocked Down" / "If Stationary" / "If Knocked Down or Stationary" (only when BOTH are genuinely reachable causes for this specific attacker) instead of always defaulting to the coarse either-or phrasing `situationOf` itself uses internally - a user-reported clarity gap: the label used to say "Knocked Down or Stationary" even for a weapon whose only possible trigger was Knockdown.
  - **A second user-reported bug (fixed alongside the first): the summary named no weapon or target at all**, merging every target's own tallies together into one generic sentence per attacker (e.g. "boost attack rolls and buy extra attacks") even when the true-optimal policy did genuinely different things against genuinely different targets (a real game scenario: boost a single ranged attack's own roll against a fragile 1-box solo since there's only one shot at it, then buy extra melee attacks against a much tankier second target) - the merge silently discarded exactly the nuance a player would want to act on. Fixed by threading `weaponLabel` through `recordFocusPolicy`/`FocusPolicyTally`/`FocusWeaponTally` as described above (the weapon half), and, at the UI layer, no longer merging `focusStrategy` across targets at all (the target half - see "Multiple targets" below).
  - **A third user-reported bug: a near-noise action from a near-empty phase got promoted to equal billing with a genuinely dominant action from the OTHER phase.** `SIGNIFICANT_ACTION_RATIO`'s 50%-of-the-bucket's-own-strongest-mass threshold (see above) is only ever compared within ONE phase (`'initial'` or `'bought'`) at a time by design - the two phases have structurally different "opportunity budgets" (an initial-attack boost decision is capped at mass 1, one roll decided once; buying/boosting bought rolls can accumulate mass well past 1 across several bought attacks), so comparing them against each other directly was tried and reverted after it silently dropped legitimate advice whenever one phase's mass was just structurally smaller than the other's. But a purely-within-phase, purely-relative comparison has its own gap: an attacker whose MAT/RAT already guarantees a hit on every configured weapon has essentially NOTHING worth boosting during "initial attacks" (every weapon's own mass there is at or near 0) - the largest of those near-0 numbers still trivially "wins" its own phase (there's nothing else to compare it against) and gets phrased with exactly the same confidence as "buy attacks with the strongest weapon" in the OTHER phase, whose own mass - spent from the very same attacker's Focus pool - can be 1-2 orders of magnitude larger. Fixed with `PHASE_WORTH_MENTIONING_FLOOR` (0.05): a phase's own local strongest mass must ALSO clear this small absolute floor before anything in that phase is considered "significant" at all, regardless of how it compares to its own (possibly also near-zero) siblings - low enough to only ever catch genuine noise (a couple of percent or less), since a `debuffed` situation in particular can legitimately have a real, low-double-digit-percent mass overall (capped by how often the debuff is even reached at all, not by how good the advice is once there).
- **Bugs found during development, beyond the two already described above (`attackIndicesByAttacker` row-filtering, "unrivaled row top-up" rescaling):** both were caught specifically because they'd have silently broken the "one shared pool for the whole sequence" behavior in the MOST COMMON multi-target configuration (dedicated weapon per target), not an obscure edge case - found via `engine.spec.ts` regression coverage (a `hardTarget→hardTarget` vs `easyTarget→hardTarget` comparison whose results were identical until the top-up fix landed) rather than assumed correct from code review alone.
- **Individually-unrealistic-value guard**: `attackerFocus` is capped at `MAX_RESOURCE_POINTS` (10, same cap as target Focus/Fury) at the UI layer (`ATTACKER_FOCUS_OPTIONS`) and re-checked in `computeSequenceOdds`. The COMBINED complexity of every focus-enabled attacker's own points (alongside every other state-space dimension) no longer gates anything at all - see `MAX_SEQUENCE_COMPLEXITY`'s own doc comment above for why a flat per-attacker-count cap used to live here, why it was replaced by a smarter-shaped complexity check, and why THAT was ultimately removed as a reject path entirely too, becoming the purely advisory `OddsEngine.slow` instead.
- **Reload (`SequencedAttack.reload`) extends buying to ranged weapons, gated by a per-weapon cap layered on top of the SAME shared Focus spend - not a second resource pool.** A ranged weapon with `reload: 1 | 2` can be bought that many times total across the whole sequence (shared across targets, exactly like Focus itself); `reload: Infinity` behaves exactly like melee (unlimited, no cap at all); `reload: 0`/unset (the default) stays exactly as un-buyable as before this feature. Set via a `ToggleSelect` in the Effects pop-up's "General" section, shown only when the row's Type is Ranged (options `[0, 1, 2, Infinity]`, rendered as `'∞'` via a custom `formatValue`; `Infinity` round-trips through the native `<select>` correctly since `toNumber` is a bare `Number(raw)` and `Number('Infinity') === Infinity`).

Widening the vector therefore makes every cache key, every cross-target carry, and the downstream-value probe Reload-aware for free, with changes needed at only two sites: the ctx-construction block (seeds `reloadWeaponIndices`/allocates slots/appends each weapon's initial Reload value after the Focus values) and `buildBoughtAttacksValue`/`resolveBoughtAttacksForward` themselves (candidate filter widened to admit a ranged row with `reload > 0`; `spentFocusLeft` moved INSIDE the per-weapon loop, since different weapons now decrement different Reload slots, with a `continue` when a finite-Reload weapon's own slot is already at 0).
  - **The one genuine seam this doesn't cover for free: `computeMultiTargetSequenceOdds`'s `hasSpendableFocus`** (routes the `row === rowCount` "leftover Focus" marker between `ownInjection`/`passthrough` - see the third bug above) used to check "is ANY slot in the vector nonzero"; once Reload shares the vector, a fragment with Reload-only-nonzero-but-Focus-all-zero must NOT count as spendable (buying always costs a Focus point - Reload only caps a specific weapon on top of that). Fixed by extracting the existing inline Focus-attacker scan into an exported `focusAttackerIndicesOf(attacks)` (single-target.ts) that `multi-target.ts` calls independently to get `focusSlotCount`, then only checks `attackerFocusRemaining.slice(0, focusSlotCount)`.
  - Each finite-Reload weapon's own cap is one more factor in the SAME `estimateSequenceComplexity` estimate (see above) - a dedicated `MAX_RELOAD_WEAPONS` count-based cap used to live here too, removed for the same "attacker/weapon COUNT is the wrong proxy for cost" reasoning, and no longer gates anything either way (purely advisory now, like the rest of that estimate).
- **"Boosted" (`SequencedAttack.boostedAttack`/`boostedDamage`) - a free, unconditional +1 die on the attack or damage roll that's ALSO ineligible for a further Focus-funded boost on that same roll (a roll can only ever be boosted once).** Implemented as two simple `TriggerEffectKey`s (`'boostedAttack'` in `ATTACK_EFFECT_KEYS`, `'boostedDamage'` in `DAMAGE_EFFECT_KEYS`, attack-row.model.ts - both share the label `'Boosted'`, disambiguated in `effectsSummary` via `SUMMARY_LABEL_OVERRIDES` exactly like the Discard/Reroll attack/damage pairs already are), which needed NO new UI component: the existing `effectsFor(row, keys)` + `<app-toggle-button>` machinery already renders anything added to those arrays. The "+1 die" half is entirely free too: `RollModifiers.boostDice` (attack-model.ts) has no notion of WHY it's whatever value it is - it's already just "dice beyond base 2", populated once at `toSequencedAttack` build time from the UI's own Dice selector (`toBoostDice(row.diceCount())`), so folding `+1` into that SAME expression when the toggle is on (`toBoostDice(row.diceCount()) + (isEffectOn(row, 'boostedAttack') ? 1 : 0)`, same for `damageModifiers`) needs zero engine change - the engine never sees a difference between a player-chosen larger dice pool and a free rule-granted one. The "ineligible for a further Focus boost" half is a ONE-LINE addition to each of exactly two functions in single-target.ts - `chooseAttackerAttackBoost`'s and `resolveAttackerDamageBoostChoice`'s existing eligibility gate (`slot === undefined || attackerFocusLeft[slot] === 0`) becomes `|| atk.boostedAttack`/`|| atk.boostedDamage` - since both are the single choke point for their decision in BOTH the backward scoring pass and the forward replay pass (`resolveAttackChainForward` calls the exact same two functions), no duplicate gating is needed anywhere else. At the time this was written, no `profileCache` key change was needed either, since the cache key in `profileFor` was keyed by row index `k` alone and a row's modifiers were fixed for the whole computation - **no longer true once Charge/Cavalry Charge existed, see below and the bug fix two bullets down.**
- **Charge/Cavalry Charge (`Attacker.charge: 'off' | 'charge' | 'cavalryCharge'`, attacker.model.ts) - an attacker-level, mutually exclusive toggle granting a free boost on the attacker's own genuine FIRST melee attack, and ONLY that one attack.** A single tri-state signal (not two booleans) makes mutual exclusivity automatic - one signal can only ever hold one value, so the dialog's own click handler (`AttackerRulesDialog.toggleCharge`) needs no cross-clearing logic. `odds-calculator.ts`'s `sequencedAttacks` computed resolves "first melee row" once per attacker (`rows.find((r) => r.type() === 'melee')?.id`, mirroring how `attackerDisplayName` is already resolved once per attacker before its own inner row loop) and passes both `attacker.charge()` and `row.id === firstMeleeId` into `toSequencedAttack`, which sets `SequencedAttack.chargeAttackBoost`/`chargeDamageBoost` (`isFirstMeleeAttack && charge === 'cavalryCharge'`/`charge !== 'off'`) - eligibility flags only, deliberately NOT folded into `boostedAttack`/`boostedDamage`/`modifiers.boostDice`/`damageModifiers.boostDice` the way the weapon's own "Boosted" toggle is (see the bug this replaced, next bullet).
- **A user-reported bug: Charge/Cavalry Charge boosted EVERY attack made with the weapon, not just the first.** An earlier version folded the charge boost into `boostedAttack`/`boostedDamage`/`modifiers.boostDice`/`damageModifiers.boostDice` at `toSequencedAttack` build time, exactly like the "Boosted" toggle above - correct for a persistent weapon-level rule, wrong for Charge, which grants a free boost on exactly one attack. Since that SAME `SequencedAttack` object is reused for every shot of a row with `attackCount > 1`, and is the exact object `buildBoughtAttacksValue`/`resolveBoughtAttacksForward` fire again when Focus buys extra attacks with the same weapon, the free die silently applied to all of them. Fixed with `withChargeBoost(atk)` (single-target.ts) - builds a locally-boosted VIEW of `atk` (reusing the existing `boostedAttack`/`boostedDamage` fields so `chooseAttackerAttackBoost`/`resolveAttackerDamageBoostChoice`'s existing "already boosted, don't also spend Focus" gates keep working unchanged, and so it doesn't stack with an already-Boosted weapon) - applied at exactly the two points a row's genuine first shot is resolved: `buildShotsValue`'s `shotsValue(shotsRemaining, ...)` when `shotsRemaining === maxShots` (the backward pass's outermost call for that row), and `resolveRofAttackForward`'s `resolveVolley` when `i === 1 && reportOffset === 0` (the forward pass's genuinely-fresh first shot, never a `partialInjections` mid-volley resume - see that function's own doc comment for why those never represent an untouched first shot). A bought attack always reads `attacks[w]`/`attacks[attackerIndex]` directly, never through `withChargeBoost`, so it automatically stopped inheriting the boost once the baking above was removed - no bought-attack-specific code needed at all. **Required one more fix alongside it**: `profileFor`'s `ctx.profileCache` is one cache shared across the WHOLE computation, keyed by row index `k` on the (previously always true) assumption that `atk`'s own modifiers are fixed for that `k` throughout - no longer true once the SAME row's shot 1 and shot 2+ can pass DIFFERENT `atk` objects, so a later, unboosted shot's query was silently hitting shot 1's own cached (boosted) profile. Fixed by adding `atk.boostedAttack`/`atk.boostedDamage` to the cache key (see `profileFor`'s own doc comment) - a no-op for every row this doesn't affect, since those flags stay constant for the whole computation everywhere else. **A first version of this fix shipped with a known, documented scope cut**: a Critical-Shred bonus attack chained off the charge-boosted first shot (a fresh `attackChainValue`/`resolveAttackChainForward` recursion, previously receiving whichever `atk` reference triggered it) incorrectly inherited the boost too. The user explicitly asked for this to be fixed rather than left as a scope cut ("a critical shred bonus attack shouldn't inherit the charge boost... It is to be treated like a new, separate attack"), so it was: `attackChainValue`, `resolveAttackerAttackBoostChoice`, `chooseAttackerAttackBoost`, `pipelineScore`, `resolveKotdDefChoice`, `resolveAttackerDamageBoostChoice`, `profileScore`, and `resolveOneOutcome` all now thread a SEPARATE `baseAtk` parameter alongside `atk` - always the row's true, never-boosted attack, passed straight through everywhere except `resolveOneOutcome`'s own `shredValueAt` closure, which uses it (not `atk`) for its recursive `attackChainValue` re-entry. The FORWARD pass needed no equivalent parameter threading: `resolveAttackChainForward`'s own Shred handling is an internal `while` loop (not a recursive call), so it was simpler to give it a new `isFirstShot` boolean and have it compute, once per depth iteration, `rollAtk = isFirstShot && topLevel ? withChargeBoost(atk) : atk` - `atk` itself (the function's own parameter) never changes, so a later, Shred-continuation iteration of the SAME loop naturally falls back to the unboosted base on its own.

**Returned result (`SequenceResult`, one per target - see `TargetSequenceResult`/`computeMultiTargetSequenceOdds` above)**:
- `steps[]`: one entry per WEAPON (`SequencedAttack`), each with `shots: SequenceShotResult[]` - one `{ occursChance, hitChance, critChance, averageDamage }` per possible shot index in that weapon's own volley (see the Rate of Fire section above for exactly how these are derived, per shot index, from `ShotStats`) - EMPTY for a no-op row (`SequenceOptions.rowActive[k] === false`, see "Multiple targets" above) - plus `destroyChanceAtThisStep` (probability of destruction *exactly* at this step), `destroyChanceByShotsRemaining` (the same total, bucketed by how many of this row's own shots were still unfired when it happened - see "Multiple targets" above), `cumulativeDestroyChance`, `expectedBoxesRemaining` (**unconditional** expectation of boxes remaining after this attack, a destroyed target counting as 0 - see below). Each shot's `averageDamage` is the **raw** damage from that shot's own roll (dice + POW − ARM), before any Focus/Fury mitigation — a property of the shot itself, not of the target's state at that instant. `destroyChanceAtThisStep`/`cumulativeDestroyChance` are still computed internally but aren't shown anywhere in the UI (see the functional documentation) — `expectedBoxesRemaining`, however, **is** used, via `OddsCalculator`'s own `rawDamageDistributionByTarget`/`averageDamageByTarget` computeds (see "Multiple targets" above for why this moved out of `ResultsPanel` and gained a "never touched this target at all" correction on top of the plain subtraction). The underlying subtraction can still leave a hair of floating-point noise above `boxesInitial` (e.g. `15.000000000000002` when it should be exactly `15`, typically when a resource like Fury makes every hit's damage fully negatable) - `Math.max(0, ...)` guards against the resulting tiny negative (`.toFixed(1)` would otherwise render `-1.78e-15` as `"-0.0"`, keeping the sign even for a value that rounds to zero) - a correctness fix at the display boundary, not a change to the underlying probability math.
- `finalDestroyChance`: total probability of destruction over the whole sequence, out of whatever mass this target's OWN `computeSequenceOdds` call was actually given (see `SequenceOptions.injection` above) - for target 0, or any later target with no earlier-ranked co-eligible target, that's the original 1.0; for a later target that genuinely shares eligibility with an earlier one, it's less than 1.0 whenever that earlier target might survive instead of dying and handing mass onward.
- `survivalDistribution`: distribution of remaining boxes, conditional on the target's survival.
- `focusStrategy: FocusStrategyEntry[]`: one entry per Focus-enabled attacker (see "Attacker Focus" above) - `OddsCalculator` merges this across every target before rendering, since Focus is one pool for the whole sequence rather than a per-target figure like everything else in this list.
- `postSequenceBuyingDestroyMass`: destroy mass from Attacker Focus buying attacks past `row: attacks.length` (see "Attacker Focus" above's third bug) - always empty for a plain single-target call, only ever populated by a multi-target `RowInjection` at that marker.

**Safety guard**: `focusPoints`/`furyPoints` are capped at 10 (`MAX_RESOURCE_POINTS`) — beyond that, `computeSequenceOdds` throws an error rather than building a disproportionately large value table. The UI silently clamps input to this range before calling the engine.

**`SequenceTarget.def: number | 'KD'`.** If `def === 'KD'`, the target starts the whole sequence Knocked Down. This is handled by reusing **exactly** the mechanism already in place for a Knockdown triggered mid-sequence:
- `startsKnockedDown` (boolean, `target.def === 'KD'`) is only used to initialize the very first step's `DebuffState` (both backward and forward) to `{ ...INITIAL_DEBUFFS, knockedDown: true }` instead of `INITIAL_DEBUFFS` - the `isKnockedDownOrStationary` logic (melee only) that decides auto-hit at every step is completely unchanged and doesn't even know whether the target started downed or became so along the way.
- `baseDef` falls back to `DEF_FLOOR` (5, instead of a dummy value that's never read) when `def === 'KD'`, since ranged/magic attacks now genuinely need it for their normal roll against the downed DEF.

**`AttackRow.pow: number | '-'`** (UI component): `'-'` represents an attack that never deals damage (but can still critical hit, a critical effect like Knockdown remaining possible). Translated to `NO_DAMAGE_POW = -9999` before reaching the engine (`resolvePow` in `odds-calculator.ts`) — a POW that negative guarantees `max(0, dice + pow - arm) === 0` regardless of dice or ARM, with no engine change required.

### `odds-engine.ts`/`sequence.worker.ts` — running the calculation off the main thread

`computeSequenceOdds` is a big pure synchronous function, and JS is single-threaded - once Knowledge of the Damned made a slow (multi-second) calculation a real possibility (see `sequence/`'s own "Performance" note above), calling it directly from a `computed()` signal the way earlier versions of this app did would freeze the WHOLE tab for that entire duration: no repaint, no CSS animation, nothing, until it returned. `OddsEngine` now runs it in a Web Worker (`sequence.worker.ts`) instead, so the page stays responsive and a "Calculating..." indicator can actually appear and animate during a slow run.

**`computeSequenceOdds` (`sequence/`) gained an optional third parameter**: `computeSequenceOdds(attacks, target, onProgress?: (fraction: number) => void)`, called once per iteration of the existing forward-simulation loop (`for (let k = 0; k < n; k++)`) as `onProgress?.((k + 1) / n)`. Purely additive - every existing call site (all of `engine.spec.ts`'s tests) keeps calling it with just 2 args, unaffected. This is a coarse, "how many of the sequence's attacks have finished" proxy, not a measure of actual work done: the backward-induction/lazy-value-table-building phase (the expensive part for a resource-heavy sequence) has no natural per-iteration seam to hook into, and tends to do most of its work on the FIRST attack (later ones mostly reuse the now-warm `getValueTableAt` cache - see "Lazy value tables" above) - so the reported percentage can jump unevenly (e.g. straight to 80%, then crawl) rather than climbing smoothly. Accepted as a reasonable approximation over showing no progress at all. `computeMultiTargetSequenceOdds` (see "Multiple targets" above) scales this same fraction across every target's own share of the work (`(targetIndex + fraction) / targets.length`), so progress still advances smoothly across a multi-target computation rather than resetting per target.

**`sequence.worker.ts`** is a thin message-protocol wrapper around `computeMultiTargetSequenceOdds` - safe to bundle standalone into a Worker since the whole `sequence/` → `attack-model.ts` → `dice-pool.ts` import chain has zero Angular/DOM dependencies, and `SequencedAttack`/`SequenceTarget` are plain data (primitives/strings/optional booleans, no functions/Maps/class instances), so they're structured-clone-safe for `postMessage`:
```ts
export type SequenceWorkerResponse =
  | { type: 'progress'; fraction: number }
  | { type: 'result'; results: TargetSequenceResult[] }
  | { type: 'error'; message: string };
```
`addEventListener('message', ...)` receives a `{ type: 'compute', attacks, targets }` request (`targets: SequenceTarget[]`, one per target - see "Multiple targets" above), calls `computeMultiTargetSequenceOdds` with an `onProgress` that posts `progress` messages, then posts a final `result` (or `error`, if it throws - e.g. an out-of-range resource-point count on any target - caught explicitly rather than left as an uncaught worker exception).

Built via the standard `new Worker(new URL('./sequence.worker', import.meta.url))` pattern - the esbuild-based `@angular/build:application` builder (Angular 21) supports this natively: a TS transformer rewrites that exact call-site pattern at build time and bundles the worker as its own independent esbuild entry point (a normal hashed `.js` output file, e.g. `worker-HLP7X6NI.js`, already covered by `ngsw-config.json`'s existing `/*.js` asset glob - no config changes needed anywhere). The file stays inside `tsconfig.app.json`'s default `src/**/*.ts` include (no separate `tsconfig.worker.json`) so it still gets full `ng build` type-checking under the ordinary DOM lib - it only ever uses `addEventListener`/`postMessage`, both of which exist on `Window` too, so nothing Worker-specific (`self.close()`, `importScripts`) is needed.

**`OddsEngine`** (`@Injectable({ providedIn: 'root' })`) owns the Worker's lifecycle and exposes plain signals - `result: Signal<TargetSequenceResult[]>`, `progress: Signal<number | null>`, `calculating: Signal<boolean>`, `error: Signal<string | null>`, `cancelled: Signal<boolean>`, `slow: Signal<boolean>` - rather than a callback/Promise API, matching this app's all-signals, no-RxJS style (a Promise doesn't fit well here either: a computation can be superseded mid-flight, and a Promise can't be "un-resolved"). `computeSequence(attacks, targets)`:
- **Always cancels whatever's in flight first** (`worker.terminate()`) before starting a new one, rather than letting a stale computation run to completion and just discarding its result - termination is immediate, and spinning up a fresh worker costs single-digit milliseconds, a rounding error next to the multi-second computations this exists for. A burst of rapid input changes (typing, dragging) therefore costs at most one cheap worker respawn per change, never a pile of full computations queuing up behind each other.
- **Delays `calculating` by `SHOW_CALCULATING_DELAY_MS` (350ms)** via `setTimeout`, so the overwhelming majority of recomputes (fast ones) never flip it on at all - no flash on every keystroke. `cancelInFlight()` clears this timer too, so a superseded computation can't cause a late, stale "now calculating" flip after being cancelled.
- `progress` resets to `0` at the start of every `computeSequence` call and back to `null` once settled (success, error, or superseded) - `null` specifically means "nothing in flight", distinct from `0` ("in flight, no progress reported yet").
- **`error`** is set from the worker's own `'error'` message or `onerror` crash event, and reset to `null` at the start of every `computeSequence` call. `sequence.ts` still throws on a few individually unrealistic field values (e.g. `attackerFocus` above `MAX_RESOURCE_POINTS`), but none of those are reachable through the UI's own inputs today - every relevant `<select>` is already range-limited to a valid value - so `error` mainly exists for `worker.onerror`'s genuine crash case and future-proofing now, not a live day-to-day path. It's a REAL fix for a real bug that used to live here, though: before `error` existed, a failure surfaced as nothing but a `console.error` - `calculating` never even flipped on (the throw is near-instant, well under `SHOW_CALCULATING_DELAY_MS`) and `result` stayed frozen at whatever the last SUCCESSFUL computation produced - from the player's side, indistinguishable from the app having silently frozen, with no further input change able to fix it while the same failing combination stayed configured. (This is exactly what originally happened with the old flat `MAX_FOCUS_ATTACKERS` attacker-count cap - a player pushing a 3rd attacker's Focus past 0 saw no visible effect at all. That specific cap is gone now, replaced by the purely advisory `slow` below, not a throw.) `ResultsPanel`'s `error` input renders a `.readout__overlay--error` banner ("Can't calculate: {message}") in place of the "Calculating" overlay, over the dimmed last-known gauges - same "reassurance, not a reset" treatment `calculating` already gets.
- **`slow`** is set synchronously, on the MAIN thread, at the very start of every `computeSequence` call - `targets.some((target) => estimateSequenceComplexity(attacks, target) > MAX_SEQUENCE_COMPLEXITY)` - BEFORE the Worker is even spun up, so it's available from the very first render of the "Calculating" overlay rather than needing to wait and see whether the computation actually turns out slow. Purely advisory: `sequence.ts` itself never rejects a config for being "too complex" (a hard cap here was tried across several rounds and explicitly rejected by the user - a player's own device may well handle far more than any fixed estimate suggests, and there's no way to know that in advance). `ResultsPanel`'s `slow` input renders a small "This might take a long time." hint UNDER the existing "Calculating" label (not a replacement for it, unlike `error`/`cancelled` - the overlay stays in the SAME state, just with extra context) via `.readout__overlay-hint` (`flex-basis: 100%` to force it onto its own line, since `.readout__overlay` is `flex-wrap: wrap`).
- **`cancel()`/`cancelled`** let the player manually bail out of a still-running computation - the actual backstop for `slow`, now that there's no hard ceiling on runtime at all: `cancel()` terminates the worker (a no-op if nothing is in flight) and sets `cancelled` rather than reusing `error` - being cancelled is a deliberate player action, not a failure, so `ResultsPanel` renders it with its own calmer `.readout__overlay--cancelled` styling (still over the dimmed last-known gauges, though the overlay's own near-opaque backdrop means "last-known" isn't actually legible through it - the label just says "Cancelled", no false claim of showing anything underneath) instead of the red error banner. Both `error` and `cancelled` reset together at the start of the next `computeSequence` call. Wired end to end: `ResultsPanel`'s `cancel` output -> `OddsCalculator.onCancel()` -> `engine.cancel()`, with a small text button (`.readout__overlay-action`, the one element inside the otherwise `pointer-events: none` overlay that opts back in, shared by both the Cancel and Retry buttons - brass-styled by default, overridden to the calmer `--text-dim` tone inside `.readout__overlay--cancelled`) rendered next to the "Calculating" label once the overlay itself is showing.
- **Retry** (`ResultsPanel`'s `retry` output -> `OddsCalculator.onRetry()`) sits next to "Cancelled", for undoing an accidental Cancel click. Re-running needs no dedicated state of its own: the inputs that produced the interrupted computation haven't changed (only the constructor's own `effect()` re-triggers `computeSequence` on an input change, and `cancel()` doesn't touch any input), so `onRetry()` just calls `this.engine.computeSequence(this.sequencedAttacks(), this.sequenceTargets())` again directly with what's already there.

`OddsCalculator`'s own `sequence`/`calculating`/`progress` are just `= this.engine.result` / `.calculating` / `.progress` (delegated signals, not `computed()`s) - a `constructor()` `effect()` is what actually triggers `computeSequence` whenever `sequencedAttacks()`/`sequenceTargets()` change: `effect(() => { this.engine.computeSequence(this.sequencedAttacks(), this.sequenceTargets()); })`. `sequenceTargets` maps `targets()` (one `Target` per target - see "Multiple targets" above and the UI section below) through the SAME per-field `SequenceTarget` conversion the old singular `sequenceTarget` computed always did, just once per target now (`OddsCalculator.toSequenceTarget`, extracted to a `static` method so the mapping itself carries no per-call overhead beyond the array iteration). `damageDistributionPointsByTarget`/`maxDamageProbabilityByTarget`/`shotRowsByTarget`/`averageDamageByTarget` (all arrays, one entry per target, replacing the old singular `damageDistributionPoints`/`maxDamageProbability`/`shotRows`) are ordinary `computed()`s over `this.sequence()` (now `TargetSequenceResult[]`) the same way the singular versions always were - a `computed()` tracks any signal read regardless of whether it's a plain delegated signal or a `computed()` itself, so this needed no different reactivity plumbing, just a `.map()` around the same per-target logic.

**Not unit-tested**: jsdom (the `test` architect target's environment) registers no `Worker` global, so `OddsEngine`'s orchestration logic and `sequence.worker.ts` itself can't run under the existing Vitest suite - verified manually in a real browser instead (a heavy scenario taking ~15s, confirming the tab stays responsive throughout, the indicator appears/clears at the right times, and the final result matches an independently-computed reference). `computeSequenceOdds`'s own `onProgress` parameter DOES get an automated test in `engine.spec.ts` (calling it directly, no Worker involved) - it's plumbing on an already-tested pure function, not a new probability rule, so this modest coverage is proportionate.

(`computeAttackOdds`, the single-attack function `computeSequenceOdds` itself is built on, is still used directly by `attack-model.ts`'s own tests and by `sequence/` internally - it never needed its own DI/Worker wrapper, since every UI path goes through a sequence, even a one-attack one.)

## The UI (`src/app/odds-calculator/`)

### Component split

`OddsCalculator` used to be a single monolithic component; it's now a thin **orchestrator** delegating to focused child components, split when the combined `.ts`/`.html`/`.css` passed ~1600 lines and adding attack rows started requiring scrolling the whole page (see "App shell" below for the bug that caused along the way):

```
odds-calculator/

  attack-row.model.ts              # AttackRow domain model (shared by odds-calculator + attacker-card/ + attack-sub-card/ + attack-edit-dialog/)
  attacker.model.ts                # Attacker domain model - MAT/RAT/AAT + its own AttackRow[] + puppetMaster (see "Attacker grouping" below)
```

Every child component that owns its own popup (`AttackEditDialog`, `AttackerRulesDialog`, `TargetProfileDialog`, `DetailsDialog`, `AboutDialog`, `ChangelogDialog`, `FeedbackDialog`) is self-contained: it exposes `open()` directly (delegating internally to its own `DialogShell` - see "Pop-ups" below), rather than the orchestrator tracking "which dialog/row is open". The orchestrator's template calls this method through **template reference variables** (`#attackEditDialogRef`, `#attackerRulesDialogRef`, `#targetProfileDialogRef`, `#detailsDialogRef`, `#aboutDialogRef`, `#changelogDialogRef`, `#feedbackDialogRef`) rather than `@ViewChild` in the orchestrator's own class - Angular resolves a template ref variable anywhere in the same template, including from a sibling element's event binding, so no `@ViewChild` boilerplate is needed there at all. `AppMenu` follows the same "trigger elsewhere, dialog lives at the orchestrator level" shape as `TargetPanel`'s cog button: it doesn't hold any of these dialogs itself, it just emits `openAbout`/`openChangelog`/`openFeedback` outputs that the orchestrator wires straight to those template ref variables. `AttackerCard` follows the same shape twice over: `addAttack`/`remove`/`openRules` are its own (`openRules` wired to `attackerRulesDialogRef.open(attacker)`, `AttackerRulesDialog` taking the whole `Attacker` the same way `AttackEditDialog` takes an `AttackRow` - many attackers sharing one dialog instance), while its sub-cards' `edit`/`remove` outputs are simply re-emitted upward unchanged (the Effects pop-up only needs the row itself, not which attacker it belongs to) - there's no `editAttacker` output for name/MAT/RAT/AAT, since those are edited directly on the card (see "Pop-ups" below), not through a dialog the orchestrator would need to open.

**Shared CSS via multiple `styleUrls`, not a single global stylesheet.** Angular components normally get their own scoped CSS file, but many classes here (`.icon-btn`, `.dialog__header`, `.toggle-btn`, ...) are used by several sibling components with identical markup. Rather than duplicating the rules by hand (risking drift) or making them globally unscoped (risking accidental collisions elsewhere in the app), each consuming component lists the relevant partial file(s) from `shared/` in its own `styleUrls` array alongside its own file. Angular bundles and scopes each partial **separately per consuming component** (each gets its own `[_ngcontent-xxx]` attribute stamped onto the rules), so a shared file can be included by five different components and each one only ever matches elements actually rendered by that component - a `.dialog__section-title` selector inside `shared/dialog-sections.css`, for instance, simply never matches anything inside `FeedbackDialog`'s scoped copy of that file, since `FeedbackDialog`'s template has no such element. (`.mini-field`/`.effect-tag` used to be textbook examples of this too - both now live in exactly one component's `styleUrls`, `MiniFieldSelect`/`EffectTags` respectively, since nothing else renders their markup directly anymore.)

**Ordering rule for `styleUrls`: shared partials first, the component's own file last.** Angular concatenates `styleUrls` in array order; when two rules have equal CSS specificity (very common here - most of this app's classes are single-class selectors), the **later** one wins a tie, not the more "local" one. This bit us for real once (see "App shell" below): `shared/section.css`'s `.console, .readout { flex-shrink: 0; ... }` and `odds-calculator.css`'s `.console--attacks { flex: 1 1 auto; ... }` both apply to the same `<section class="console console--attacks">` element with equal specificity, and having the shared file listed *after* the component's own file silently let the shared rule win, overriding `flex-shrink` back to `0` and breaking the one section that's supposed to scroll. Every component in this split now lists its shared partials first and its own file last specifically to make local overrides always win predictably.

### `attack-row.model.ts` — the `AttackRow` domain model

Pure TypeScript (no Angular), imported by the orchestrator, `AttackerCard`, `AttackSubCard`, and `AttackEditDialog`. Each row (`AttackRow`, one **weapon**) is an object whose **every field is itself a signal** - see the "why" below. No editable label: `toSequencedAttack` still builds a `label` (`Attack ${index + 1}`) on the `SequencedAttack` it returns, but nothing in the app actually reads it - the step numbering shown in the "Step by step" results breakdown (`details-dialog.html`) is the plain positional loop index (`i + 1`) instead, not this field. Base (non-effect) fields: `attackCount` ("# Atks"), `type`, `diceCount`, `pow`, `damageDiceCount`, `rof`. Notably absent: `stat` - MAT/RAT/AAT live one level up, on the row's parent `Attacker` (see "Attacker grouping" below), since one attacker's several weapons (melee weapon, ranged weapon, spell) all roll against the SAME printed stats rather than each carrying its own copy.

**Every toggleable effect - general, attack-roll, damage-roll, crit-only, and genuinely hit-or-crit-triggered alike - lives in ONE fixed-size array, `triggerEffects: TriggerEffectRow[]`, rather than a mix of individually-named booleans plus a separate array.** An earlier version had 15 separate `WritableSignal<boolean>` fields (`jumpTheShark`, `blessed`, `forceAutoHit`, `discardAttackLowest`, ...) alongside `triggerEffects` for just the 13 keys that genuinely distinguish "on a hit" from "on a critical hit" (`armorPiercing`, `decapitation`, the persistent `StatEffect`s). That split meant every one of those 15 booleans got its own hand-written toggle-button block in `effects-dialog.html` - `[class.toggle-btn--active]="row.x()"`, `(click)="row.x.set(!row.x())"`, repeated with only the field name and label changing - real repetition with no structural reason for it. Unifying under one `TriggerEffectRow` shape is what let a single `ToggleButton` component (see "Pop-ups" below) replace every one of those hand-written blocks, including the 13 original ones:
```ts
interface TriggerEffectRow {
  readonly key: TriggerEffectKey;
  readonly trigger: WritableSignal<EffectTrigger | 'off'>;
}
```
For the 15 "simple" keys (no real hit/crit distinction at all - Jump the Shark, Discard lowest, Trash, ...), `'hit'` is simply used as the interface's generic "on" value, and the UI only ever renders ONE button for them (`ToggleButton`'s default `activeValue="hit"`). 12 more genuinely hit/crit-triggerable keys get a PAIR of buttons (one per group), both bound to the SAME `TriggerEffectRow` with a different `activeValue` - `ToggleButton`'s `toggle()` method implements the shared "toggle button" behavior for both cases: clicking the button for the already-active value switches the effect back to `'off'`; clicking a different value (only reachable for a pair) switches straight to it, no need to turn it off first. 27 keys total this way (`TRIGGER_EFFECT_KEYS`) - **`'armPenalty'` (the 13th genuinely hit/crit-triggerable key) is the one deliberate exception**, pulled back OUT of this generic system entirely once it needed a real user-editable amount rather than a plain on/off - `TriggerEffectRow` no longer even has a field to carry one (`amount` was removed once `armPenalty` was its only reader). See `AttackRow.armPenaltyHitAmount`/`armPenaltyCritAmount` and "Content of the Attack edit pop-up" below for its own, separate two-field design.

`TRIGGER_EFFECT_KEYS` stays a **fixed set**, created once by `createTriggerEffects()` and never recreated during a row's lifetime (same "no add/remove-by-id machinery needed" reasoning as when the old dynamic `StatEffectRow[]` list was replaced by a fixed array - see git history) - it's just grown to cover every effect instead of only the hit/crit-triggerable ones. It's split into five exported, ordered key lists (`GENERAL_EFFECT_KEYS`, `ATTACK_EFFECT_KEYS`, `DAMAGE_EFFECT_KEYS`, `HIT_CRIT_PAIR_KEYS`, `CRIT_ONLY_SIMPLE_KEYS`) so the template can pull just the subset relevant to a given dialog section, in the right order, via `effectsFor(row, keys)`. `TRIGGER_EFFECT_LABELS: Record<TriggerEffectKey, string>` centralizes every button's display text (`ToggleButton` looks its own label up from its `effect().key` - no separate `label` input needed); a small `SUMMARY_LABEL_OVERRIDES` map covers the handful of keys whose *summary tag* text needs to differ from the button's own label (`discardAttackLowest`'s button says "Discard lowest", its tag says "Discard lowest (atk)" - the two "Discard lowest" buttons, attack-roll and damage-roll, would otherwise be indistinguishable in the tag list).

**Why signal-per-field instead of a plain array of JS objects?** With Angular signals, mutating a nested object inside a signal array doesn't trigger recalculation (a signal only detects the replacement of its own value). Two options: (a) clone the whole array on every keystroke, or (b) give each field its own signal, which `computed()` will read individually and can therefore track finely. Option (b) is chosen here: adding/removing an **attack row** replaces its parent attacker's `attacks` array (`attacker.attacks.update(...)`, see `attacker.model.ts`'s `addAttackTo`/`removeAttackFrom`), but editing an effect (fixed) or any other field only touches its own signal — no deep cloning needed. The same rationale drives `TargetState` (see below).

- **`diceCount` / `damageDiceCount`**: the user directly picks the **total** number of dice rolled (2 by default), not a boost-dice count. `toBoostDice(diceCount)` performs the conversion (`max(0, diceCount - 2)`) when building the `SequencedAttack` object sent to the engine. `discardModifier(lowest, highest)` translates the pair of booleans into `{ highest?: 1, lowest?: 1 } | undefined`.
- **`attackCount`** ("# Atks") and **`rof`**: both passed straight through to `SequencedAttack.attackCount`/`.rof`. `attack-sub-card.html` renders these two fields differently depending on `row.type()`: for melee/arcane, a single `<app-mini-field-select>` bound to `attackCount` alone (`ATTACK_COUNT_OPTIONS`, 1-10 - `rof` is simply never shown, since the engine's own `rofOutcomes` already ignores it for non-ranged attacks, so switching a row's Type away from Ranged and back doesn't need to reset the field). For **ranged**, both fields render together under one shared "# Atks" `<label class="mini-field">`, as two RAW `<select>` elements (`RANGED_ATTACK_COUNT_OPTIONS`, 0-10, and `ROF_OPTIONS`) rather than two separate `<app-mini-field-select>`s - `MiniFieldSelect` only ever renders one label + one select, and this merged field needs one label spanning two selects, so the markup is inlined directly in `attack-sub-card.html` (reusing `shared/mini-field.css`'s classes, added to `AttackSubCard`'s own `styleUrls`) instead of going through the shared component. `RANGED_ATTACK_COUNT_OPTIONS` allows `0` (a purely ROF-driven weapon, e.g. a Sprayer with no guaranteed base shot) - melee/arcane's own `ATTACK_COUNT_OPTIONS` doesn't, so `AttackSubCard.onTypeChange` (wired via `MiniFieldSelect`'s optional `valueChange` output on the Type select) bumps `attackCount` back up to `1` when switching away from Ranged while it's `0`, the one case where a value valid under the ranged options wouldn't be valid under the melee/arcane ones.
- `toSequencedAttack(row, index, stat, attackerName)`: a named function (not an inline `.map()` callback) with an explicit `SequencedAttack` return type annotation, projecting one `AttackRow` into the plain object shape the engine expects — generates the `Attack ${index+1}` label, converts `pow` via `resolvePow`, looks up each simple effect via the local `isEffectOn(row, key)` helper (built on the same `triggerOf` lookup `armorPiercing`/`decapitation` already used), assembles `effects`/`statEffects`. `statEffects` is built in two steps: the generic `triggerEffects` entries map straight across (`{ type: e.key, trigger: e.trigger() }`, no `amount` - see above), then `armPenaltyHitAmount`/`armPenaltyCritAmount` are folded in separately via an `if`/`else if` that pushes a single `{ type: 'armPenalty', trigger: 'hit' | 'crit', amount }` entry for whichever of the two is nonzero (never both, by construction). `stat`/`attackerName` are no longer the row's own values (see "Attacker grouping" below) - the orchestrator's `sequencedAttacks` computed resolves them per row (`statFor(attacker, row.type())`, `attackerDisplayName(attacker, i)`) while flattening every attacker's `attacks()` into one flat, globally-indexed list for the engine.

  **TypeScript pitfall this design avoids: the "excess property" checker doesn't apply to an object literal returned by a `.map()`/`.forEach()` callback without an explicit type annotation on that callback**, even if the enclosing `computed(...)` carries an explicit generic type. An old renamed/removed field (`criticalEffects`, replaced by `effects`/`statEffects`) had once remained silently accepted by the compiler in a `{ ...criticalEffects: {...} }` literal directly inside a `.map()` even though `SequencedAttack` no longer had it - the value was simply ignored at runtime. Moving the literal into a standalone function with an explicit return type (`toSequencedAttack`) is a more robust fix than just annotating the callback inline, since a plain function call's result is never subject to excess-property "freshness" checks in the first place - there's no loophole left to reintroduce by accident on a future edit.
- `effectsSummary(row): string[]`: builds the list of short labels ("Discard lowest (atk)", "Trash", "Crit Knockdown"...) shown under each attack sub-card - now a single pass over `triggerEffects`, applying `SUMMARY_LABEL_OVERRIDES` where the tag text needs to differ from the button label, plus a `'Crit '` prefix whenever `trigger() === 'crit'` (never true for a simple-toggle key, since those are only ever `'off'`/`'hit'`). Brutal Damage and Critical Shred are both crit-only but rendered as simple toggles (see `CRIT_ONLY_SIMPLE_KEYS`), so that automatic prefix never reaches them either - each needs its own `SUMMARY_LABEL_OVERRIDES` entry instead (`'Crit Brutal Damage'`, `'Crit Shred'`) to read the same way as a genuine hit/crit pair's crit-side tag would, even though their BUTTON labels ("Brutal Damage", "Shred") stay short since they only ever appear in the "Critical" section to begin with - no need to repeat "Critical" in a button that's already grouped under that heading.
- `resetEffects(row)`: resets every entry in `triggerEffects` to `'off'`, plus `armPenaltyHitAmount`/`armPenaltyCritAmount` to `0` — the "base" fields (type, dice, POW) are deliberately left untouched.

### `attacker.model.ts` — the `Attacker` domain model, and grouping attacks by attacker

`Attacker` owns the MAT/RAT/AAT its own attacks share (`mat`/`rat`/`aat: WritableSignal<number>`, same signal-per-field reasoning as `AttackRow`), a `name: WritableSignal<string>` (`''` = unnamed - `attackerDisplayName(attacker, index)` falls back to `` `Attacker ${index + 1}` `` by current position, exactly how an attack row's own number was always a live position rather than a stored value), and `attacks: WritableSignal<AttackRow[]>`. `statFor(attacker, type)` is the one piece of logic that actually implements "MAT/RAT/AAT live on the attacker, not the attack": MAT for melee, RAT for ranged, AAT for arcane. `addAttackTo`/`removeAttackFrom` are `OddsCalculator`'s old `addAttack`/`removeAttack` (copy-the-previous-attack default, can't drop below one attack) lifted verbatim, now scoped to one attacker's own `attacks` signal instead of the whole sequence.

No import of `Attacker` in `attack-row.model.ts` (or vice versa beyond `AttackRow`/`createAttackRow`/`cloneAttackRow`, which `attacker.model.ts` needs to seed a fresh attacker's first attack) - `toSequencedAttack` takes `stat`/`attackerName` as plain parameters instead, keeping the two files decoupled and avoiding a circular import.

`OddsCalculator.attackers: signal<Attacker[]>` replaces the old flat `rows: signal<AttackRow[]>`. `sequencedAttacks` flattens attacker → attacks with a single running index, since attacks still resolve as ONE ordered sequence for the engine regardless of which attacker owns them - the engine itself (`sequence/`, `attack-model.ts`) needed **no changes at all** for this feature: it already took a flat `SequencedAttack[]` with a plain `stat: number`/`attackerName: string` per attack (the latter always hardcoded `''` before this, now genuinely populated). `onRemoveAttacker`/`onRemoveAttack` both keep the same "can't drop below one" guard the old flat list had, just at two levels now: an attacker can't be removed while it's the only one, and an attack can't be removed while it's the only one on its attacker (removing the whole attacker is the only way to go lower there).

### `target-panel/target-panel.model.ts` — the `TargetState` domain model

**`Target` (`{ id, name: WritableSignal<string>, state: TargetState }`)** wraps `TargetState` for the multiple-targets feature - the SAME `Attacker`/`AttackRow` relationship `attacker.model.ts` already has, just one level up: `TargetState` itself is completely unchanged (still the flat "signal per field" bag every function below already operates on), `Target` just gives it a stable `id` (for `@for` tracking and `AttackRow.eligibleTargetIds` - see "Multiple targets" in the engine section above) and a name. `createTarget(source?: Target)` mirrors `createAttacker()`/`cloneAttackRow` - omit `source` for a fresh default target, pass one to clone its CURRENT profile into fresh signals (`cloneTargetState`, one line per `TargetState` field, same shape as `cloneAttackRow`) - matching "+ Add target" copying the previous target's profile. `targetDisplayName(target, index, count)` mirrors `attackerDisplayName`, with one difference: it only appends a number (`"Target N"`) once `count > 1` - a lone target just reads `"Target"`, since numbering something that's alone would imply a second one is coming.

Same "signal per field" structure as `AttackRow`, shared by `TargetPanel` and `TargetProfileDialog` (and read by the orchestrator to build the engine call) - `Target.state` IS this, unmodified:
```ts
interface TargetState {
  def: WritableSignal<number | 'KD'>;
  arm: WritableSignal<number>;
  boxes: WritableSignal<number>;
  focusPoints: WritableSignal<number>; // mutually exclusive with furyPoints - see below
  furyPoints: WritableSignal<number>;
  toughKind: WritableSignal<'off' | 'tough' | 'toughSteady'>; // mutually exclusive - see below
  shieldAmount: WritableSignal<number>; // flat ARM bonus, 0-10 (0 = off) - see shieldArmBonus below
  unyielding: WritableSignal<boolean>;
  carapace: WritableSignal<boolean>;
  dispellableTough: WritableSignal<boolean>; // same grant as toughKind === 'tough', but Dispel-removable
  dispellableUnyielding: WritableSignal<boolean>; // same grant as unyielding, but Dispel-removable
  rapidHealing: WritableSignal<boolean>; // no dispel-pair - see target-panel.model.ts's doc comment
  // Flat DEF/ARM spell bonuses, 0-10 each (0 = off) - see spellArmBonus's doc comment below.
  spellDefAmount: WritableSignal<number>;
  spellArmAmount: WritableSignal<number>;
  upkeepSpellDefAmount: WritableSignal<number>;
  upkeepSpellArmAmount: WritableSignal<number>;
}
```
- **`toughKind` instead of two independent booleans**: Tough and Tough Steady are mutually exclusive by definition (Tough Steady *is* "Tough, but immune to Knockdown negation" - see `sequence/`), so modeling them as a single 3-state field avoids ever representing the nonsensical "both active" state. `toggleToughKind(target, kind)` in `TargetProfileDialog` mirrors `ToggleButton`'s own `toggle()` (see "Pop-ups" below): clicking the active kind's button turns it `'off'`, clicking the other switches straight to it.
- **`focusPoints`/`furyPoints` are two independent fields, but stay mutually exclusive by convention, not by construction**: a model is either a warcaster (Focus) or a warlock (Fury), never both, so both being nonzero at once would represent a state the tabletop game itself doesn't allow. Unlike `toughKind` (a single 3-state field that makes "both" unrepresentable), this is enforced at the call site instead: `TargetProfileDialog`'s `onFocusChange`/`onFuryChange` (bound to each `<app-toggle-select>`'s own `(valueChange)` output - see "Pop-ups" below) zero the other field whenever one is set above 0. `targetSummary` mirrors this with an `else if` (only ever pushes one `key: 'resource'` tag) rather than two independent `if`s, so the "one resource tag" invariant holds even if some future code path left both fields nonzero. The orchestrator's `sequenceTarget` computed now just reads both fields directly into the engine's own independent `focusPoints`/`furyPoints` - which were always two separate fields on `SequenceTarget`, with no "kind" concept at all; the combined UI representation this replaced was never something the engine itself needed.
- **`spellDefAmount`/`spellArmAmount`/`upkeepSpellDefAmount`/`upkeepSpellArmAmount`** are four FIXED counters (0-10 each, 0 = off), not a repeatable list - two spell "categories" ("Spells" - permanent, Dispel can't remove it; "Upkeep spells / Animi" - removable by Dispel), each with its own DEF and ARM total. **An earlier version modeled this very differently**: a genuinely dynamic, repeatable `spellBonuses: WritableSignal<SpellBonusRow[]>` list (like the old, since-removed `StatEffectRow` list), each entry carrying a free-text `name`, its own `defAmount`/`armAmount`, an `isSpell` toggle (whether Blessed ignores it), and a `dispellable` toggle - plus, in an even earlier version, a `kind: 'stat' | 'rule'` variant so a row could instead grant Tough/Unyielding (see "Dispellable special rules" `git` history for how THAT case was carved out first). Once the UI settled on "just track the TOTAL DEF/ARM bonus per category, not each individual spell's name," the whole per-entry model (name, `isSpell`, `SpellBonusRow` itself, `createStatSpellRow`, the "+ Add stat spell" button, `EditableName` in this dialog) had nothing left to do and was removed outright, in favor of the four fixed fields above - both categories are always Blessed-ignorable now (there's no more `isSpell`/non-spell distinction reachable from this UI at all - see `spellArmBonus` below for what that means for the ENGINE's own `nonSpellArmBonus`/`nonSpellDefBonus` fields, which were deliberately left alone rather than deleted).
- **`TargetState.dispellableTough`/`dispellableUnyielding`**: the same grant `toughKind === 'tough'`/`unyielding` represent, but removable by an attack's Dispel effect (an upkeep spell) - OR'd into the `effective*` helpers exactly like a permanent toggle:
  ```ts
  export function effectiveUnyielding(target: TargetState): boolean {
    return target.unyielding() || target.dispellableUnyielding();
  }
  export function effectiveCarapace(target: TargetState): boolean {
    return target.carapace(); // no dispellable-Carapace concept
  }
  export function effectiveToughKind(target: TargetState): ToughKind {
    if (target.toughKind() !== 'off') return target.toughKind();
    return target.dispellableTough() ? 'tough' : 'off';
  }
  ```
  A permanent toggle always takes priority in `effectiveToughKind` (an odd case of both a permanent AND a dispellable Tough grant should still read as whichever the permanent one is, not silently downgrade) - there's no dispellable Tough STEADY at all (only plain Tough, matching the old `SPELL_RULE_OPTIONS`'s deliberately narrow `['tough', 'unyielding']`, since Tough Steady/Shield/Carapace are almost always permanent model rules rather than spell-granted in practice). The orchestrator's `sequence` computed calls these `effective*` functions - rather than reading `target.toughKind()`/`target.unyielding()`/`target.carapace()` directly - for the engine's PRE-Dispel fields, and the raw signals directly for the POST-Dispel fields (see `sequence/`'s "Target capabilities" section for why that split is always exactly "effective vs permanent-only" and never needs finer filtering). **There's no dispellable Shield, and so no `effectiveShield`**: `shieldArmBonus` (below) reads `target.shieldAmount()` directly - an `effectiveShield` that could never actually differ from the raw signal would just be dead code.
- **`shieldArmBonus(target)`**: `target.shieldAmount()` - Shield is just a single 0-10 counter (0 = off, matching `SHIELD_AMOUNT_OPTIONS = range(0, 10)`), not a separate boolean plus amount - deliberately the innate signal only, per the note above.
- **`spellArmBonus(target)` / `spellArmBonusPostDispel(target)` / `spellDefBonus(target)` / `spellDefBonusPostDispel(target)`**: each a one-line sum/passthrough over the four fixed fields above, mirroring the `dispellableTough`/`dispellableUnyielding` "permanent vs Dispel-removable" split exactly:
  ```ts
  export function spellArmBonus(target: TargetState): number {
    return target.spellArmAmount() + target.upkeepSpellArmAmount();
  }
  export function spellArmBonusPostDispel(target: TargetState): number {
    return target.spellArmAmount(); // the upkeep/Animus half never survives Dispel
  }
  // spellDefBonus / spellDefBonusPostDispel: same shape, defAmount fields.
  ```
  These feed the engine's `SequenceTarget.spellArmBonus`/`spellArmBonusPostDispel`/`defBonus`/`defBonusPostDispel` (see `sequence/`) - `nonSpellArmBonus`/`nonSpellArmBonusPostDispel`/`nonSpellDefBonus`/`nonSpellDefBonusPostDispel` have no UI-layer counterpart anymore (there's no non-spell source left to sum - see `TargetState` above), so `odds-calculator.ts`'s `sequenceTarget` computed simply omits them from the object literal it builds, relying on `sequence/`'s own `?? 0` default for each (see "Target capabilities" above).
- `targetSummary(target)`: same role as `effectsSummary(row)`, producing the tag list shown under the Target row (`Focus 2`, `Tough Steady`, `Tough [Up]`, `Shield +2 ARM`, `Spell +2 DEF`, `Upkeep +3 ARM [Up]`, ...). Reads `target.toughKind()`/`target.dispellableTough()`/`target.shieldAmount()`/`target.unyielding()`/`target.dispellableUnyielding()`/`target.carapace()`/`target.spellDefAmount()`/`target.spellArmAmount()`/`target.upkeepSpellDefAmount()`/`target.upkeepSpellArmAmount()` (not the `effective*`/`spellArmBonus`-style aggregate variants) directly, each producing its own separate tag - a permanent AND a dispellable grant of the same rule both active at once shows two tags (e.g. "Unyielding" and "Unyielding [Up]"), deliberately not deduped, the same reasoning the old spell-granted-rule tag used. Every tag key here is now a fixed, hand-picked string (`'spellDef'`, `'upkeepSpellArm'`, ...) rather than a dynamic row's own `id` - there's no more per-entry list to track identity for.
- `resetTargetProfile(target)`: resets everything **except** `def`/`arm`/`boxes` (which live outside the popup, in `TargetPanel`'s own card). `resetTargetFully` (the old DEF/ARM/Boxes-inclusive variant the hamburger menu's Reset used) was removed once that action collapsed to `this.targets.set([createTarget()])` - a single fresh default target already covers everything the old function did, one call site, no separate helper needed.

### Multiple targets — remaining UI pieces

Mirrors the attacker-grouping pattern throughout: `odds-calculator.ts`'s `targets = signal<Target[]>([createTarget()])` replaces the old singular `target: TargetState` field; `odds-calculator.html` loops `@for (target of targets(); track target.id)` over `<app-target-panel>` instances exactly like it already loops attackers over `<app-attacker-card>`, with a "+ Add target" button below the list (`onAddTarget`, cloning the last target via `createTarget(list.at(-1))`, then scrolling the new card into view - same `afterNextRender`/`ElementRef` pattern `onAddAttacker` already uses) and a remove button per card (`onRemoveTarget`, disabled while it's the only one).

- **`TargetPanel`** changed from owning the WHOLE "Target" section (title, single row) to being ONE card in a list, the same shape shift `AttackerCard` went through when attacks were grouped by attacker - `target: input.required<TargetState>()` became `target: input.required<Target>()` plus `index`/`count`/`removable` inputs (for the "Target"-vs-"Target N" placeholder and the disabled-while-alone remove button) and `openProfile`/`remove` outputs, with an `<app-editable-name>` added for the inline-renameable name (previously the section just had a static "Target" title).
- **`TargetProfileDialog`** changed from a fixed `target: input.required<TargetState>()` binding to the SAME "opened with the specific thing being edited" pattern `AttackEditDialog` already uses for `AttackRow`: `protected readonly target = signal<TargetState | null>(null)`, set by `open(target: TargetState)` (called per-card as `targetProfileDialogRef.open(target.state)`), with the template wrapping its whole body in `@if (target(); as t) { ... }` instead of the old unconditional `@let t = target();` - split into TWO separate `@if` blocks (one for the default-slot content, one for the `dialogActions` footer) rather than one, since Angular can't route an `@if` block's content into a named projection slot once that block has more than one root node (NG8011) - the same constraint `AttackEditDialog`'s own template already works around.
- **`AttackEditDialog`** gained a `targets: input<Target[]>([])` (bound from the orchestrator as `[targets]="targets()"`) purely to render a new "In range of" section (the FIRST section in the dialog, ahead of General/Attack/Damage/On hit/Critical, since which targets a weapon can even hit is more fundamental than any effect it has) - one plain toggle button per target (styled with the same `.toggle-btn`/`.toggle-btn--active` classes `<app-toggle-button>` uses, but hand-written rather than an actual `<app-toggle-button>` instance, since that component is bound to a `TriggerEffectRow` and weapon-target eligibility isn't one) - shown only when `targets().length > 1`. `isTargetEligible(row, targetId)`/`toggleTarget(row, targetId)` read/write `AttackRow.eligibleTargetIds` (`WritableSignal<string[] | null>`, `null` = every target): toggling while it's still `null` starts from the FULL current target-id list (`this.targets().map(t => t.id)`) rather than an empty one, so the very first click reads as "turn OFF just this one" - matching what the button visually showed (every target's button already active) - instead of "turn on just this one." `isOnlyEligibleTarget(row, targetId)` (`current.length === 1 && current.includes(targetId)`) disables that one button - an attack must stay in range of at least one target, so the last one standing can't be toggled off; `toggleTarget` itself also short-circuits on the same condition as defense-in-depth, in case the disabled state is ever bypassed (e.g. a stale template render).
- **`rangeSummary(row, targets)`** (`attack-row.model.ts`, alongside `effectsSummary`) is `AttackSubCard`'s own equivalent of the "in range of" toggles, rendered UNDER the weapon's fields as a single `.range-line` ("In range of: Target 1, Target 2...", brass-accented, `attack-sub-card.css` - deliberately NOT routed through the shared `EffectTags` component, so it can't be mistaken for one of that component's steel-colored effect tags right below it; `AttackSubCard.rangeLabel(tags)` joins the tag list's own labels with `', '` for that line). Always the FULL current target list once `eligibleTargetIds` is `null` (unset = every target) - shown unconditionally, not just once a weapon is actually scoped down, so a player never has to open the Effects pop-up to confirm a weapon covers everyone; empty (nothing rendered at all) only when there's a single target to begin with. `AttackSubCard` needed a `targets: input<Target[]>([])` of its own to call this, threaded straight through from `OddsCalculator` via `AttackerCard`'s own new `targets` input (the same plain pass-through pattern `removable` already uses down that same chain).
- **`ResultsPanel`**: `results: input.required<TargetSequenceResult[]>()` replaces the old singular `sequence: input.required<SequenceResult>()`; `results().length <= 1` renders the ORIGINAL two-gauge layout completely unchanged (byte-for-byte the same template branch, so a single-target sequence's Results panel is pixel-identical to before this feature), `> 1` renders a single `.readout__all-destroyed` line (see `chanceToDestroyAll` below) plus one `.icon-btn--stats` (`query_stats`) button - the same `.readout__row` layout the single-target branch already used for its own gauge grid + button - emitting `showDetails(0)` (always the first target; the Details pop-up's own tab strip is where the player switches target from there). Per-target results (destroy chance, average damage) don't render anywhere in `ResultsPanel` itself once there's more than one target - they moved into `DetailsDialog`'s own tab strip (below) so this panel stays a single compact row regardless of target count, rather than a list that grows with it (an earlier version rendered one `.readout__target-row` per target here, each with its own button - removed for exactly that reason). `TargetSequenceResult.engagementChance` is deliberately never surfaced here - a player-facing "X% engaged" note was tried and pulled for being too much incidental information on a panel meant to answer "did I kill it," not "how did the queue behave" - the field stays on the engine's own return type for whoever wants it (tests, a future feature), just not wired to any template.
- **`chanceToDestroyAllTargets(attacks, results)`** (`sequence/`) computes the true JOINT "every target destroyed" probability - NOT `destroyChanceByTarget().reduce((a, b) => a * b, 1)`, which would silently assume every target's own fate is independent (wrong whenever two targets share a weapon: the same dice decide both). It groups target indices into connected components via union-find over `attacks[].eligibleTargetIndices` (two targets union'd whenever some attack lists both, or has `eligibleTargetIndices` unset - eligible for everyone, unioning the whole set), then multiplies together the highest-INDEX target's own `finalDestroyChance` from each component - exact for exactly the cases `computeMultiTargetSequenceOdds` itself is exact for (see that function's own doc comment), since a later target's mass, by construction of the passthrough/injection chain, can never reach it without every earlier rival sharing a row with it already having died. `OddsCalculator.chanceToDestroyAll` (a `computed<number | null>`, `null` with a single target) calls this using `sequencedAttacks()` and `sequence()` (both already computed for the engine call, so this is a cheap, synchronous post-processing step - no new engine run, no worker round-trip) and feeds `ResultsPanel`'s own `chanceToDestroyAll` input.
- **`DetailsDialog`**: every input became a by-target array (`shotRowsByTarget`, `damagePointsByTarget`, `maxDamageProbabilityByTarget`, `destroyChanceByTarget`, `averageDamageByTarget`, plus `targetNames`); `open(targetIndex = 0)` sets a local `selectedIndex` signal read throughout the template as `...ByTarget()[selectedIndex()]`. A `.target-tabs` strip (one tab per target, each showing its own destroy chance AND average damage - the only place either is shown once `ResultsPanel` has collapsed to its single summary line, see above) renders ONLY when `targetNames().length > 1`, so - same principle as `ResultsPanel` above - a single-target sequence's Details pop-up is unchanged from before. (An `engagementChanceByTarget` input and matching "X% chance this target is even attacked" note existed briefly here too - removed for the same reason as `ResultsPanel`'s own note above.)
- **`OddsCalculator.focusStrategySummaries`** (`computed<string[]>`) turns every target's own `result.focusStrategy` (see the Attacker Focus section above) into one `summarizeFocusStrategy` line PER (attacker, target) pair actually engaged, rather than merging tallies across targets the way an earlier version did - `reachesTarget(attackerIndex, targetIndex)` (checking `sequencedAttacks()` for a row with that `attackerIndex` and an `eligibleTargetIndices` that includes `targetIndex`, or unset) skips a pair entirely when NONE of that attacker's own rows can even reach that target, since `focusStrategy` is seeded from every Focus-enabled attacker regardless of eligibility (see single-target.ts) and would otherwise print a misleading "rarely finds it worth spending Focus here" line for a target the attacker could never touch. `attackerName` passed into `summarizeFocusStrategy` becomes `"${attackerName} vs ${targetName}"` once `results.length > 1`, and just the plain attacker name for a single target (nothing to disambiguate) - unchanged output for every pre-existing single-target sequence, byte for byte, same as `ResultsPanel`/`DetailsDialog`'s own single-target branches above.

### Numeric fields as `<select>` rather than `<input type="number">`

Every field with a known range (DEF, ARM, Boxes, Focus/Fury points, MAT/RAT/AAT, POW, Dice, Shield amount, spell stat bonus amount) is a `<select>` rather than an `<input type="number">`, so that picking a value opens a native picker on mobile instead of the keyboard. The option lists are generated once via `range(start, end)` (`range.util.ts`).

**`MiniFieldSelect` (`mini-field-select/mini-field-select.ts`)** - one `.mini-field` labelled `<select>`, covering the Target row's DEF/ARM/Boxes, `AttackerCard`'s MAT/RAT/AAT, and `AttackSubCard`'s Type/ROF/Dice/POW/Dice: the same shape (a label, a `<select>` looping over a fixed options array, writing back through a string-to-value parser), previously hand-written at every one of those call sites. A **generic** component (`MiniFieldSelect<T>`), since the value type genuinely differs per field - `number` (ARM/Boxes/Dice), `number | 'KD'` (DEF), `number | '-'` (POW), `AttackType` (Type), `RofValue` (ROF):
```ts
readonly label = input.required<string>();
readonly signal = input.required<WritableSignal<T>>();
readonly options = input.required<readonly T[]>();
readonly narrow = input(false);
readonly parse = input<(raw: string) => T>((raw) => raw as unknown as T);
```
Takes the `WritableSignal<T>` itself (`[signal]="target().def"`, `[signal]="row.diceCount"`, ...) rather than a value/output pair, matching how every other signal-per-field domain model in this app (`AttackRow`, `TargetState`) is already read and written directly wherever it's used - the template binds `[ngModel]="signal()()"` / `(ngModelChange)="signal().set(parse()($event))"` internally. `parse` defaults to a plain cast, which is exactly correct for `Type`'s own select (a `<select>` change event is already the right string, nothing to convert) - every numeric field passes `toNumber`, `parseDef`, or `parsePow` explicitly instead. `label` is always a static attribute now (MAT/RAT/AAT are three separate `<app-mini-field-select>` instances with fixed labels on `AttackerCard`, one per stat, rather than a single field with a data-dependent label). An `optionLabel` input (`(v: T) => string`, defaulting to `` `${v}` ``) controls how each `<option>` renders - `AttackSubCard`'s Type select is the one consumer overriding it, swapping the raw `AttackType` value for its emoji (🗡️/🏹/🪄) via `TYPE_EMOJI`.

`shared/mini-field.css` moved out of `TargetPanel`'s and the old flat attack row's own `styleUrls` - now only `MiniFieldSelect` needs it, the same reasoning as `EffectTags`/`shared/effect-tags.css` above. Confirmed empirically that using `MiniFieldSelect` as a genuine child component (not content projection) doesn't disturb `.target-row`'s existing `align-items: flex-end` layout: `<app-mini-field-select>` becomes the actual flex item now instead of `.mini-field` directly, but since it renders exactly one child with no extra sizing of its own, its box is pixel-identical to `.mini-field`'s own - unlike `DialogShell`'s cross-component CSS pitfalls (this refactor doesn't need any combinator selector spanning `MiniFieldSelect`'s own template and its parent's, so that whole class of bug doesn't apply here).

**`ToggleSelect` (`toggle-select/toggle-select.ts`)** - a numeric counterpart to `ToggleButton`, reading as a plain pill toggle showing just its label at 0 (e.g. "Shield Guards") and "Label: N" once active (e.g. "Shield Guards: 2"), matching how a boolean `.toggle-btn` looks off/on, but opening a native value picker on click/tap instead of just flipping a boolean - a native `<select>` already opens exactly that picker on every platform this app targets, so no popover/overlay was needed. Same `WritableSignal`-as-input convention as `MiniFieldSelect`, but plain `number`-typed (not generic) since every current use is a numeric counter:
```ts
readonly label = input.required<string>();
readonly signal = input.required<WritableSignal<number>>();
readonly options = input.required<readonly number[]>();
readonly title = input('');
readonly formatValue = input<(v: number) => string>((v) => `${v}`);
readonly formatActive = input<(label: string, formattedValue: string) => string>((label, v) => `${label}: ${v}`);
readonly valueChange = output<number>();
```
**Two elements, not one: a decorative `.toggle-btn` label `<span>` on top of a fully invisible, absolutely-positioned real `<select>`** - an earlier version of this component just applied `.toggle-btn`/`.toggle-btn--active` directly to the `<select>` itself (`appearance: none` to strip native chrome), but that leaks: a browser's native dropdown popup can render its rows using the closed `<select>`'s own computed `color`/`background-color` - which is exactly why that version's popup showed the pill's brass "active" background, and why every `<option>` had to repeat "Label: N" (each option's own text is what the closed control itself displays, so the label couldn't be separated from the value there). The current markup splits the two concerns instead:
```html
<span class="toggle-select">
  <select class="toggle-select__native" [ngModel]="signal()()" (ngModelChange)="onChange($event)">
    @for (v of options(); track v) { <option [value]="v">{{ formatValue()(v) }}</option> }
  </select>
  <span class="toggle-btn toggle-select__label" [class.toggle-btn--active]="signal()() > 0" aria-hidden="true">
    {{ signal()() > 0 ? formatActive()(label(), formatValue()(signal()())) : label() }}
  </span>
</span>
```
The `<select>` (`.toggle-select__native`) carries `position: absolute; inset: 0;` (stretched to exactly cover the label below, so a click/tap anywhere on the visible pill opens it) and `opacity: 0` - and deliberately **only** `opacity`, never `color`/`background-color`: `opacity` is a paint-time compositing effect that hides the closed box without touching the computed style values a browser's native popup construction reads, so leaving `color`/`background` at their UA default keeps the popup legible instead of transparent-on-transparent. Its own `<option>` text is just the plain value - the label text lives only on the decorative `<span>` (`.toggle-select__label`, `pointer-events: none`), which never receives real interaction of its own; `.toggle-select__native:hover + .toggle-select__label` / `:focus-visible + ...` sibling selectors forward the real select's own interaction states onto it for the hover/focus-visible look. CSS painting order (an absolutely-positioned element always paints above a non-positioned sibling in the same stacking context, regardless of DOM order) is what lets the invisible `<select>` sit on top and capture every click while still being the FIRST element in markup - required for those adjacent-sibling selectors to reach the label placed after it.

`formatValue` (defaulting to the plain number) controls how a value renders in BOTH the native `<option>` list and the active pill, so the two always stay in sync - `TargetProfileDialog`'s Shield instance and the "Upkeep spells / Animi"/"Spells" sections' four DEF/ARM instances all pass `formatBonus = (v) => \`+${v}\`` (an inline component field, since every one of them is a flat stat bonus and every value should read as "+N", not "N") so both picker and pill show "+3" rather than "3"; every other use (Focus, Fury, KotD, Shield Guards, Scapegoats) leaves it at the default. `formatActive` (defaulting to `` `${label}: ${v}` ``, e.g. Shield's "Shield: +3") controls how the active pill COMBINES the label with that formatted value - those same four DEF/ARM instances pass `formatStatActive = (label, v) => \`${v} ${label}\`` instead, so a stat pill reads "+2 ARM" (value first) rather than "ARM: +2" (Shield's own label-first order), matching how a player would actually write a stat bonus.

Replaces the old label+`<select>` pairs for Focus, Fury, both Knowledge of the Damned counters, Shield Guards, Scapegoats, and (as of the Special rules unification below) Shield (`TargetProfileDialog`, see "Content of the Target profile pop-up" below). `valueChange` (fired after `signal()` is updated, with the new value) is the one addition beyond what `MiniFieldSelect` needs - it exists purely so `TargetProfileDialog` can enforce Focus/Fury's own mutual exclusivity from outside the component (see `TargetState` above); every other use (KotD, Shield Guards, Scapegoats, Shield) simply doesn't bind it, keeping the component itself free of any cross-field awareness. `:host { display: contents; }` (same trick `EditableName` uses) keeps the wrapping custom element out of the box model entirely, so `.toggle-select` (the inner wrapper `<span>`) is what `.toggle-group`'s own `display: flex; flex-wrap: wrap;` sees as the flex item.

**Pitfall to know about: `<select>` + `ngModel` always communicates in strings.** A native `<select>` only ever knows `value`s of type `string`; `(ngModelChange)` therefore always emits a string, never a number, even when `[ngModel]` is fed a number. Each binding explicitly converts back: `toNumber(raw)` (`select.util.ts`) for regular numeric fields, and `parseDef`/`parsePow` for DEF/POW, which additionally accept a sentinel value (`'KD'`, `'-'`) that must absolutely not be converted to a number.

### Actions

- `OddsCalculator.onAddAttacker()` / `onRemoveAttacker(id)`: append/remove a whole `Attacker` (`createAttacker()`; removal keeps at least 1 attacker, same "can't drop below one" guard the old flat list had).
- `OddsCalculator.onAddAttack(attacker)` / `onRemoveAttack(attacker, id)`: thin wrappers delegating to `attacker.model.ts`'s `addAttackTo`/`removeAttackFrom` - adds a row to *that* attacker by cloning its last attack's values (`cloneAttackRow`, fresh signals initialized to the same value - no shared reference with the source row, including a deep clone of `triggerEffects`), or a default row (`createAttackRow`) if it doesn't have one yet; removal keeps at least 1 attack on that attacker (removing the whole attacker is the only way to go lower).
- `OddsCalculator.onAttackerDrop(event: CdkDragDrop<Attacker[]>)` / `AttackerCard.onAttackDrop(event: CdkDragDrop<AttackRow[]>)`: both just `[...array]` then `moveItemInArray(copy, event.previousIndex, event.currentIndex)` then `signal.set(copy)` - `moveItemInArray` (from `@angular/cdk/drag-drop`) mutates the array it's given in place, so the copy is what makes this a signal-correct write (a fresh array reference) rather than a silent in-place mutation the signal would never notice.

### Reordering (`@angular/cdk/drag-drop`)

Attacker cards and attack sub-cards can each be dragged to reorder - `@angular/cdk`'s drag-drop module (no other part of Angular CDK/Material is used anywhere in this app) is the only external UI dependency in the project, added specifically because it's one of the only interaction patterns here that genuinely needs real pointer-tracking logic rather than a native HTML control; it's also the one library choice here that had to handle **touch** properly (native HTML5 drag-and-drop events don't fire on touchscreens at all), which ruled out a hand-rolled solution as the pragmatic choice for a mobile PWA.

- **Two independent, unconnected drop-list levels**, not one: `.attacker-list` (`cdkDropList` in `odds-calculator.html`) reorders `Attacker`s; each `AttackerCard`'s own `.attacker-card__attacks` (`cdkDropList` in `attacker-card.html`) reorders that ONE attacker's `AttackRow[]`. Since they're never given `cdkDropListConnectedTo` each other, CDK never lets an item cross from one list into the other - an attack can't accidentally end up dragged onto a different attacker, and an attacker card can't be dropped into an attacks list.
- **A dedicated drag handle (`cdkDragHandle`), not the whole card.** Both cards are dense with their own interactive elements (selects, icon buttons, the attacker name's `contenteditable` span) - making the entire card the `cdkDrag` root (with no handle) would mean the FIRST few pixels of every tap/click/drag-to-select-text on any of those controls also count as a potential drag gesture. A small `drag_indicator` (Material Symbols) glyph, `.drag-handle` (`shared/icon-btn.css`), is the only element wired with `cdkDragHandle`; `cdkDrag` itself stays on `<app-attacker-card>`/`<app-attack-sub-card>` (the parent template's `@for` item), so the handle can live inside a CHILD component's own template while still driving the PARENT's drag - `CdkDragHandle` resolves its owning `CdkDrag` by walking the DOM ancestor injector chain, which crosses component boundaries fine since it isn't a component-scoped lookup.
- **`touch-action: none` on `.drag-handle`** stops the browser's own touch-scroll gesture from competing with a drag gesture that starts on it - without it, a drag on a touchscreen would fight the page's normal vertical scroll.
- **`.cdk-drag-placeholder`/`.cdk-drag-preview`** (`shared/icon-btn.css`) are CDK's own generated elements, restyled to match the app's existing "empty slot" language: the placeholder left at the drop target gets the same dashed-outline treatment as the "+ Add attacker"/"+ Add attack" buttons; the floating preview that follows the pointer gets a drop shadow and a high `z-index` so it visibly separates from the list underneath it while dragging.

### Pop-ups (Attack edit / Attacker rules / Target profile / Details)

Per-attack special effects, per-attacker special rules (currently just Puppet Master), the target's resource points/capabilities/spells, and the results breakdown are moved into pop-ups rather than shown permanently, to keep the attacker card, attack sub-card, Target row, and results summary compact. Values with a fixed, small shape (attacker name/MAT/RAT/AAT, attack Type/ROF/Dice/POW/Dice) are edited directly on the card instead - name/MAT/RAT/AAT used to live in a separate `AttackerEditDialog`, and Type/ROF/Dice/POW/Dice used to live in the Attack edit pop-up alongside its effects, but grouping attacks by attacker gave both a natural home directly on the card, with room to spare once MAT/RAT/AAT and the attacker name moved there too. That original `AttackerEditDialog` was deleted outright once nothing was left for it to do; `AttackerRulesDialog` is a separate, later addition for a different purpose (attacker-level capabilities that genuinely don't fit inline, like Puppet Master's toggle) - not a revival of the deleted one. The Attack edit pop-up (still `AttackEditDialog` in code, titled "Effects" in the UI) is effects-only now.

Implementation: the native HTML **`<dialog>`** element (no modal/overlay CDK module - `@angular/cdk` is used elsewhere in the app, but only its drag-drop module, see "Reordering" above), wrapped in a shared **`DialogShell`** component (`dialog-shell/dialog-shell.ts`) rather than each of the seven dialogs (Attack edit, Attacker rules, Target profile, Details, About, Changelog, Feedback) owning its own `<dialog>` directly - this used to be a block of markup (the `<dialog>`, its click-outside-to-close handling, and the header/close-button) hand-copied verbatim into all of them, along with the `open()`/`close()`/`closeOnBackdropClick()` methods behind it.

**`DialogShell`**: takes `title` (required), `wide` (the `dialog--wide` width modifier - Details), and `framed` (the "fixed header/footer, only the middle scrolls" layout - Attack edit, Attacker rules, Target profile) inputs, and exposes `open()`/`close()`. Each consuming dialog component holds a `@ViewChild('shell') private shell?: DialogShell` and delegates its OWN public `open()` to `this.shell?.open()` - callers OUTSIDE these components (the orchestrator's template, `AppMenu`) don't change at all, since every dialog still exposes `open()` the same way it always did. There's no equivalent public `close()` left on any of the seven anymore: nothing outside a dialog's own template ever called it (every call site turned out to be the dialog's own close/done/cancel button), so a dialog's projected content just calls `shell.close()` directly via the `#shell` template reference variable, which content projection keeps in scope for everything nested inside `<app-dialog-shell #shell>...</app-dialog-shell>` in that dialog's own template.
- `AttackEditDialog` holds `protected readonly row = signal<AttackRow | null>(null)`, set by `open(row)` - a single pop-up instance is reused for every attack (rather than one per attack). `AttackerRulesDialog` mirrors this shape exactly, one level up: `protected readonly attacker = signal<Attacker | null>(null)`, set by `open(attacker)`, one instance reused for every attacker. `TargetProfileDialog` doesn't need an equivalent signal: there's only ever one target, so it takes `target` as a plain `input.required<TargetState>()` and `open()` takes no argument.
- `closeOnBackdropClick(event, dialog)` now lives ONCE, inside `DialogShell` itself: for a `<dialog>` opened in modal mode, a click on the `::backdrop` bubbles up a `click` event whose `target` is the `dialog` element itself (not a child) — this property lets us distinguish "click on the backdrop" from "click inside the content" without `stopPropagation()`. The Escape key closes the pop-up natively, with no extra code.
- **A footer (Reset/Done, Cancel/Send, ...) is projected into `DialogShell` via a `dialogActions` attribute** on the consumer's own wrapping `<div>`, matched by `<ng-content select="[dialogActions]" />` in `dialog-shell.html`; everything else projects into the default slot. Two things worth remembering if this pattern gets reused elsewhere:
  - **`<ng-content>` for one selector must appear exactly ONCE in the shell's template, not once per branch of an `@if`/`@else`.** An earlier version had `@if (framed()) { <div class="dialog__body"><ng-content /></div> } @else { <ng-content /> }` - two separate default-slot `<ng-content>` tags, one per branch - and NEITHER ever received any projected content (confirmed empirically: `.dialog__body` rendered with zero children, in every dialog, framed or not). The fix keeps a single `<ng-content />`, toggling `.dialog__body`'s presence via `[class.dialog__body]="framed()"` on an unconditionally-rendered wrapper `<div>` instead of branching the `<ng-content>` itself.
  - **A projected `[dialogActions]` element must be the ONLY root node of whatever `@if`/`@for`/`@else` block contains it** (Angular diagnostic NG8011). `AttackEditDialog`'s body content and its `dialogActions` footer both used to live inside the SAME `@if (row(); as row) { ... }` block (a pattern carried over unchanged from the old `EffectsDialog` it replaces); with several other root nodes alongside it, that block's content silently fell back to the DEFAULT slot instead of the named one. The fix splits it into two separate, sibling `@if (row(); as row) { ... }` blocks - one for the body (many root nodes, fine, since none of them need to reach a named slot), one containing only the `dialogActions` div (exactly one root node, so it routes correctly). `FeedbackDialog`'s `@if (state() === 'sent') { ... } @else { ... }` needed the same split, doubled up per branch.

**Content of the Attack edit ("Effects") pop-up**: the same effect sections the old standalone `EffectsDialog` had (see the functional documentation for the details of each effect) - # Atks/Type/ROF/Dice/POW live on `AttackSubCard` itself now, not in this pop-up (see "Numeric fields as `<select>`" above) - each section rendering a `<app-toggle-button>` (see below) per relevant `TriggerEffectRow`, pulled via `effectsFor(row, keys)`:
- "General": `effectsFor(row, generalEffectKeys)` → Jump the Shark (a single button, which drives both the to-hit roll and the damage roll), Blessed (resolved by `sequence/`'s `profileFor` - see "Target capabilities").
- "Attack": `effectsFor(row, attackEffectKeys)` → Auto-hit, Discard lowest, Discard highest, Reroll, Sanguine Fate — since each is its own independent `TriggerEffectRow`, Discard lowest and Discard highest can be active together with no special coordination logic.
- "Damage": `effectsFor(row, damageEffectKeys)` → Discard lowest, Discard highest, Reroll, Trash, Shatter, Chain Weapon (same resolution point as Blessed) — same principle on the damage side.
- "On hit": `effectsFor(row, hitCritPairKeys)`, each `<app-toggle-button [effect]="effect" activeValue="hit" />`, PLUS (appended inside the same `.toggle-group`) an `<app-toggle-select>` for `-X ARM`, bound directly to `row.armPenaltyHitAmount` - see below. `Dispel`, `Grievous Wounds`, and Sustained Attack needed no template change at all to appear here - `Dispel`/`Grievous Wounds` are just another `StatEffectType` added to `STAT_EFFECT_TYPES`, and `sustainedAttack` is just another key added directly to `HIT_CRIT_PAIR_KEYS` in `attack-row.model.ts` - `hitCritPairKeys` (`effectsFor`'s own input) picks up both generically.
- "Critical": the SAME `effectsFor(row, hitCritPairKeys)` list again, this time `activeValue="crit"` (each button pair shares one `TriggerEffectRow` - see `ToggleButton` below, which is exactly what makes "On hit"/"On crit" mutually exclusive for Sustained Attack the same way it already is for Armor Piercing/Decapitation - one `TriggerEffectRow.trigger` can only ever be `'off'`/`'hit'`/`'crit'`, never both), followed by `effectsFor(row, critOnlySimpleKeys)` → Brutal Damage, Shred, each a single (default `activeValue="hit"`) button, since neither has an "On hit" variant, then a SECOND `-X ARM` `<app-toggle-select>`, this one bound to `row.armPenaltyCritAmount`. Brutal Damage/Shred keep a short label ("Shred", not "Critical Shred") since they only ever appear here, already grouped under the "Critical" heading - their summary tags say "Crit Brutal Damage"/"Crit Shred" instead (`SUMMARY_LABEL_OVERRIDES`); Sustained Attack needs no override at all, since `effectsSummary`'s generic `trigger === 'crit'` → `"Crit " + label` prefix already produces "Crit Sustained Attack" for free, the same way it does for every other genuine hit/crit-pair effect.
- **`-X ARM` is deliberately NOT part of the generic `TriggerEffectRow`/hit-crit-pair system** every other effect above uses, because it's the one effect here with a genuinely user-editable amount, and clicking it should open the value picker directly - not flip a boolean pill that then reveals a SEPARATE amount control elsewhere (an earlier version worked exactly that way: a plain `ToggleButton` pair plus one standalone amount `<select>`/`<app-toggle-select>` below both sections, gated on the shared `TriggerEffectRow`'s `trigger !== 'off'`). Instead `AttackRow` carries two independent `WritableSignal<number>` fields, `armPenaltyHitAmount`/`armPenaltyCritAmount` (0 = off, `ARM_PENALTY_OPTIONS = range(0, 10)`) - the same "two fields kept exclusive at the call site" shape `TargetState.focusPoints`/`furyPoints` uses: `AttackEditDialog`'s `onArmPenaltyHitChange`/`onArmPenaltyCritChange` (bound to each `<app-toggle-select>`'s own `(valueChange)` output) zero the other field whenever one is set above 0, so a single `-X ARM` instance still triggers on a hit or a crit, never both, exactly as the old shared-`TriggerEffectRow` design guaranteed structurally. Both instances pass `[formatValue]="formatPenalty"` (`(v) => \`-${v}\`\`) and `[formatActive]="formatPenaltyActive"` (`(_label, v) => \`${v} ARM\`\`, ignoring the pill's own off-state label `"-X ARM"` - not a real noun like "Shield" or "DEF", so it's dropped once a concrete value is picked) so an active pill reads "-2 ARM" (value first), the same convention the "Upkeep spells / Animi"/"Spells" sections' DEF/ARM pills use. `TriggerEffectRow` itself lost its `amount` field entirely once `-X ARM` was the only key that ever used it - `createTriggerEffects`/`cloneTriggerEffects`/`resetEffects` all simplified accordingly, and `toSequencedAttack`'s `statEffects` mapping gained two `if`/`else if` pushes (translating whichever of the two fields is nonzero into the engine's own `{ type: 'armPenalty', trigger, amount }` shape - `sequence/`'s `StatEffect` itself is completely unaware this changed on the UI side).
- "Reset" (`resetEffects(row)`) and "Done" (`shell.close()`) side by side at the bottom of the pop-up (`.dialog__actions`, `flex: 1 1 0` each).

**`ToggleButton` (`toggle-button/toggle-button.ts`)** - one `.toggle-btn` / `.toggle-btn--active` (defined in `shared/dialog-sections.css`, listed in this component's own `styleUrls` too - see "Component split" above for why a shared partial needs re-listing per consumer) bound to a `TriggerEffectRow`:
```ts
readonly effect = input.required<TriggerEffectRow>();
readonly activeValue = input<EffectTrigger>('hit');
protected readonly label = computed(() => TRIGGER_EFFECT_LABELS[this.effect().key]);
protected readonly active = computed(() => this.effect().trigger() === this.activeValue());
```
`toggle()` clicks the already-active value back to `'off'`; clicking a different value (only reachable when a pair renders the SAME effect twice, once per `activeValue`) switches straight to it. This one component is EVERY toggle button in the Attack edit pop-up now - the simple ones (default `activeValue="hit"`, rendered once) and the hit/crit pairs (rendered twice, `activeValue="hit"` and `activeValue="crit"`) alike - replacing what used to be a hand-written `[class.toggle-btn--active]="row.x()"` / `(click)="row.x.set(!row.x())"` block repeated per effect. No separate `label` input: it looks its own label up from `TRIGGER_EFFECT_LABELS[effect().key]`, since that map already has to exist for `effectsSummary`'s sake.

**`EffectTags` (`effect-tags/effect-tags.ts`)** - the small pill-tag row shown under an attack sub-card (`effectsSummary(row)`, plus a `ROF <value>` tag - see `attack-row.model.ts` above) and under the Target row (`targetSummary(target)`): identical markup and CSS (`shared/effect-tags.css`) in both places, so both now render through this one component instead of each carrying its own copy of `@if (summary(...).length > 0) { <div class="effect-tags">@for (tag of summary(...); track tag.key) { <span class="effect-tag">{{ tag.label }}</span> } }`. Takes a single `tags = input.required<readonly EffectTag[]>()`, where `EffectTag` (`{ key: string; label: string }`) is a deliberately minimal shape - `effectsSummary`'s own `EffectSummaryTag` (`key: TriggerEffectKey`) and `targetSummary`'s `TargetSummaryTag` (`key: string`) both satisfy it structurally without either needing to import from the other's domain model. `shared/effect-tags.css` moved out of the old flat attack row's and `TargetPanel`'s own `styleUrls` - now only `EffectTags` itself needs it, since the `.effect-tags`/`.effect-tag` elements are entirely inside `EffectTags`'s own template, not projected from its callers (unlike `DialogShell`'s `dialogActions` slot - there's no content projection here at all, just a plain `tags` input).

**Content of the Attacker rules pop-up (`AttackerRulesDialog`)**: a single "Special rules" `.toggle-group` with one hand-written toggle button (`Attacker.puppetMaster`, a plain `WritableSignal<boolean>`) - the same hand-written-toggle pattern `TargetProfileDialog` uses below, for the same reason: `Attacker`'s own booleans aren't `TriggerEffectRow`s, so `ToggleButton` (coupled to that shape) doesn't fit. No Reset button (matches `AttackEditDialog`'s own single-surface precedent - there's nothing to "start over from" with just one toggle, unlike `TargetProfileDialog`'s many fields). Built to grow: more attacker-level capabilities (Puppet Master was the first, per the functional documentation's former roadmap entry) land as more toggles in the same section, not a new pop-up each time.

**Content of the Target profile pop-up (`TargetProfileDialog`)** follows the same general "toggle-button pop-up" shape, but its own booleans (`unyielding`, `carapace`, `rapidHealing` on `TargetState`) are a different domain with no `TriggerEffectRow`/hit-crit concept at all, so they're still hand-written toggle buttons rather than `<app-toggle-button>` instances:
- "Resources": two `<app-toggle-select>` instances (Focus/Fury) in one `.toggle-group` - see `ToggleSelect` below. `TargetProfileDialog`'s own `onFocusChange`/`onFuryChange`, bound to each instance's `(valueChange)` output, keep them mutually exclusive.
- "Knowledge of the Damned": two independent `<app-toggle-select>` instances (Offensive/Defensive, `offensiveKnowledgeOfTheDamned`/`defensiveKnowledgeOfTheDamned` on `TargetState`, `KOTD_OPTIONS = range(0, 10)`) in one `.toggle-group` - no mutually-exclusive "pick one" needed, so no `(valueChange)` handler either.
- "Shield Guard / Scapegoat": same shape as "Knowledge of the Damned" above - two independent `<app-toggle-select>` instances (`shieldGuards`/`scapegoats` on `TargetState`, `SHIELD_GUARD_OPTIONS = range(0, 10)` and `SCAPEGOAT_OPTIONS = range(0, 4)` - a deliberately different range from every other counter here, see `sequence/`'s `MAX_SCAPEGOATS`).
- "Special rules": Tough / Tough Steady (mutually exclusive with each other AND with "Dispellable special rules"' own Tough toggle below - see `toggleToughKind` just below), an `<app-toggle-select>` for Shield (`shieldAmount` on `TargetState`, `SHIELD_AMOUNT_OPTIONS = range(0, 10)` - folded from a separate boolean + conditionally-shown amount `<select>` into this one control, the same shape as every other counter here, no `(valueChange)` handler needed), Unyielding (mutually exclusive with "Dispellable special rules"' own Unyielding toggle - `toggleUnyielding`), Carapace, Rapid Healing — all six controls share one `.toggle-group` section.
- **"Dispellable special rules"**: two plain toggle buttons, Unyielding and Tough, in one `.toggle-group`, mutually exclusive with their permanent counterparts in "Special rules" above (a model is Tough, or Unyielding, one way at a time - never counted as both a permanent AND a dispellable grant simultaneously, even though nothing in the underlying `effective*` OR-logic would otherwise prevent it): `toggleUnyielding(target)`/`toggleDispellableUnyielding(target)` each flip their own field, then clear the OTHER one whenever the flip lands on `true`; `toggleToughKind(target, kind)` (shared with the "Special rules" Tough/Tough Steady buttons - see `TargetState` above) additionally clears `dispellableTough` whenever it lands on anything but `'off'`, and `toggleDispellableTough(target)` clears `toughKind` back to `'off'` whenever IT lands on `true` - the same "flip one field, zero the other(s) it conflicts with" pattern `onFocusChange`/`onFuryChange` use for Focus/Fury, just fanned out across three buttons instead of two. An earlier version had no component method here at all (`[class.toggle-btn--active]="t.dispellableUnyielding()"`, `(click)="t.dispellableUnyielding.set(!t.dispellableUnyielding())"` inline in the template) - the exclusivity requirement is what brought the handler methods back.
- **"Upkeep spells / Animi" and "Spells"** - two more `.toggle-group` sections, each holding a DEF and an ARM `<app-toggle-select>` (`TargetState.upkeepSpellDefAmount`/`upkeepSpellArmAmount` and `spellDefAmount`/`spellArmAmount` respectively, all four `SPELL_BONUS_OPTIONS = range(0, 10)`), replacing what used to be a single dynamic "Custom effects" repeatable list (`@for (spell of t.spellBonuses(); ...)`, each row an `<app-editable-name>` plus DEF/ARM toggle-selects plus Spell/Dispellable `.toggle-btn--sm` toggles plus a remove button - see `TargetState`'s doc comment above for the full history of that design and why it was dropped). All four instances pass `[formatValue]="formatBonus"` and `[formatActive]="formatStatActive"` so they read "+2 ARM"/"+3 DEF" (value first) rather than Shield's own "Shield: +N" order - see `ToggleSelect` above. No `(valueChange)` handler on any of the four (unlike Focus/Fury or the "Dispellable special rules" toggles) - a model can have both a DEF and an ARM bonus from spells simultaneously, and "Spells" and "Upkeep spells / Animi" are independent categories, so nothing here needs to zero anything else.
- "Reset" (`resetTargetProfile(t)`) / "Done" (`shell.close()`).

  **`@let t = target();` rather than `@let target = target();`**: since `target` is both the component's `input.required<TargetState>()` signal AND the natural name for its unwrapped value, naming the `@let` the same as the input causes `NG8016: Cannot read @let declaration 'target' before it has been defined` (the RHS `target()` call resolves against the *new* `@let` binding being declared, not the outer input signal, so it doesn't even reach the real input). Using a differently-named local (`t`) sidesteps the collision entirely.

**Buttons within a given category sit in a `flex-wrap: wrap` container (`.toggle-group`)**, rather than `nowrap` like the Target row: unlike that (a fixed, known number of fields), the number of active effects/capabilities is open-ended, so a pop-up needs to be able to accommodate any combination by wrapping, without ever widening the `<dialog>` (whose width stays capped at `width: min(90vw, 480px)`, unchanged).

**Fixed header/footer, scrolling body (`.dialog__content--framed` + `.dialog__body`, both in `shared/dialog-sections.css`).** Both the Effects and Target profile pop-ups keep their header (title + close button) and footer (Reset/Done) in place while only the sections in between scroll:
- `.dialog__content--framed` turns the container into a `display: flex; flex-direction: column; overflow: hidden;` box; its direct-child header and `.dialog__actions` footer get `flex-shrink: 0`.
- The middle content is wrapped in a `.dialog__body` div with `flex: 1 1 auto; min-height: 0; overflow-y: auto;`, so it's the only part that scrolls once it overflows the dialog's `max-height: 80vh`.
- Since the first section title now sits inside `.dialog__body` right after the header rather than directly after it, `.dialog__body > .dialog__section-title:first-child` removes that first title's own top border/margin/padding — otherwise it would show its own separator line just below the header's bottom border, reading as a doubled line a few pixels apart.
- `DetailsDialog` doesn't use this modifier (its `.dialog__content` scrolls as a single block) since it has no fixed footer to protect.

### `AppMenu` — the header hamburger dropdown

Unlike every other pop-up in this app, `AppMenu`'s dropdown is **not** a native `<dialog>` - it's a plain `position: absolute` panel anchored under the ☰ trigger button, toggled by a signal (`isOpen`). A short, fixed list of actions doesn't need a `<dialog>`'s backdrop/focus-trap semantics, and a full-screen modal for a handful of menu items would be heavier than the content warrants. Two consequences of not being a `<dialog>`:
- **No `::backdrop` to catch an outside click**, so `AppMenu` binds Angular's global event syntax directly in the template - `(document:click)="onDocumentClick($event)"` and `(document:keydown.escape)="close()"` - rather than relying on the `closeOnBackdropClick` pattern every other pop-up uses. `onDocumentClick` walks the click's `target` up against the menu's own root element (`@ViewChild('menuRoot')`) via `Node.contains()`; the click that *opens* the menu (on the trigger button, itself inside `menuRoot`) also reaches this handler through the same bubbling, but since its target is contained within `menuRoot` it's correctly treated as "inside" and doesn't immediately re-close what `toggle()` just opened.
- **These global listeners still integrate with zoneless change detection** the same way a plain template `(click)` binding does: Angular's own event-binding instructions (not zone.js) are what schedule change detection after a listener runs, and that applies equally to `document:`/`window:`-scoped global listeners declared in a template, not just element-scoped ones - no special handling was needed here.

`AppMenu` itself owns none of these actions - it only emits `reset`/`openAbout`/`openChangelog`/`openFeedback` outputs and closes itself, mirroring how `TargetPanel`'s cog button emits `openProfile` rather than owning `TargetProfileDialog` (see "Component split" above). One item is the odd one out, not going through an output: "Support me" is a plain `<a>` styled as `.app-menu__item` linking straight to Ko-fi - there's no state or dialog behind it, just a URL, so wiring it through `OddsCalculator` the way the other three are would've been indirection for its own sake.
- **Reset** (`OddsCalculator.resetAll()`): calls the new `resetTargetFully(target)` (`target-panel.model.ts`) - unlike `resetTargetProfile` (used by the Target profile pop-up's own Reset, which deliberately leaves DEF/ARM/Boxes alone since those live outside that pop-up), this additionally sets `target.def`/`arm`/`boxes` back to their defaults (`DEFAULT_DEF`/`DEFAULT_ARM`/`DEFAULT_BOXES`, now named constants shared between `createTargetState` and `resetTargetFully` so the two can't silently drift apart) - then `attackers.set([createAttacker()])` collapses the attack sequence back to one default attacker with one default attack. No confirmation step, matching every other Reset button in the app.
- **About** (`AboutDialog`): a static-content pop-up, no signals or inputs of its own - just the plain `<dialog>`/`open()`/`close()`/`closeOnBackdropClick` shape every other dialog component uses, with a block of copy in its template instead of form controls. It's also the one dialog in the app that can open itself, unprompted: `ngAfterViewInit` checks `localStorage.getItem('chancemachine.hasSeenAbout')`, and if that key is unset, sets it and calls its own `open()` - a first-time visitor sees the explanation without having to find the menu, and it never fires again on that device/browser afterward (regardless of whether that first pop-up was actually read, or how quickly it was closed - the flag is set unconditionally the moment it auto-opens, not on some "did they engage with it" heuristic). `ngAfterViewInit` specifically (not the constructor) is what guarantees `@ViewChild('dialog')` has already resolved by the time this runs, since `open()` needs the native `<dialog>` element to exist in the DOM to call `showModal()` on it. Manually opening About from the menu goes through the same `open()` but never touches the localStorage key either way. `HAS_SEEN_ABOUT_KEY` is exported (not a private module-level string) specifically so `ChangelogDialog` can read it - see below.
- **Changelog** (`ChangelogDialog`): see below.
- **Feedback** (`FeedbackDialog`): see below.

### `ChangelogDialog` — "what's new", and the versioning scheme behind it

There's no version number anywhere else in this app (`package.json`'s `"version": "0.0.0"` is never read at runtime) - `changelog-dialog/changelog.data.ts` IS the versioning scheme: a hand-maintained, newest-first array of `{ date, items }` entries, and `LATEST_CHANGELOG_DATE` (simply `CHANGELOG[0].date`) is the single source of truth for "what's the current version". A visitor's progress is tracked the same way, as a plain ISO date string in `localStorage['chancemachine.lastSeenChangelogDate']` - "have they seen everything" is just a string comparison (`lastSeen >= LATEST_CHANGELOG_DATE`) between the two, no separate incrementing counter or semver needed. Adding a new entry to `CHANGELOG` (with today's date, newest-first) is the entire mechanism for "there's something new to show" - nothing else needs to change.

**Auto-opens like `AboutDialog`, but with an extra rule: never on a visitor's very first ever load.** On that load `AboutDialog` already covers "what is this app", and dumping the ENTIRE changelog history on someone who's never used any earlier version would be noise, not news - so that visit just silently records `LATEST_CHANGELOG_DATE` without ever showing the pop-up, exactly as if they'd already seen it (a returning visitor later that day would then correctly see nothing new, not the full history retroactively).

Telling "first ever load" apart from "returning visitor, been a while" means checking the SAME `HAS_SEEN_ABOUT_KEY` `AboutDialog` uses (imported from `about-dialog.ts`, not duplicated as a second magic string) - but this read has to happen BEFORE `AboutDialog`'s own `ngAfterViewInit` can have set it (that's what "was it *already* set" means), and `ngAfterViewInit` is the wrong place to do that: an earlier version of this code deferred the read into a `queueMicrotask(...)` inside `ChangelogDialog.ngAfterViewInit`, reasoning that every sibling's synchronous `ngAfterViewInit` for one change-detection pass - including `AboutDialog`'s - completes before any microtask runs. That reasoning was backwards in practice: `AboutDialog.ngAfterViewInit` sets the key *before* returning on a visitor's very first ever load, so by the time the deferred microtask ran, it always observed the POST-set value and concluded "not their first visit" on every load, including the very first one - both dialogs auto-opened, stacked on top of each other (only caught after shipping, once actually used in a browser - `document.querySelector('dialog[open]')` in earlier manual verification only checked the first match in document order, silently missing the second one).

The fix reads it in the **constructor** instead (as a class field initializer, `private readonly wasAlreadySeenAbout = hadAlreadySeenAbout()`): Angular constructs every component in a view tree - running every field initializer/constructor body - before running ANY of their `ngAfterViewInit` hooks, for the WHOLE tree, a strict phase separation rather than an ordering convention. This is guaranteed to see the value from before this page load's dialogs ran, regardless of `<app-about-dialog>`'s position relative to this component in `odds-calculator.html`, unlike either the `ngAfterViewInit`-microtask attempt above or a plain synchronous read inside `ngAfterViewInit` (same bug, no microtask needed to trigger it).

Reading `localStorage` in the constructor reintroduces the OTHER problem an even earlier version of this code hit: `app.spec.ts`'s `should create the app` test calls `TestBed.createComponent(App)`, which DOES run every component's constructor (unlike `ngAfterViewInit`, which needs `fixture.detectChanges()` - never called in that test), and this project's Vitest/Node test environment doesn't provide a working `localStorage` that early (a Node 25 quirk - see the `--localstorage-file` warning in `ng test` output), throwing `TypeError: localStorage.getItem is not a function`. `hadAlreadySeenAbout()` (the free function `ChangelogDialog` calls for this) wraps the read in a try/catch, falling back to `true` ("assume already seen", i.e. never auto-open) if it throws - a real browser always has a working `localStorage`, so the catch branch only ever matters for that test, and "can't tell" failing safe as "don't auto-open" is a reasonable default regardless.

### `FeedbackDialog` — posting to a Google Apps Script Web App

The app has no backend of its own (it's a static PWA), so the Feedback form posts to a **Google Apps Script Web App** bound to a spreadsheet - `google-apps-script/feedback.gs` at the repo root (NOT part of the Angular build; its header comment documents the paste-and-deploy setup) exposes a `doPost(e)` that appends one row per submission (timestamp, type, message, email, data, user agent) to a "Feedback" sheet, creating that sheet with a header row on first use, and also sends a notification email (`MailApp.sendEmail`, `replyTo` set to the sender's email when they left one) so a submission doesn't just sit unnoticed in the spreadsheet. `data` is the reporter's current targets/attackers/weapons config as JSON (`serializeFeedbackData` in `feedback-data.ts`, captured once when the dialog opens via `FeedbackDialog.open(data)`) rather than the page URL a prior version sent - there's only ever one page, so the URL carried no information, while the full config lets a report be reproduced exactly instead of relying on prose description.

`FEEDBACK_ENDPOINT_URL` is a module-level constant in `feedback-dialog.ts` holding the deployed Web App URL (`.../exec`) from `feedback.gs`'s own setup steps.

The notification email re-indents `data` for readability (`prettyPrintJson_` in `feedback.gs`: `JSON.parse` then `JSON.stringify(_, null, 2)`, falling back to the raw string if it isn't valid JSON) and renders it in a `<pre><code>` block - the sheet cell itself keeps the compact single-line form `serializeFeedbackData` actually sends, since re-indenting there would just spread one submission across many spreadsheet rows visually.

**`mode: 'no-cors'`, not `'cors'` - a deliberate, necessary tradeoff, not an oversight.** Apps Script Web Apps don't reliably send back `Access-Control-Allow-Origin` headers a cross-origin `fetch` can read, so requesting in `'cors'` mode fails outright even when the script executes correctly server-side; `'no-cors'` is the standard, documented workaround for calling Apps Script from client-side JS. The cost: the response becomes **opaque** - `submit()`'s `await fetch(...)` resolving only means the request left the browser, not that `doPost` actually ran or wrote the row (a wrong URL, an undeployed script, or an error inside `doPost` won't surface as a caught exception here, only a genuine network failure will). The UI is deliberately honest about this asymmetry: a successful `fetch` shows "Thanks! Your message has been sent" (optimistic), and only a thrown exception - not a script-side failure - shows the retry notice.

### App shell: title/Results fixed, Target and Attack sequence share the rest

The orchestrator is structured as a three-zone app shell stacked in a fixed-height container (`height: 100dvh` on `.page`, propagated via `display:flex; flex-direction:column; height:100%` on `:host` then `.panel`, `.panel__body`). `<app-results-panel>` (`.readout`, a direct flex child of `.panel__body`) gets `flex-shrink: 0; min-width: 0;` **on its own host element** so it keeps its natural (now single-row) size regardless of target count. `<app-target-panel>` is no longer a direct child of `.panel__body` itself - both Target and Attack sequence now follow the identical two-level shape: an outer `<section>` (`.console--targets` / `.console--attacks`, plain sections in the orchestrator's own template, not extracted into components) is the actual flex item of `.panel__body`, and an inner list (`.target-list` / `.attacker-list`) is what actually has `overflow-y: auto` - so "+ Add target"/"+ Add attacker" stay visible below their own scrolling list regardless of how many cards it holds. `TargetPanel`/`AttackerCard`'s own host elements are the real flex items inside their respective lists, each needing its own `:host { display: block; flex-shrink: 0; }`; spacing between cards is a plain `gap` on the list.

**The two outer sections are deliberately NOT symmetric.** Both are `flex-shrink: 1` (so a genuine squeeze - more combined content than fits - shrinks each proportional to how much content it has, rather than one starving the other to zero), but only `.console--attacks` is `flex-grow: 1` plus carries a `min-height` floor (in `dvh`, so it scales with the device rather than being a fixed pixel count): Attack sequence is the primary workspace, so it both stretches into genuinely spare room and keeps a guaranteed minimum under a squeeze. `.console--targets` is `flex-grow: 0` and `min-height: 0` - it is never bigger than its own content, full stop, so "+ Add target" always sits directly under the last target card instead of floating with dead space beneath it once the viewport has more room than Targets actually needs.

**`min-height: 0` is essential at every level of this flexbox chain - AND on the correct level.** Without it on `.console--targets`/`.console--attacks` themselves, a flex item in a column refuses by default to shrink below its content's height (the same `min-*:auto` pitfall as for the width of the Target row, see below) - which would have prevented either list from ever being smaller than its content, and therefore from ever scrolling: the whole page would have grown taller instead. This is exactly the regression the `styleUrls` ordering bug (see "Component split" above) caused: a shared rule silently overriding `flex-shrink` back to `0` on `.console--attacks` broke this chain, and the symptom looked identical to a missing `min-height: 0` even though the actual cause was cascade order, not a missing rule. A related but distinct pitfall bit this same layout again later: `.console--attacks`'s own `min-height` floor was first written on `.attacker-list` (one level further in) instead of on `.console--attacks` itself - `.panel__body`'s own shrink algorithm happily shrank `.console--attacks` below that floor anyway (nothing stopped it there), and `.attacker-list`'s min-height then just overflowed its own non-clipping parent section, leaking all the way up into the whole page scrolling as a block. A `min-height` floor has to live on the exact flex item the OUTER shrink decision is being made about, not on a descendant one level deeper.

`100dvh` rather than `100vh` on `.page` (`app.css`): on mobile, the browser's address bar appears/disappears while scrolling, which changes the actually visible height. `100vh` is computed against the maximum height (bar hidden), which can leave the bottom of the screen (here, Results) partially hidden behind the address bar when it's visible; `dvh` (*dynamic* viewport height) tracks the actually visible height at all times. `100vh` is kept as the first-written fallback for browsers that don't support `dvh`.

**`--app-height` (`app.ts`), a JS-computed height that wins over `100dvh` once set.** An earlier fix for the installed PWA disabled the browser's pull-to-refresh gesture entirely (`html { overscroll-behavior-y: none; }` in `src/styles.css`) because, on some Android WebView versions, that gesture's reload triggered a `dvh` recalculation glitch that left the fixed layout mis-sized until the user manually scrolled. That traded away a real feature: pull-to-refresh is also how a user manually forces the installed PWA to pick up a newly-deployed version, since the Angular service worker (`ngsw`, `app.config.ts`) only activates an already-downloaded update on the next full navigation, not automatically. The actual fix addresses the root cause instead of avoiding the gesture: `App`'s constructor sets a `--app-height` custom property from `window.visualViewport.height` (falling back to `window.innerHeight` where `visualViewport` isn't supported), refreshed on every `visualViewport`/`window` `resize` event, and `.page` uses `height: var(--app-height, 100dvh)` - the JS-driven value taking priority over the plain `100dvh` declaration once it's set, with `100dvh` remaining the fallback for the brief window before JS runs on first paint. `visualViewport.resize` fires reliably when the address bar (or an on-screen keyboard) changes the visible area, which is more consistent across WebView versions than relying on `dvh` to recompute on its own - so the layout now stays correct through a pull-to-refresh reload, and the gesture itself is left enabled (`overscroll-behavior-y` back to its default `auto`).

### Hidden scrollbars

`.target-row` (horizontal scrolling, `shared/scrollable-row.css`) and `.attacker-list` (vertical scrolling, in the orchestrator's own CSS) hide their scrollbar (`scrollbar-width: none` + `::-webkit-scrollbar { display: none }`) while remaining scrollable (mouse/trackpad/touch) - a visible scrollbar would have ended up right under/next to the fields' digits and visually cluttered them.

### The Target row: compact, centered and spaced, fitting on a single line (mobile included)

The Target row uses `flex-wrap: nowrap` rather than `wrap`: the goal is for everything to fit on a single line even on a narrow phone, scrolling horizontally rather than wrapping to a new line if needed. Fields are centered horizontally on the row (`justify-content: safe center` on `.target-row`) with generous `gap` between them; the values inside each field are themselves centered (`text-align`/`text-align-last: center` on `.mini-field__input`, `align-items: center` on `.mini-field`). Attacker/attack cards don't need this treatment - each is its own self-contained box stacked vertically, not a row of fields that has to stay on one line - so `shared/scrollable-row.css` (see "Component split" above for why a shared partial file rather than duplicated CSS) now has just this one consumer; the attack-edit pop-up's own field row wraps instead (`flex-wrap: wrap` - see "Pop-ups" above), since a dialog already scrolls vertically.

The `safe` keyword in `justify-content: safe center` avoids a known pitfall: with a plain `center`, if the row ends up overflowing (a very narrow viewport, or more fields added later), the start of the content can become unreachable by scrolling in some browsers - `safe` falls back to `start`-like alignment in that specific case, so horizontal scrolling (`overflow-x: auto`) can always reveal everything.

**Vertical alignment of controls (`--control-h`).** Every control on a row (`<select>`, Effects/cog/✕ buttons) shares the same explicit height via the `--control-h` variable (defined on `:host` in the orchestrator's `odds-calculator.css`, inherited by every child component since CSS custom properties cascade through the DOM regardless of Angular component boundaries), rather than relying on `align-items: flex-end` alone to align them visually. Before this variable, each control had a slightly different height (padding/border specific to each element type), and even though `flex-end` mathematically aligned their box bottoms pixel-perfectly, the visually different sizes still read as misaligned. A checkbox wrapped in a `<span class="mini-field__control">` (`height: var(--control-h)`, centered) reserves the same "control row" height as the other fields without enlarging the checkbox itself.

**Custom, minimal `<select>` arrow.** A `<select>`'s native arrow reserves a browser/OS-dependent amount of space (often 20px+), which left little room to fit everything on one line once numeric fields became `<select>`s. `.mini-field__input--select` (`shared/mini-field.css`) disables native rendering (`appearance: none`) and draws a tiny arrow via `background-image` (two linear gradients forming a chevron), which lets it control exactly how much space the arrow takes up - and keeps the value genuinely centered rather than offset by a wide arrow.

Two CSS pitfalls hit while implementing "fits on a single line", worth keeping in mind if these rules are ever revisited:
- **`min-width: 0` on `:host`**: the orchestrator is itself a flexbox item of the `.page` container (`app.css`). By default, a flexbox item refuses to shrink below its content's minimum width (`min-width: auto`) - with `nowrap` rows, this minimum content can exceed the screen's width, which would have made **the whole page** overflow (not just scroll within the row) without this `min-width: 0`. The classic flexbox pitfall of "min-width:auto prevents shrinking". Each split-out child component that's a direct flex item of `.panel__body` (`TargetPanel`, `ResultsPanel`) needs the same `min-width: 0` on its own `:host` for the same reason.
- **Global `box-sizing: border-box`** (`src/styles.css`): without it, `width` on inputs doesn't count padding or border, which made width calculations (aiming for "everything fits within 375px") unpredictable - each input rendered several pixels wider than its declared width.

**Measurement pitfall to know about if these widths are tweaked by hand in the browser**: this component runs without zone.js (Angular zoneless), so after modifying a signal from the console (`ng.getComponent(...)`), reading `scrollWidth`/`clientWidth` **immediately** can return pre-render values - the view update is scheduled, not synchronous. Waiting for two `requestAnimationFrame`s before measuring (or simply re-checking after a following screenshot) avoids wrongly concluding that a row "fits" when the DOM hadn't yet caught up with the new state. The same applies to reading `getComputedStyle`/`classList` synchronously right after a script-dispatched `.click()` in the same evaluation: a click handled by Angular's zoneless change detection doesn't flush the DOM update before the *next* task boundary, so a follow-up check needs to happen in a separate script execution (e.g. a separate browser-automation call), not immediately after, or it'll read stale state.

## PWA

- `@angular/service-worker` enabled only outside dev mode (`enabled: !isDevMode()`), `registerWhenStable:30000` registration strategy.
- `ngsw-config.json`: prefetches application files (HTML/CSS/JS/manifest), lazy-caches icons.
- `public/manifest.webmanifest` + `public/icons/*`: multi-resolution icons for home-screen installation (Android and iOS).
- The calculation engine itself makes no network calls: the app works fully offline once loaded/installed. Feedback and analytics (see below) are the only network-dependent things in the app, and neither blocks or degrades any other feature when unavailable.

### Custom install prompt (`PwaInstall`, `src/app/pwa-install.ts`; `PwaInstallBanner`, `src/app/odds-calculator/pwa-install-banner/`)

A root-provided `@Injectable` (the only other one in the app is `OddsEngine` - note neither uses Angular's conventional `Service` class-name suffix, an intentional deviation from the style guide kept consistent across both) wrapping the non-standard `beforeinstallprompt` event, so the app can offer its own install trigger at a moment the visitor chooses, instead of relying purely on whatever install affordance the browser shows on its own (see https://web.dev/learn/pwa/installation-prompt, which this follows closely):

```ts
window.addEventListener('beforeinstallprompt', (event) => {
  event.preventDefault();
  this.deferredPrompt = event as BeforeInstallPromptEvent;
  this.installable.set(true);
});
```

- **`BeforeInstallPromptEvent`** (`prompt(): Promise<void>`, `userChoice: Promise<{ outcome }>`) is hand-declared, not part of TypeScript's DOM lib typings - it's Chromium-only and not a standardized event, so `window.addEventListener('beforeinstallprompt', ...)` falls through TS's generic string-event-name overload (inferring a plain `Event`), and the handler casts it once captured.
- **Eagerly constructed from `App`'s own constructor** (`private readonly pwaInstall = inject(PwaInstall);`, a class field, not read again there) rather than waiting for `PwaInstallBanner` to inject it first - registers the listener as early as possible, the same reasoning `trackPwaInstall()`/`updateAppHeight` already get called directly in that constructor for. `PwaInstallBanner` injects the same root-provided singleton to read `installable()` and call `install()`.
- **`install()` always clears the captured event afterward, accepted or dismissed either way** - a `beforeinstallprompt` event can only be shown once, matching the banner's own disappearance immediately after use.
- **Also listens for `appinstalled`, independently of `install()`**, to reset `installable` back to `false` - covers installing through some route OTHER than this service's own captured event (a browser's separate omnibox install icon isn't gated by the `preventDefault()` above, since accepting it doesn't go through the same event at all).
- **Checks `window.matchMedia('(display-mode: standalone)').matches` once at construction** and skips registering either listener at all if already running as the installed app (nothing to offer, and the event wouldn't fire again for an already-installed PWA anyway). Wrapped in try/catch, defaulting to "not standalone" on failure - this project's Vitest/Node test environment doesn't provide a working `window.matchMedia` (`App`'s eager `inject(PwaInstall)` means `app.spec.ts` constructs this service without ever rendering into a real browser), the same "fail safe instead of crashing" pattern `ChangelogDialog` already uses for its own `localStorage` access.
- **Only Chromium-based browsers (Chrome/Edge, Android and desktop) fire `beforeinstallprompt` at all - Safari (iOS and desktop) never does**, so `installable` simply stays `false` there and the banner never appears - no manual "Add to Home Screen" fallback instructions yet (see the functional documentation's roadmap).

`PwaInstallBanner` is rendered directly in `odds-calculator.html`, between `.panel__header` and `.panel__body` - visible on its own rather than tucked inside `AppMenu`, since `beforeinstallprompt` is a one-shot opportunity worth surfacing directly instead of behind a menu tap. It shows only while `pwaInstall.installable()` is `true` and a local `dismissed` signal is `false`; the **✕** button just sets that signal, a session-only dismissal (no `localStorage`, unlike About/Changelog's "seen it" flags) since re-showing it on the next load costs nothing and there's no repeated pop-up to guard against. The install button itself is styled with `border: 1px solid var(--brass); color: var(--brass)` to match `.panel__eyebrow` (the "ChanceMachine" title text), filling solid on hover.

## Analytics (GoatCounter)

`index.html` loads GoatCounter (`<script data-goatcounter="https://chancemachine.goatcounter.com/count" async src="//gc.zgo.at/count.js">`) - a cookie-free, privacy-friendly page-view counter chosen specifically to avoid the GDPR cookie-consent banner a cookie-based tool like Google Analytics would require for EU visitors. It counts page views automatically on its own; `src/app/analytics.ts` is for the handful of CUSTOM events this app tracks on top of that.

- **`trackPwaInstall()`** (called once from `App`'s constructor in `app.ts`, alongside the existing `updateAppHeight` viewport wiring): listens for the standard `appinstalled` event and reports it as a GoatCounter event (`{ path: 'pwa-install', title: 'PWA install', event: true }`). `appinstalled` fires the same way regardless of which install path was taken - the browser's own promotion UI, this app's own install banner (`PwaInstall`/`PwaInstallBanner`, see "Custom install prompt" above), or a platform's manual "Add to Home Screen" - so tracking never needs to hook `beforeinstallprompt` itself, even though `PwaInstall` separately does (for a different reason: building its own prompt trigger, not tracking).
- **`trackPwaInstallDismiss()`** (called from `PwaInstallBanner`'s own ✕ button handler): the decline-rate mirror of `trackPwaInstall()` above, same shape (`{ path: 'pwa-install-dismiss', title: 'PWA install banner dismissed', event: true }`).
- **`trackDetailsOpen(data)`** (called from `OddsCalculator.onDetailsOpened()`, chained alongside `detailsDialogRef.open($event)` in odds-calculator.html's `(showDetails)` binding): reports `{ path: 'details-open', title: data, event: true }`, where `data` is the CURRENT targets/attackers/weapons config as JSON - the exact same string `serializeFeedbackData` produces for the Feedback pop-up (see "`FeedbackDialog` — posting to a Google Apps Script Web App" above), passed through `OddsCalculator.feedbackData()`. `path` stays the fixed literal `'details-open'` rather than embedding `data` there - GoatCounter's own dashboard aggregates hits BY path, so a unique path per call would scatter every distinct configuration into its own "page" instead of counting toward one aggregate total; `title` is where per-hit detail belongs, visible in GoatCounter's raw hit log without disturbing the aggregate count. **Deduplicated across repeat opens**: a module-level `lastTrackedDetailsData` in `analytics.ts` remembers the last config actually tracked, and `trackDetailsOpen` no-ops when the new `data` is identical - opening/closing the pop-up repeatedly without changing anything only counts once. Resets on a page reload (a fresh module load), which is exactly when a "first open" should count again.
- **`window.goatcounter` is typed via `declare global { interface Window { ... } }`** in `analytics.ts` rather than pulling in a package for it - GoatCounter's script defines this global itself at runtime, there's no npm package to depend on. Every call goes through `window.goatcounter?.count(...)` (optional chaining, not a null check + throw): the script may not have loaded yet, or may be blocked outright by an ad/tracker blocker, and analytics silently doing nothing in that case is correct - it must never be able to break the app.
- **Installed/offline PWA usage isn't visible to GoatCounter at all** beyond the `appinstalled` event itself: any session where the app is opened without a network connection (or where the analytics script is blocked) simply never reaches `chancemachine.goatcounter.com`, the same limitation any client-side web analytics tool has for an installable, offline-capable PWA.
- **`ngsw-config.json`'s `dataGroups` explicitly declares both GoatCounter URLs** (`gc.zgo.at/count.js`, the tracking beacon at `chancemachine.goatcounter.com/count`), with a `"freshness"` strategy (network first, 3s timeout, falls back to cache only if the network genuinely fails). This isn't caching for performance - it's a fix for a real production bug: `@angular/service-worker` intercepts EVERY fetch on a page under its scope, including cross-origin ones, and a request that doesn't match any `assetGroups`/`dataGroups` pattern surfaced as a synthetic `504 Gateway Timeout (from service worker)` in the browser's network tab instead of just passing through to the network - only reproducible against a real deployed build, since the service worker is disabled in dev mode (`enabled: !isDevMode()`), which is why local testing never caught it. Any future third-party/cross-origin script added to `index.html` needs the same treatment, or it'll hit the same failure mode.

## Design decisions worth remembering

- **Targeted rules edition: Warmachine MK4** (user's choice). Base mechanics (2d6, boost, double = critical, Tough) are considered stable and shared across editions; specific named effects are implemented with the most widely accepted wording, but still need to be checked/adjusted against the exact MK4 rulebook — see the functional documentation for the details of these assumptions.
- **Attack order within a sequence: defined by the user**, no automatic optimization (a deliberate product decision, see the functional documentation for the rationale and its limits).
- **Effects: a short, exact list rather than a generic system** — extensible within `AttackEffects`/`RollModifiers` (`attack-model.ts`) and `StatEffect`/`StatEffectType` (`sequence/`) as new rules get confirmed, but always a closed, named set of cases rather than an engine for arbitrary expressions.
- **Reroll: a fixed optimal policy, no configurable threshold on the UI side** — rerolling a missed to-hit roll, or a below-average damage roll, mathematically maximizes the expected result; asking the player for a threshold would have added no useful flexibility for the cost of extra interface complexity.
- **Persistent target penalties: a minimal typed state (`DebuffState`), with value tables built lazily rather than a dense multi-dimensional table** — the number of penalty dimensions (9) made a dense table combinatorially intractable, while the number of states *actually* reachable for a given sequence stays low in practice. An earlier version precomputed the reachable set up front (`computeReachableDebuffStates`, since removed) purely to know what to eagerly build; once Knowledge of the Damned's charge counters made the OTHER dimensions (`pmMask`/`kotdOffLeft`/`kotdDefLeft`) big enough for that eager approach to waste real time building never-reached combinations, `getValueTableAt` (`sequence/`) replaced it with memoized on-demand construction - see `sequence/`'s own "Lazy value tables" doc comment. This choice keeps the calculation exact either way (no approximation on the final result), just cheaper: only states/resource-combinations some real branch of the computation actually reaches ever get a table built for them at all.
- **Target's Focus/Fury spending: optimal via backward induction, not a simple "spend if this hit would otherwise kill me" reflex** — relevant because a point can be worth more spent earlier (to preserve boxes useful for surviving a future hit) than kept "just in case". The calculation stays exact (no heuristic), at the cost of a value table per attack and per reachable penalty state rather than a simple local rule. Defensive Knowledge of the Damned gets the same treatment; Puppet Master/Offensive Knowledge of the Damned deliberately don't (see `sequence/`'s own Knowledge of the Damned section for why).
- **Critical Shred resolved as a bounded self-referential value problem rather than dynamically growing the sequence**: cloning and inserting an attack into `attacks[]` mid-calculation would make the sequence length itself probabilistic, breaking the per-step value-table indexing everywhere else. Instead `attackChainValue`/`resolveAttackChainForward` (`sequence/`) resolve one attack instance and recurse into another instance of THEMSELVES on a shredding crit, capped at `MAX_SHRED_DEPTH` — see the dedicated section above for the full design, including a real exponential-blowup performance bug (naive per-branch forward-simulation recursion) caught and fixed during development.
- **The calculation runs in a Web Worker, not a plain `computed()` signal** — see `odds-engine.ts`'s own section above for the full design. Forced by a real constraint, not a preference: JS is single-threaded, and a slow (multi-second, achievable with Knowledge of the Damned's charge counters pushed high) synchronous call would freeze the whole tab with no way to show progress or even repaint. `worker.terminate()` + a fresh worker per request (rather than a request-ID/generation counter that lets a stale computation finish and just discards its result) was chosen specifically to avoid burning CPU on superseded work, at the cost of the (cheap, single-digit-millisecond) respawn overhead.
